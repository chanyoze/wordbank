# 조용히 실패하는 결함 8종 — WebSquare/cips 실무 기록

작업 중 여덟 종류의 버그를 만났는데, **공통점이 하나 있었다. 에러가 안 난다.**
콘솔은 깨끗하고 화면만 틀리다. 그래서 매번 "왜 안 되지?" 로 시작해 여러 라운드를 돌았다.

이 글은 그 8종을 유형별로 정리한 것이다. 특정 회사·고객과 무관한 프레임워크 일반 구조만 다룬다.

> **WebSquare**: 국내 SI 에서 널리 쓰는 상용 UI 프레임워크. XML(wqxml)로 화면을 선언하고 JS 로 제어한다.
> **cips**: 그 위에 조직이 얹은 공통 라이브러리 레이어(데이터셋 등록·버튼·오토핏 등)를 가리키는 예시 이름.

## 1. 옵션 전달 파이프라인이 중간에 끊긴다

설정값(옵션)이 화면까지 오는 경로는 3단이다.

```
① SQL 이 뽑는다        select 문이 OPT_048 을 조회
② dataList 가 받는다    <w2:column id="OPT_048"> 선언
③ JS 가 읽는다          dataList.getCellData(0, "OPT_048") == "T"
```

**②가 빠지면 WebSquare 는 응답 필드를 그냥 버린다.** 예외도 경고도 없다.
`getCellData` 가 `null` 을 돌려주고 `== "T"` 가 `false` 가 되어 **옵션이 꺼진 것처럼 동작**한다.

실제로 한 화면에서 SQL 은 19종을 내려주는데 dataList 에는 9종만 선언돼 있었다.
나머지 10종이 전부 `false` 로 읽혀 관련 컬럼이 통째로 사라졌다.
사용자 눈에는 "기능이 누락된 것" 으로 보이고, 옵션 설정을 아무리 확인해도 켜져 있으니 원인을 못 찾는다.

### 같은 유형 — 그리드 컬럼 vs dataList 컬럼

그리드 본문에는 컬럼이 있는데 dataList 에 없으면 **항상 빈칸**이 된다. 검사는 단순한 집합 연산이다.

```
그리드 gBody 컬럼 id 집합 − dataList 컬럼 id 집합 = 값이 안 채워지는 컬럼
```

### 정적 스캐너로 잡는다

세 지점에서 옵션명 집합을 추출해 차집합을 낸다. DB 도 브라우저도 필요 없이 텍스트만 본다.

| 판정 | 조건 | 의미 |
|---|---|---|
| 🔴 치명 | ③에 있고 ②에 없음 | 항상 빈 값 → 옵션이 반대로 동작 |
| 🟠 주의 | ②에 있고 ①에 없음 | 선언만 있고 안 내려옴 |
| ⚪ 정리 | ①에 있고 ②에 없음 | 버려짐(무해) |
| ⚪ 정리 | ①②는 되는데 ③이 안 읽음 | 미사용 |

```bash
# ① SQL — <select id="..."> 블록만 잘라 옵션 패턴 수집
awk -v q="$QID" '$0 ~ ("<select id=\""q"\"") {f=1} f && /<\/select>/{exit} f' "$SQ" \
	| grep -o 'OPT_[0-9_]*' | sort -u > /tmp/sql.txt
# ② dataList 선언, ③ JS getCellData 호출 도 같은 방식으로 뽑아 comm 으로 비교
comm -23 /tmp/js.txt /tmp/dec.txt   # 🔴 JS 는 읽는데 선언 없음
```

## 2. 예외를 감싸면 프레임워크의 에러 표시가 죽는다

### 프레임워크는 이미 준비돼 있었다

공통 JS 에 업무 오류(business error) 처리가 들어 있었다.

```js
} else if (resultData.errorCode == "E9999") {       // 업무 오류
	const i = resultData.messageDetail.indexOf("ORA-20009");
	if (i != -1) {
		// ORA-20009 뒤의 안내문만 잘라낸다
		resultData.ddMsg = 잘라낸문구;
		com.alert(잘라낸문구, null, null, "warn");   // warn 경고창
	}
}
```

그리고 하단 메시지바가 `ddMsg` 유무로 빨간 배너를 가른다.

```js
if (statusCode != "S" && isEmpty(ddMsg)) {
	$(".notice").show();   // 빨간 배너 — 코드 결함용
} else {
	$(".notice").hide();
}
```

즉 **DB 프로시저가 올린 안내문이 잡히면 warn 알림이 뜨고 빨간 배너는 자동으로 숨겨진다.**
설계는 처음부터 그렇게 돼 있었다.

### 무엇이 막았나

```java
try {
	service.doSomething(param);
} catch (Exception e) {
	throw new RuntimeException("[모듈] 처리에 실패했습니다.", e);   // ← 여기
}
```

응답 객체는 `messageDetail` 에 `ex.getMessage()` 를 넣는다.
**래퍼 예외의 `getMessage()` 는 래퍼 문구만 돌려준다.** 원인(`ORA-20009: ...`)이 사라지니
프레임워크의 추출이 실패하고, warn 알림 없이 빨간 배너만 남는다.

### 조치 — 최하위 원인으로 교체

```java
private Exception rootCause(Exception aoEx) {
	Throwable cur = aoEx;
	while (cur.getCause() != null && cur.getCause() != cur) {
		cur = cur.getCause();
	}
	return (cur instanceof Exception) ? (Exception) cur : aoEx;
}
// result.setMsg(STATUS_ERROR, "처리 실패", rootCause(e));
```

컨트롤러 한 곳에 넣으면 그 컨트롤러의 모든 엔드포인트가 함께 고쳐진다.

### 곁가지 — 직접 띄우면 중복된다

원인을 모르던 단계에서 애플리케이션 코드가 알림을 직접 띄우게 했더니 모달이 두 번 뜨는 구조가 됐다.
**프레임워크가 이미 표시한다면 앱 코드는 "실패 시 후속 콜백을 태우지 않는 것" 만 하면 된다.**

```js
if (isFail(res)) return;      // 재조회·팝업 닫기 차단만
if (typeof cb === "function") cb(res);
```

## 3. 오토핏 높이 계산이 컨테이너를 모른다

### 계산식이 이게 전부다

```js
var 조정높이 = 팝업높이 - 컴포넌트.nFixSize - 동적보정 - 전역보정;
```

**컨테이너도 형제도 보지 않는다.** 그래서 `nFixSize` 에는 그 컴포넌트 **위아래의 모든 몫**을
사람이 직접 인코딩해야 한다. 형제가 하나 늘거나 배치가 바뀌면 그 순간 틀어진다.

게다가 선언값에 **타입별 가산분**이 몰래 더해진다.

```
gridView +200 / tabControl +197 / group +197 / textarea +206 ...
```

`322` 라고 적으면 실제로는 `522` 로 동작한다. 최소값 클램프(기본 100)도 있어서,
높이가 **정확히 100** 이면 계산 결과가 아니라 클램프가 걸린 것이다.

### 결론 — 형제가 여럿이면 상수로 못 맞춘다

자기 영역을 혼자 쓰는 컴포넌트만 상수가 안정적이다.
형제가 여럿이면 오토핏 대상에서 빼고 화면이 직접 소유하는 게 맞다.

```js
const 넘침 = 컨테이너.scrollHeight - 컨테이너.clientHeight;   // 브라우저가 계산해준 값
const 여백 = (컨테이너바닥 - 패딩) - 마지막요소바닥;
const 조정 = (넘침 > 0) ? -넘침 : (여백 > 3 ? 여백 : 0);

설정높이 += 조정;
그리드.setSize(null, 설정높이);
setTimeout(재확인, 60);        // 재그리기가 비동기라 한 번 더 본다
```

### ⚠️ 함정 2가지 — 이것 때문에 다섯 라운드를 돌았다

**① 읽는 값과 쓰는 값의 단위가 다르다.**
`setSize` 는 CSS 높이를 넣는데 `getBoundingClientRect().height` 는 테두리(약 3px)를 포함해 돌려준다.
측정값을 되읽어 다시 설정하면 영원히 제자리걸음한다.

```
회차: 3 / 높이: 557 / 넘침: 3
회차: 4 / 높이: 557 / 넘침: 3   ← 값이 안 변한다
```

→ **설정한 값을 따로 누적**해야 한다.

**② 기준 박스를 잘못 잡으면 탭 스트립만큼 초과한다.**
탭컨트롤의 *바깥* 박스를 기준으로 잡으면 탭 스트립(약 42px)과 패딩이 빠져 그만큼 넘친다.
실제 제약 박스는 탭 **컨텐츠 body** 요소다.

### 정답 높이가 고정값이 아니다

```
회차: 0 / 설정: 223 / 조정: 349 / 컨테이너: 953·953   ← 초기 마크업 높이
회차: 0 / 설정: 572 / 조정:  -4 / 컨테이너: 953·957   ← 오토핏 후
회차: 1 / 설정: 568 / 조정: -18 / 컨테이너: 953·971   ← 데이터 로드로 행이 채워짐
회차: 2 / 설정: 550 / 조정:   0 / 컨테이너: 953·953   ← 수렴
```

회차 1의 `-18` 이 핵심이다. 조회 응답이 도착해 하위 그리드에 행이 생기면서 높이가 늘었다.
**정답이 시점마다 다르므로 1회 계산이 아니라 수렴 루프여야 한다.**

## 4. 특정 콜스택에서는 동적 submission 이 동작하지 않는다

공통팝업(LOV) 종료 콜백 안에서 동적 submission 을 실행하면
엔진 내부에서 `Cannot read properties of null (reading 'action')` 으로 죽는다.

원인을 코드로 추적하기 어려웠는데, **전수 조사가 결정적이었다.**

```
lov.onClose 를 정의한 화면 715개
  → 동적 submission 사용   0건
  → 선언형 submission + loadData  109건
```

0/715 는 취향 문제가 아니라 **프레임워크가 허용하지 않는 패턴**이라는 뜻이다. 선언형으로 바꿔 해결했다.

```xml
<xf:submission id="wsmInqXxx" ref="data:json,조회조건맵" target="data:json,결과리스트"
	action="/api/xxx.do" method="post" mediatype="application/json"></xf:submission>
```

주의점 둘:

- 데이터셋 등록에 `oRtrvSubmission` 을 빠뜨리면 `loadData` 가 **조용히 무동작**한다.
- `ref` 로 지정한 맵은 **그 맵 id 를 키로 감싸서** 전송된다(서버가 `body.get("<맵id>")` 로 꺼냄).
  서버 계약이 특정 키를 요구하면 맵 id 를 그 이름으로 고정해야 한다.

### 곁가지 — onclick 문자열이 다른 scope 에서 재해석된다

클릭 처리가 끝나기 전에 새 창이 열리면, 대기 중이던 `ev:onclick` 문자열이
**새로 열린 팝업 scope 에서 다시 평가**된다. 그 결과가 이것이다.

```
scwin.onSanctnBtn('...') is not a function
```

함수는 멀쩡히 정의돼 있다. **잘못된 scope 에서 찾는 것**이다.
완화책은 창을 여는 동작을 `setTimeout(fn, 0)` 으로 다음 tick 에 미루는 것.

## 5. 부모→자식 조회조건은 자동으로 넘어가지 않는다

`oParentData` 로 부모-자식 관계를 등록해도 **조회조건은 화면이 직접 채워야 한다.**
프레임워크는 관계만 알지 값은 옮겨주지 않는다.

```js
cips.dd.event.data.onBeforeDataLoad = function(dataId) {
	const 복사 = function(대상맵, 부모, 컬럼들) {
		const i = 부모.getRowPosition();
		컬럼들.forEach(c => 대상맵.set(c, 부모.getCellData(i, c)));
	};
	if (dataId == 자식.getID()) {
		복사(자식조회조건, 부모, ["KEY1", "KEY2", "KEY3"]);
	}
};
```

한 화면에는 이 훅이 **통째로 없었다.** 조회조건 맵도, submission 도, 데이터셋 등록도 다 있는데
**채우는 코드만** 빠져서 빈 조건으로 조회 → 0건 → 화면이 그냥 비어 보였다.

DB 에는 데이터가 있는데 화면만 비어 있으니, 서버 검증 오류와 화면 상태가 어긋나 보여
"데이터가 꼬였나?" 로 오판하기 쉬운 유형이다.

## 6. 정적 검사 도구가 조용히 통과한다 — 가장 위험한 유형

앞서 만든 스캐너의 검사 대상 하나가 **이미 없는 파일**을 가리키고 있었다.
화면이 둘로 분리되면서 파일명이 바뀌었는데 스크립트를 안 고친 것이다.

```bash
chk "화면 이름" "wqxml/OldScreen.xml" ...   # 지금은 없는 파일
```

없는 파일을 `awk` 에 넘기면 **빈 결과가 나오고 "없음 ✅" 로 통과**한다.
즉 **초록불인데 아무것도 안 본 상태**였다. 그동안 계속 그랬다.

```bash
# 대상이 없으면 조용히 빈 검사를 한다 — 파일이 분리·개명되면 여기서 먼저 걸러야 한다
for f in "$WQ" "$SQ"; do
	[ -f "$f" ] || { echo "  🔴 대상 파일 없음: $f"; return; }
done
```

**교훈: 정적 검사 도구는 "대상이 존재하는가" 를 먼저 확인해야 한다.**
통과(✅)와 미검사(빈 결과)가 같은 출력으로 보이면, 도구가 없는 것보다 있는 게 더 위험하다.
거짓 안심을 주기 때문이다.

## 7. 없는 API 를 부르면 검증이 통째로 죽는다

필수값 검증을 넣었는데 **빈 값으로도 저장이 통과**했다. 검증이 빠진 줄 알았지만, 코드에는 있었다.

```js
if(!oRow.USER_NO) {
    msg.alert("승인자는 필수 입력 항목입니다.");   // ← 이 유틸에 alert 은 없다
    return false;
}
```

그 메시지 유틸이 제공하는 것은 `confirm` · `error` · `warn` · `info` 넷뿐이었다.
없는 함수를 부르니 `TypeError` 가 나고, 예외가 **검증 함수 전체를 빠져나가** `return false` 에 도달하지 못했다.
결과적으로 **검증이 있는데도 저장이 그대로 진행**됐다.

### 왜 안 보이나 — 프레임워크가 훅을 감싸기 때문

공통 트리거 계열은 개발자 훅을 **전부 try/catch 로 감싸는** 경우가 많다.

```js
try {
    if(typeof dd.event.save.onClickBefore == "function") {
        var bRtn = dd.event.save.onClickBefore();
        if(typeof bRtn == "boolean" && !bRtn) return;
    }
} catch(e) {
    devConsole.error(...);   // 콘솔에만 남는다
}
```

훅이 던진 예외는 콘솔에만 찍히고 흐름은 계속 간다. 화면에는 아무 흔적이 없다.
게다가 그 로거가 **개발자 콘솔 전용**이면 운영에서는 아무도 보지 못한다.

이 구조 자체는 합리적이다 — 개발자 코드 하나가 프레임워크 전체를 멈추면 안 되니까.
대가는 **훅 안의 버그가 조용해진다**는 것이다.

### 잡는 법

API 표면이 좁은 유틸(`msg`, `util` 류)은 **오탈자·유사명을 IDE 가 못 잡는다.** 동적 객체라 타입 정보가 없다.
호출 목록과 정의 목록을 뽑아 차집합을 보는 편이 확실하다.

```bash
# 호출된 이름
grep -roh 'msg\.[a-zA-Z]*' src | sort -u
# 실제 정의된 이름
grep -n 'msg\.[a-zA-Z]* *= *function' lib/framework.js
```

## 8. 같은 함수인데 진입 경로마다 게이트가 다르다

저장할 것이 없는 상태에서 **버튼을 클릭하면** 에러가 났다.

```
Cannot read properties of null (reading 'action')
```

그런데 **같은 동작의 단축키로는 에러가 안 났다.** 처음엔 단축키가 다른 창을 잡는 줄 알았다. 아니었다.

### 두 경로는 결국 같은 함수를 탄다

```
클릭      → commonTrigger.save.onClick()
단축키    → getActiveWindowInfo() → fireEvent("save") → 같은 함수
```

활성 창 판정 함수는 모달 팝업 목록을 역순으로 훑어 **가장 위 모달을 돌려준다.**
팝업이 모달이면 단축키도 정상적으로 그 팝업에 도달한다. 경로 차이가 아니었다.

### 차이는 단축키에만 붙은 선행조건이었다

```js
if(option._bIsActiveLov) return false;                       // LOV 활성
for(const p of getAllPopupList()) { ...메시지창이면... return; }  // 확인창 활성
if(oDataset && oDataset.oGrid.isEditing()) return false;     // 그리드 편집 중
```

**에러가 안 난 게 아니라 저장이 시작조차 안 된 것**이었다.
그리드 셀에 포커스가 있으면 편집 중으로 잡혀 조용히 중단된다.

### 진짜 결함은 그 아래 있었다

동적 submission 생성 헬퍼에 **null 가드가 없었다.**

```js
var obj = getSubmission(id);
if (obj === null) { createSubmission(opt); obj = getSubmission(id); }
else { deleteSubmission(id); createSubmission(opt); obj = getSubmission(id); }
executeSubmission(obj, data);   // ← null 이면 여기서 .action 을 읽는다
```

생성이 실패해도 그대로 넘긴다. **4번(콜스택 제약)과 같은 함수, 같은 실패 지점**이다.
근본은 호출부가 *"보낼 것이 없는데 전송을 태운"* 것이었다.

### 잡는 법

- **증상이 경로마다 다르면 게이트를 의심한다.** 같은 함수를 탄다면 차이는 그 앞에 있다
- 전송을 감싸는 자리에 **"보낼 것이 있는가" 판정을 명시**한다. 없으면 아예 부르지 않는다
- 그 판정에 **보류 중인 삭제분**을 빠뜨리지 않는다 — 화면 행 수가 0 이어도 삭제가 대기 중이면 전송 대상이다

## 정리

| 결함 | 왜 안 보이나 | 잡는 법 |
|---|---|---|
| 옵션 3단 끊김 | 선언 없는 필드는 조용히 버려짐 | 집합 차집합 정적 검사 |
| 래핑 예외 | 원인 메시지가 가려짐 | 최하위 cause 로 교체 |
| 오토핏 높이 | 프레임워크가 컨테이너를 안 봄 | 실측 + 수렴 루프 |
| 콜스택 제약 | 엔진 내부에서 null | 선례 전수 조사 |
| 부모→자식 조회조건 | 관계는 알지만 값은 안 넘김 | 로드 직전 훅 확인 |
| 도구 미검사 | 빈 결과 = 통과 | 대상 존재 가드 |
| 없는 API 호출 | 훅 예외를 콘솔로만 흘림 | API 표면 대조 |
| 경로별 게이트 차이 | 한쪽은 시작조차 안 함 | 진입 경로별 선행조건 비교 |

여덟 개 모두 **에러가 안 나고 화면만 틀린다.** 그래서 화면만 보고 원인을 추측하면 라운드를 돈다.

매번 국면을 바꾼 건 추측이 아니라 데이터였다.
**선례 전수 조사**(0/715), **브라우저 실측 로그**(넘침 3px 이 안 줄어드는 걸 눈으로 확인),
**배포본 타임스탬프 비교**(빌드는 됐는데 배포가 안 됨). 추측을 한 번 더 얹는 대신
"무엇이 사실인지" 를 재는 쪽이 항상 빨랐다.
