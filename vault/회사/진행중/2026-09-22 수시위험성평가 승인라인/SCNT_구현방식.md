수시위험성평가([ATMS26-012])에 **SCNT 표준 승인관리**를 붙이면서 결정한 구현 방식을 정리한다. 기존에는 승인선이 공사팀장/안전팀장/현장소장 **3단계로 하드코딩**(`APPRV_C/BD/A_USER_NO`)돼 회사마다 다른 결재 라인을 담을 수 없었다. SCNT는 승인라인을 **데이터로 관리**하므로 이 제약이 사라진다. 아래는 두 승인 엔진을 옵션으로 가르고, 기존 회차를 안전하게 보존하는 방법이다.

## 두 엔진을 옵션으로 가른다

기존 결재 엔진(`SFAS_OPT_060`)과 신규 SCNT 엔진(`SFAS_OPT_060_003`)은 **상호배타**다. 한 현장에서 둘 다 켜지면 안 된다.

> ⚠️ **2026-09-03 정정** — 원래 *"admin UI가 양방향 잠금으로 막는다"* 고 적었으나 **그 가드는 아직 없다.**
> 옵션 관리 화면 4종에 `SFAS_OPT_060_003` 항목 자체가 없어 지금은 DB를 직접 고쳐 운용한다.
> 그래서 손으로 `T/T` 를 만들 수 있고 실제로 두 현장에서 발생했다(데이터 조치 완료).
> **운영 배포 전 필수 작업**이다.

| 상태 | `SFAS_OPT_060` | `SFAS_OPT_060_003` |
|---|---|---|
| 기존 결재 | `T` | `F` |
| **SCNT 표준승인** | **`F`** | `T` |
| 승인 미사용 | `F` | `F` |

### 이 설계의 대가 — 조용한 함정 ⚠️

SCNT 현장은 `060 = F`로 저장된다. 그래서 `060='T'`를 "승인 활성"으로 읽던 기존 SQL이 SCNT 현장을 **"승인 없음"으로 오판**한다. 약 15~20파일·40여 조건절을 아래처럼 일괄 수정해야 한다.

```sql
SFAS_OPT_060 = 'T'  →  (SFAS_OPT_060 = 'T' Or SFAS_OPT_060_003 = 'T')
SFAS_OPT_060 = 'F'  →  (SFAS_OPT_060 = 'F' And SFAS_OPT_060_003 = 'F')
```

빠뜨리면 미승인 건이 목록에 노출되거나 상태 라벨이 공백이 된다 — 증상이 조용해서 리뷰가 가장 필요한 부분이다.

## 옵션을 바꿔도 기존 회차는 그대로 (소급 유지)

가장 많이 나오는 질문이다. 결론은 **기존에 만들어진 회차는 건드리지 않는다**. 옵션 변경 이후 새로 만든 회차부터 SCNT로 진행된다. 즉 한 화면에 두 방식이 섞여 보이고, 회차마다 자기가 시작한 방식으로 끝까지 간다.

왜냐하면 진행 중이던 회차를 갑자기 SCNT로 갈아엎으면, 예컨대 안전팀장 승인을 기다리던 회차가 기존 버튼은 사라지고 SCNT로는 아직 요청 전이라 **승인도 취소도 못 하고 멈추기** 때문이다. 승인 이력은 감사 성격이라 사후에 바뀌면 곤란하기도 하다.

SCNT 회차의 상태값은 다음과 같이 흐른다.

| 상태 | 언제 |
|---|---|
| 작성중 | 아직 승인라인을 만들지 않음 |
| 요청대기 | 승인라인 저장, 승인요청 전 |
| 승인대기 | 승인요청함 |
| 승인중 | 결재 중간 단계 진행 |
| 승인반려 | 반려됨 |
| 승인완료 | 최종 승인됨 |

상태 옆에 **단계 / 대기자** 컬럼이 붙어 지금 몇 단계이고 누구 차례인지 목록에서 바로 보인다(기존 결재 회차는 빈칸). SCNT 회차의 상태값을 클릭하면 승인 팝업이 열린다.

## 데이터 구조

호스트 테이블 `TSF_ASSMNT_RECEIVE`에 SCNT 승인요청을 링크할 컬럼 4개(`CFM_COMPANY_ID`·`CFM_PROJ_CODE`·`CFM_DEM_SN`·`CFM_STS_CODE`)를 추가했다. 기존 `STTS_CD`는 **그대로 둔다** — 컷오버가 현장별이라 한 현장에 구/신 데이터가 공존하므로 한 컬럼에 합치면 구분이 안 되기 때문이다.

`CFM_STS_CODE`는 SCNT의 `TBASE_SANCTN_DEM.STS_CODE`(REG/DEM/PROG/REJ/CMPL)를 **번역 없이 그대로 복사**한다. Handler가 복사만 하면 되어 틀릴 여지가 없고, 표시명은 공통코드 함수(`SF_GetCommonCodeName()`)가 처리한다. 승인 단계명·대기자는 저장하지 않고 조회 시 SCNT에서 주입한다(이중 소유 방지).

## 화면 구성

- **외곽 목록**: `060_003=T`면 승인 컬럼을 세트로 교대한다 — `상태|공사팀장|안전팀장|현장소장` → `상태|단계|대기자`. 목록이라 행별 SCNT 조회는 N+1이 되므로, 키를 모아 `selectSanctionDemandMap()` **1회 호출** 후 메모리 병합한다.
- **승인 팝업**(신규): 상태 클릭 시 열리는 조회 전용 화면. 상단 평가서 요약 / 하단 내용·검토의견 / 우측 승인패널(단계 이력 + 승인·반려·취소). 외곽 3컬럼이 요약, 팝업 승인패널이 상세다.

## 종합검토의견을 승인과 분리했다

기존에는 종합의견이 승인 액션의 산출물이었다(승인 버튼 → 의견 팝업 → 단계별 컬럼에 저장, 승인취소 시 삭제). SCNT에서는 이를 **작성자가 본문에서 미리 채우는 입력 항목**으로 분리했다.

| | 기존 (060) | SCNT (060_003) |
|---|---|---|
| 쓰는 시점 | 승인하면서 (결재자) | 미리, 본문에서 (작성자) |
| 검증 시점 | 각 결재 단계 | 승인요청 직전 1회 |
| 검증 범위 | 자기 것 1개 | 공사팀·안전팀 종합의견 둘 다 |
| 승인취소 시 | 내용 초기화 | 보존 |

옵션092가 켜져 있으면 두 종합의견 중 하나라도 비면 승인요청을 막는다(FE 1차 + BE `validateBeforeDemand` 2겹).

## 진행 상황

승인 팝업 신규 화면, DDL 4컬럼, 옵션 배선, 외곽 승인 컬럼(상태+단계+대기자+벌크 병합), 소급 유지, 그리고 요청/승인/반려/취소 시 `CFM_*`를 기록하는 **SanctionTargetHandler(OTAT)** 까지 구현했다. 남은 작업은 상태부여 seam, 수정/삭제/잠금 seam(EDIT_TF — 정합·보안 직결), 종합의견 승인요청 게이트, 옵션 admin + SQL 일괄수정(최대 리스크), USETGT 등록·승인라인 정의다.
