## 1. 한 줄 요약

수시위험성평가의 **자체 승인 로직**(`STTS_CD` 30/40/50/60 + 공사팀장/안전팀장/현장소장 고정 3단계)을
**SCNT 표준 승인관리**로 대체하고, 다른 모듈도 붙일 수 있는 **재사용 표준**을 함께 세웁니다.

기존 방식의 근본 문제는 **승인선이 3단계로 하드코딩**돼 있다는 점입니다.
회사마다 결재 라인이 다른데 컬럼(`APPRV_C/BD/A_USER_NO`)이 3개로 고정돼 있어 확장이 안 됩니다.
SCNT는 승인라인을 데이터로 관리하므로 이 제약이 사라집니다.

---

## 2. 핵심 설계 — 옵션으로 두 엔진을 가른다

### 2.1 상호배타 구조

| 상태 | `SFAS_OPT_060` | `SFAS_OPT_060_003` |
|---|---|---|
| 기존 결재 사용 | `T` | `F` |
| **SCNT 표준승인 사용** | **`F`** | `T` |
| 승인 미사용 | `F` | `F` |

- `060` = **기존 결재 엔진** on/off (의미 그대로 유지)
- `060_003` = **NEW 승인(SCNT)** 사용여부 (신규)
- **둘 다 `T`는 불가** — admin UI에서 양방향 잠금으로 원천 차단

### 2.2 ⚠️ 이 설계의 대가 (가장 주의할 점)

SCNT 현장은 **`060 = F`로 저장**됩니다.
그래서 `060='T'`를 **"승인 활성"** 으로 읽는 기존 SQL이 SCNT 현장을 **"승인 없음"으로 오판**합니다.

```sql
-- 약 15~20 파일 / 40여 조건절을 일괄 수정해야 함
SFAS_OPT_060 = 'T'  →  (SFAS_OPT_060 = 'T' Or SFAS_OPT_060_003 = 'T')
SFAS_OPT_060 = 'F'  →  (SFAS_OPT_060 = 'F' And SFAS_OPT_060_003 = 'F')
```

빠뜨리면 **미승인 건이 목록에 노출되거나 상태 라벨이 공백**이 됩니다.
→ 상세 목록: [SfasRcpt_옵션060_영향목록.md](../TO-BE/SfasRcpt_옵션060_영향목록.md)

## 2.5 옵션을 바꾸면 기존 회차는 어떻게 되나 (소급 유지) ✅ 적용 완료

> 실무에서 가장 많이 물어보실 부분이라 따로 정리했습니다.

### 결론부터 — **기존 회차는 건드리지 않습니다**

기존 결재(060)를 쓰다가 SCNT(060_003)로 바꿔도, **이미 만들어진 회차는 원래 방식 그대로** 굴러갑니다.
옵션 변경 시점 **이후에 새로 만든 회차부터** SCNT로 진행됩니다.

| | 옵션 변경 전에 만든 회차 | 변경 후에 만든 회차 |
|---|---|---|
| 결재 방식 | **기존 결재 그대로** | SCNT 표준승인 |
| 상태 표시 | `공사팀장승인대기` 등 기존 문구 | `승인대기` 등 SCNT 문구 |
| 승인 버튼 | **그대로 뜸** (계속 승인/취소 가능) | 승인 팝업에서 처리 |

즉 **한 화면에 두 방식이 섞여** 보입니다. 회차마다 자기가 시작한 방식으로 끝까지 갑니다.

### 왜 이렇게 했나

옵션을 바꾸는 순간 **전부 SCNT로 갈아엎는 방식**도 있었는데, 그러면 이런 일이 생깁니다.

> 안전팀장 승인을 기다리던 회차가 있는데 옵션을 바꿈
> → 기존 승인 버튼이 사라지고, SCNT 기준으로는 아직 요청도 안 된 상태
> → **승인도 취소도 못 하는 상태로 멈춤**

승인 이력은 감사 성격이라 나중에 "이 회차가 어떻게 승인됐는지"가 바뀌면 곤란하기도 합니다.
그래서 **진행 중이던 건은 절대 끊기지 않게** 하는 쪽을 택했습니다. 옵션을 되돌려도 마찬가지입니다.

### 🔒 소급 유지는 **승인 모듈 현장에만** 적용한다 (2026-08-10 범위 축소)

소급 유지의 목적은 **"060='T' → 'F' 로 전환하면서 진행 중이던 회차가 안 보이게 되는 것"을 막는 것**이다.
그런데 판정을 `상태 30~60 이면 레거시 궤도` 로만 두면, **승인을 아예 안 쓰는 현장**(`060`·`060_003` 둘 다 `F`)에서도
과거에 060 을 잠깐 켰다 끈 회차 때문에 승인자 3컬럼이 갑자기 나타난다. → 예전에 없던 화면이라 혼란.

그래서 `fnIsLegacyApprvRow` 를 이렇게 좁혔다.

```js
scwin.fnIsLegacyApprvRow = function(anRowIdx) {
    if(scwin.fnIsScntRow(anRowIdx)) return false;

    // (1) 레거시 승인을 켜둔 현장 → 예전 방식 그대로 (회차 상태 무관)
    if(scwin.oOptConfig.bUseOpt060 === true) return true;

    // (2) 소급 유지는 '승인 모듈로 전환한 현장'에만
    if(scwin.oOptConfig.bUseOpt060003 === true) {
        return ["30", "40", "50", "60"].includes(wdlAsmt.getCellData(anRowIdx, "STS_CODE"));
    }

    return false;   // 승인 미사용 현장 → 예전처럼 안 보임
};
```

컬럼 표시(`bHasLegacyApprv`)도 이 함수를 쓴다 — **판정 규칙을 한 곳에만 두어** 표시와 편집정책이 어긋나지 않게 했다.

| 회차 구성 | 미사용 (F/F) | 레거시 (060=T) | 승인모듈 (060_003=T) |
|---|---|---|---|
| 접수만 | 숨김 | **보임** | 숨김 |
| 접수 + 레거시30 | **숨김** | **보임** | **보임** (소급) |
| 승인모듈만 | 숨김 | 숨김 | 숨김 |
| 레거시30 + 승인모듈 | 숨김 | **보임** | **보임** (혼용) |

### 화면에서 보이는 상태값

승인이 붙으면서 상태 컬럼에 아래 값들이 나타납니다. **하나의 "상태" 컬럼**에서 회차에 따라 달라집니다.

**SCNT로 진행되는 회차**

| 상태 | 언제 |
|---|---|
| 요청대기 | 승인요청 전 (승인라인 유무와 무관) |
| 승인대기 | 승인요청함 |
| 승인중 | 결재가 중간 단계까지 진행됨 |
| 승인반려 | 반려됨 |
| 승인완료 | 최종 승인됨 |

**기존 결재로 진행되던 회차**는 예전 문구(`공사팀장승인대기`·`안전팀장승인대기`·`현장소장승인대기`·`평가서승인완료`)를 그대로 유지합니다.

상태 컬럼 옆에 **단계 / 대기자** 두 컬럼이 추가되어, 지금 몇 단계이고 누구 차례인지가 목록에서 바로 보입니다.
(기존 결재 회차는 이 두 칸이 비어 있습니다)

#### C 와 D 를 가르는 이유 (2026-08-21 추가)

> ⚠️ **이 절의 정책은 대체 예정이다.** 2026-08-23 공유 결정으로 접수상태 회차는 소급유지 대신
> **승인단계를 생성해 승인 궤도로 편입**한다(협력 제출본 → `승인대기` / 원청 작성본 → `요청대기`).
> 명세: [TO-BE/승인상태_전환명세.md](../TO-BE/승인상태_전환명세.md) §3-3.
> 아래 판별 방법(§4-3 백필 근거)은 그대로 쓰이므로 남겨 둔다.

둘 다 `STTS_CD` 10/20 에 승인라인이 없는, 겉보기엔 같은 회차다. 그런데 **어떻게 만들어졌는지가 다르다.**

- **C — 원청이 접수화면에서 직접 만든 회차.** 이후 아무 프로세스도 진행된 적이 없다. 승인요청을 열어줘도 잃을 이력이 없다.
- **D — 협력사가 제출해서 원청 목록에 올라온 회차.** 승인요청 프로세스를 거쳐 올라온 게 아니다. 여기에 승인요청을 열면 *적법하게 제출되지 않은 건*이 승인 파이프라인에 들어간다.

그래서 **C 만 `요청대기` 로 열고, D 는 접수/미접수 그대로 둔다.**

##### 판별 방법 — 전용 컬럼이 없다

두 생성 경로가 테이블에 **같은 모양**을 남긴다. 판별에 쓸 수 있는 컬럼이 없다는 뜻이다.

| | 협력 제출 (`trscSub`) | 원청 직접작성 (`insertAsmt`) |
|---|---|---|
| `TSF_ASSMNT_RECEIVE` | Merge | Insert |
| `TSF_ASSMNT_REGIS` | 협력이 미리 작성 | **같은 트랜잭션에서 함께 Insert** |
| `CHECK_TF` | 제출 시 `'T'` | `#{RCPT_TF}` — 접수하면 `'T'` |
| `CRTUSERNO` | 협력사 사용자 | 원청 사용자 |

`REGIS` 유무도 `CHECK_TF` 도 못 쓴다(실측: `REGIS` 있음이 365k 중 364k, `REGIS.CHECK_TF='T'` 도 364k).
남는 신호는 **최초생성자 소속**뿐이라 이걸로 판별한다.

```sql
(Select Max('T') From TCC_EMPLOYE x Where 1 = 1 And x.USER_NO = a.CRTUSERNO And x.COMPANY_ID = a.R_COMPANY_ID) COOP_CRT_TF,
(Select Max('T') From TCC_EMPLOYE x Where 1 = 1 And x.USER_NO = a.CRTUSERNO And x.COMPANY_ID = a.COMPANY_ID) RCPT_CRT_TF
```

> Oracle 은 `Select` 절에서 `Exists` 를 못 쓴다. 스칼라 서브쿼리 형태여야 한다.

**교차검증** — 원청 경로는 RECEIVE·REGIS 를 한 트랜잭션에서 만들어 `CRTDATE` 가 같고, 협력 경로는 작성과 제출 시점이 벌어진다. 이 독립 신호가 위 판별과 일치한다.

| `CRTDATE` 관계 | 협력 | 원청 | 판별불가 |
|---|---|---|---|
| RECEIVE 가 나중 (제출 패턴) | **313,589** | 468 | 3,293 |
| 동시생성 5초 이내 (한 트랜잭션) | 22,700 | **24,452** | 469 |

원청의 98%가 동시생성, 협력의 93%가 시점 차이 — 서로 다른 두 신호가 같은 방향을 가리킨다.

**판별불가 처리**: 생성자가 `Null`(2,761건)이거나 사용자 정보가 없는 건(639+368건)은 **D(협력)로 떨어져 소급유지**된다.
잘못 열어서 부적합한 회차가 승인 파이프라인에 들어가는 것보다 안전한 쪽이다.

##### 화면도 같은 규칙을 써야 한다

`fnIsScntRow` 가 승인 팝업 링크·편집잠금·컬럼표시를 지배하므로, SQL 의 상태명과 규칙이 어긋나면 **"접수인데 승인 팝업이 열리는"** 상태가 된다.

```js
// 그 외(요청 전·접수 등, 결재 실적 0건)는 승인 모듈 현장이면서 원청이 직접 만든 회차만 승인 모듈.
return scwin.oOptConfig.bUseOpt060003 === true && wdlAsmt.getCellData(anRowIdx, "RCPT_DRCT_TF") === "T";
```

##### 추후 데이터는 컬럼으로 해결한다 (미착수)

`CRTUSERNO` 는 원래 이 용도의 컬럼이 아니다. `TSF_ASSMNT_RECIVE_CONST_CMT.REG_COMPANY_ID`(작성자 회사ID) 선례가 같은 스키마에 있으므로, `TSF_ASSMNT_RECEIVE` 에도 같은 컬럼을 두면 신규 데이터는 조회 없이 확정된다.

| 경로 | 넣을 값 |
|---|---|
| `insertAsmt` (원청) | `#{COMPANY_ID}` |
| `trscSub` (협력) | `#{COOP_COMPANY_ID}` |
| 소급분 백필 | `CRTUSERNO` 소속 기준 1회 `Update` (위 판별식과 동일 규칙) |

### ⚠️ 전환 시 안내 필요 — 옵션을 켜는 순간 기존 건의 **상태명이 정정된다**

**배포만으로는 아무 변화가 없습니다. `SFAS_OPT_060_003 = 'T'` 로 켜는 순간 그 현장에서만 일어납니다.**

상태명(`STS_NAME`) 산출 조건이 승인 모듈 도입으로 이렇게 바뀌었습니다.

| | 조건 |
|---|---|
| main(운영) | `d.SFAS_OPT_060 = 'T' And a.STTS_CD = '40'` → `안전팀장승인대기` |
| 20260922 | `(d.SFAS_OPT_060 = 'T' **Or d.SFAS_OPT_060_003 = 'T'**) And a.STTS_CD = '40'` |

그래서 **`060 = 'F'` 인데 상태 30~60 인 건**(= 과거 060을 켜고 승인을 진행하다 끈 회차)은
- `060_003 = 'F'` 일 때 → 승인 분기를 다 통과해 **"접수"** 로 보임 (= main 과 동일)
- `060_003 = 'T'` 로 켜는 순간 → **"공사팀장승인대기" / "안전팀장승인대기"** 로 표시됨

**실측 예 (2026-08-10, PMIS4)** — `30212 / GC001 / 202606`, 현장 옵션 `060='F'` · `060_003='T'`

| REG_SN | STTS_CD | main 표시 | 현재 표시 | 승인버튼 |
|---|---|---|---|---|
| 8841 | 40 | 접수 | 안전팀장승인대기 | 노출 (안전팀장 84275 — 공사팀장은 이미 승인 완료) |
| 8842 | 30 | 접수 | 공사팀장승인대기 | 노출 (공사팀장 66791) |

#### 판단

**정정이 맞다.** 상태 30~60 은 실제로 결재가 진행 중인 데이터이고, main 에서 "접수"로 보이던 것이 오히려 실상을 감추고 있었다.
승인 모듈을 켜면 그 건들은 **레거시 결재로 마저 처리**해야 하므로, 상태명이 정확해지고 승인버튼이 뜨는 게 일관된다.
승인자 3컬럼 소급 유지(2.5장)도 이 상태명 표시와 짝이다 — "공사팀장승인대기"인데 공사팀장이 누군지 안 보이면 안 되기 때문.

#### 전환 계획에 반영할 것

- [ ] 옵션을 켜기 전, 그 현장에 **`060='F'` + 상태 30~60 + `CFM_DEM_SN` 없음** 인 건이 몇 개인지 확인하고 담당자에게 미리 안내
  ```sql
  Select a.PROJ_CODE, a.STAN_MONTH, a.REGIS_SEQ, a.STTS_CD
  From TSF_ASSMNT_RECEIVE a, TCC_PROJ_CODE d
  Where 1 = 1
  And a.COMPANY_ID = d.COMPANY_ID
  And a.PROJ_CODE = d.PROJ_CODE
  And a.CFM_DEM_SN Is Null
  And a.STTS_CD In ('30', '40', '50')
  And Nvl(d.SFAS_OPT_060, 'F') = 'F'
  And d.COMPANY_ID = :회사 And d.PROJ_CODE = :현장
  ```
- [ ] 그 건들은 **승인 모듈로 옮길 수 없다** — `fnIsScntRow` 가 상태 30~60 이면 무조건 `false` 를 반환하고, 승인 팝업은 SCNT 회차에서만 열린다. **레거시로 끝까지 진행**하는 것이 현 설계다. 업무상 이게 맞는지 전환 전에 확정할 것
- [ ] 2026-08-10 기준 해당 건: `A0001` 19건 · `GC001` 11건 (둘 다 회사 30212 개발). **운영에는 `060_003='T'` 현장이 없다** (`origin/main`·`origin/dev` 에 `SFAS_OPT_060_003` 자체가 없음)

> 운영 DB 반영은 배포 전 별도 확인 필요.

**기존 `STTS_CD`는 그대로 둡니다.** 컷오버가 현장별이라 한 현장에 구/신 데이터가 공존하므로,
한 컬럼에 Case로 합치면 둘을 구분할 방법이 없습니다. (실제로 `STTS_CD`에 값 있는 건 1,491건 존재)

### 3.2 `CFM_STS_CODE` — SCNT 코드를 그대로 복사

숫자 코드로 번역하지 않고 **`TBASE_SANCTN_DEM.STS_CODE` 값을 그대로** 씁니다.

| 코드 | 표시명(공통코드 `SANCTN_STS_CODE`) |
|---|---|
| `REG` | 작성중 → **화면에는 `요청대기` 로 표시**(§2.5 통일 규칙, 공통코드 자체는 그대로) |
| `DEM` | 승인대기 |
| `PROG` | 승인중 |
| `REJ` | 승인반려 |
| `CMPL` | 승인완료 |

**이유**: Handler가 번역 없이 복사만 하면 되어 틀릴 여지가 없고,
표시명은 `SF_GetCommonCodeName()`이 처리하므로 문구가 바뀌어도 SQL을 안 고칩니다.

### 3.3 저장 vs 조회 구분

| 데이터 | 방식 |
|---|---|
| 상태(`CFM_STS_CODE`) + DEM 링크 3키 | **호스트에 저장** (Handler가 write) |
| 승인단계명 · 대기자 | **저장 안 함** — 조회 시 SCNT에서 주입 |

단계·대기자를 저장하면 SCNT와 **이중 소유**가 되어 정합이 깨집니다. CESC·DCMT도 동일 원칙입니다.

## 4. 화면 구성

### 4.1 외곽 목록 `SfasRegAtRiskasmtRcpt`

`060_003 = T`면 승인 관련 컬럼을 **세트 단위로 교대**합니다.

                        ↓  060_003 = T
[SCNT]       상태 | 단계 | 대기자

|---|---|
| `STATUS` (레거시 상태) | `!060_003` |
| `CFM_STS_NAME` (상태) | `060_003` |
| `SANCTN_STEP_NAME` (단계) | `060_003` |

(CESC는 행마다 호출하는 N+1 구조 — 그대로 따르지 않았습니다)

### 4.2 승인 팝업 `SfasPopRegRiskAssessmentConfirm` (신규)

목록에서 **상태 컬럼 클릭** 시 열립니다. 조회 전용이며, 승인 액션은 승인패널 wframe이 담당합니다.

## 5. 종합검토의견 — 승인과 분리

기존에는 종합의견이 **승인 액션의 산출물**이었습니다.
승인 버튼 → 의견 팝업 → 입력한 텍스트 1개가 **누가/어느 단계냐에 따라 갈려서** 저장:

```
STTS_CD=30 & 공사팀장 → SYNTH_CONSTR_OP
STTS_CD=40 & 안전팀장 → SYNTH_SAF_OP
STTS_CD=50 & 현장소장 → APPRV_CMT
```

승인취소하면 **내용이 지워지기까지** 했습니다.

### SCNT에서는

종합의견은 *"항목별 검토의견을 일일이 쓰기 힘드니 평가서 단위로 하나만 쓰고 퉁친다"* 는 용도이므로,
**승인과 완전히 분리**해 작성자가 **미리 채워두는 입력 항목**으로 둡니다.

| | 기존 (060) | **SCNT (060_003)** |
|---|---|---|
| 쓰는 시점 | 승인하면서 (결재자) | **미리, 본문에서** (작성자) |
| 검증 시점 | 각 결재 단계 | **승인요청 직전 1회** |
| 검증 범위 | 자기 것 1개 | **공사팀·안전팀 종합의견 둘 다** |
| 승인취소 시 | 내용 초기화 | **보존** |

```
옵션092(종합검토의견 사용) = T  AND  옵션060_002(작성검증) = T  이면
  → SYNTH_CONSTR_OP · SYNTH_SAF_OP 둘 중 하나라도 비면 승인요청 차단 (레거시 동형)
```
✅ **FE 게이트 구현 완료** — 팝업 `fnValidateSynthOp`가 request 분기에서 검증. 차단 문구 **"승인의견을 입력하세요."**(레거시 `SfasPopRegConfirmOpinion`과 동일). 
※ 규칙은 092만이 아니라 **092 && 060_002**(레거시 실제 동작 확인). BE 2겹은 미적용 — 코어 `validateBeforeDemand`가 **저장(createDemand) 시점**이라 "승인요청 전" 규칙과 타이밍이 어긋나고, FE 게이트로 충분하다고 판단(A안).

  - **검증 위치**: SCNT 팝업 FE 게이트(`fnValidateSynthOp` 옆에 항목별 검증 추가). 팝업이 이미 `wdlConstrRvw`(공사·CHK1)·`wdlSafRvw`(안전·CHK2) 로드.
  - **`060_001` granularity 존중** (BE `trscCmtCont` 확인): **'A'=검증 안 함 / 'B'=전 항목 필수 / 'C'=중점 항목(`PRIORITY='O'`)만 필수**(비중점 면제). SCNT 게이트도 이 값 그대로 반영 — 조건 `(060_001 != 'C' Or PRIORITY = 'O')`.
  - **변형2 미채택**: "승인완료 직전 차단"은 레거시(검토하며 작성)에 더 가깝지만, "최종 단계 판별 + 완료시점 차단" 배선이 복잡하고 종합의견과 타이밍이 갈려 UX 불일치. SCNT 승인자가 회사·현장마다 달라 실무 일반화 불가 → 단순·명확한 변형1로 통일.
