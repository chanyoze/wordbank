## 4. 불일치 — 전부 해소됨 (2026-08-31)

### 4-1. `CONSTR_LDR_USER_NAME` — 팝업에만 보였다 → **해소**

| | 조건 |
|---|---|
| 외곽 | `!bUseOpt060 && !bUseOpt060003` — 승인 엔진을 쓰는 현장이면 숨김 |
| 팝업 (이전) | 제어 없음 — 항상 표시 |
| 팝업 (현재) | **항상 숨김** |

**실측** — `30212 / GC001 / 9117` 은 `C_USER_NO = 66791`(이찬호p) 이 채워져 있는데, `GC001` 이 `060_003='T'` 라 외곽에서는 숨겨지고 팝업에서만 보였다.

`CONSTR_LDR_USER_NAME` 은 **레거시 결재선을 지정하는 담당자**다. 승인 팝업은 승인 궤도 회차만 다루므로 이 컬럼이 할 일이 없다.

### 4-2. `RCPT_CANC_OP` — 값이 생길 수 있게 됐다 → **팝업에서 제외**

| | 조건 |
|---|---|
| 외곽 | `bUseOpt060 || bHasLegacy` — **그대로 둔다** |
| 팝업 (이전) | 그 행에 값이 있으면 표시 |
| 팝업 (현재) | **항상 숨김** |

예전에는 승인 모듈 현장에서 접수취소 버튼이 아예 없어 값이 생길 일이 없었다. 2026-08-28 에 접수·접수취소 버튼을 회차 단위로 되살렸으므로 **승인 모듈 현장에서도 접수취소사유가 쌓인다.**

그래도 팝업에는 넣지 않는다 — **접수취소는 접수 흐름에 속한 행위**이고, 팝업에 들어온 회차는 이미 그 흐름을 떠났다.
외곽 조건은 건드리지 않는다. 외곽에는 두 궤도가 섞여 있고 `bHasLegacy` 가 무라인 회차에서 참이라 필요한 자리에서 보인다.

### 4-3. `PROJ_HDCF_CFM_OP` — 외곽에서 부활, 팝업에는 **안 되살린다**

2026-08-25 에 *"060_003 에서는 등록 경로가 없다"* 는 이유로 팝업에서 제거했다. 2026-08-28 에 `fnIsScntRow` 를 고치면서 무라인 회차가 레거시 취급이 되어 외곽에서는 다시 보인다(명세 §9-8).

4-1·4-2 와 같은 이유로 팝업에는 두지 않는다. 현장소장의견은 레거시 결재 흐름의 산물이다.

## 5. 확정된 원칙 (2026-08-31)

> **승인 팝업은 승인 궤도 회차만 다룬다. 접수·레거시결재 흐름 전용 컬럼은 팝업에 두지 않는다.**
> 외곽 목록은 두 궤도가 섞여 있으므로 궤도별 조건을 그대로 유지한다.

§4 의 세 컬럼과 아래 두 물음이 이 한 문장으로 정리된다.

| # | 물음 | 결론 |
|---|---|:--|
| **①** | `RCPT_CANC_OP` · `CONSTR_LDR_USER_NAME` 을 팝업에서 어떻게 할까 | **소스에서 삭제** — 접수·레거시 흐름 전용 (2026-09-02, `setColumnVisible(false)` → 완전 삭제) |
| **②** | `PROJ_HDCF_CFM_OP` 를 팝업에 되살릴까 | **안 되살린다** — 같은 이유 |
| **③** | 팝업에 승인 단계·대기자(`SANCTN_STEP_*`) 를 넣을까 | **불필요** — 승인이력 탭이 같은 정보를 더 자세히 준다 |
| **④** | 팝업에 레거시 승인자 3컬럼을 넣을까 | **불필요** — 레거시 결재 회차는 팝업에 들어오지 않는다 |

> 반대 방향(외곽에 없는데 팝업에만 있는 컬럼)은 **불일치로 본다** — 4-1 이 그 사례였다.
> 팝업에 새 컬럼을 넣기 전에 *"이 값이 승인 궤도에서 의미가 있나"* 를 먼저 묻는다.

### 5-1. 숨김이 아니라 삭제로 간 이유 <sub>(2026-09-02)</sub>

①의 두 컬럼은 **외곽에선 조건부로 보이지만 팝업에선 어떤 옵션·궤도에서도 보일 일이 없다**고 판정된 것들이다.
그런 컬럼을 `setColumnVisible(false)` 로 남겨 두면 두 가지가 남는다.

- 조회할 때마다 **쓰지 않을 값을 만든다** — `SFCC_GET_USER_NM(...)` 함수 호출이 매번 돈다
- 나중에 누가 옵션 분기를 붙이다 **되살릴 여지**가 남는다. `RCPT_CANC_OP` 는 접수완료 회차 전환이 열리면서 값이 실제로 채워질 수 있게 됐다(§4-2)

**4계층(SQL Select · dataList · 그리드 헤더 · 그리드 body)을 전부 지운다.** `PROJ_HDCF_CFM_OP`(2026-08-25) 와 같은 방식이다.

| 컬럼 | 지운 곳 |
|---|---|
| `CONSTR_LDR_USER_NAME` | `…RcptConfirmSql:155` · `…RcptConfirm.xml` 의 dataList·`GH_*`·body·`setColumnVisible` |
| `RCPT_CANC_OP` | `…RcptConfirmSql:149` · 〃 |

> 삭제 후 그리드 헤더/바디 컬럼 수가 **14 / 14** 로 일치하는지 확인한다. 한쪽만 지우면 컬럼이 밀린다.

## 6. 유지 방법

- 조건식을 고칠 때 **양쪽 화면을 같이** 확인한다. 한쪽만 고치면 4-1 같은 불일치가 생긴다.
- 컬럼을 새로 넣을 때 이 문서의 **§1-1 · §2-1(항시)** 에 들어가는지 먼저 정한다. 항시 컬럼은 나중에 옵션으로 감추기가 비싸다.
- 대조는 스크립트로 재생성할 수 있다 — 그리드 body 의 `<w2:column id>` 와 `setColumnVisible` 호출을 뽑아 맞대면 된다.
  ⚠️ 속성이 여러 줄로 쪼개진 컬럼은 단순 정규식이 놓친다(`CCTV_MNTR_NAME` 이 그랬다). 결과가 비면 눈으로 한 번 더 본다.
