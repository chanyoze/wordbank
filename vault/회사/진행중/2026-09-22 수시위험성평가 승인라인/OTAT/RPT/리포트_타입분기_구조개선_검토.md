# 리포트 타입 분기 구조 개선 검토 (상시·수시위험성평가서)

> 작성 2026-08-10 / 대상 `RRPT_ID=31` A·B·C·D 4종
> 결론: **파일을 늘리는 방식이 한계에 온 게 아니라, 이미 무너져서 잘못된 서식이 나가고 있다.**
> ⚠️ 이 문서는 검토안이며 코드·`.crf` 는 아직 손대지 않았다.

## 1. 현재 구조

리포트 타입은 **SQL에서 옵션 3개 조합으로 결정**된다 — [SfasRegAtRiskasmtRcptSql.xml:63-72](../../../src/main/resources/sqlmap/mappers/sfas/SfasRegAtRiskasmtRcptSql.xml#L63-L72)

```sql
(Case
    When SFAS_OPT_066_001 = 'T' And SFAS_OPT_066_002 = 'F' And SFAS_OPT_048_001 = 'F' Then 'B'
    When SFAS_OPT_066_002 = 'T' And SFAS_OPT_048_001 = 'F' Then 'C'
    When SFAS_OPT_048_001 = 'T' Then 'D'
    Else 'A'
 End) RPT_TYPE_CODE
```

이 값이 `DVS_CD` 가 되어 `TCC_RRPT_FILE_BAS` 에서 `.crf` 를 고른다.

**세 옵션은 전부 "컬럼 하나를 보이느냐" 다.**

| 옵션 | 의미 |
|---|---|
| `SFAS_OPT_066_001` | 이전등급 사용여부 |
| `SFAS_OPT_066_002` | 개선(감소)후등급 사용여부 |
| `SFAS_OPT_048_001` | 라인추가 작성주체 컬럼 사용여부 |

즉 **컬럼 3개의 on/off 를 파일 4개로 표현**하고 있다. 옵션이 하나 늘면 조합은 8 → 16.

## 2. 🔴 이미 깨져 있다 — 조합이 우선순위 체인에 먹힌다

> ⚠️ **2026-09-02 주석 — 이 장의 판정표는 "기본본" 기준이다.**
> 이후 `docs/OTAT/RPT/` 의 사본이 **개발회사 전용본(`_LGHTEST`)** 으로 교체되었고(README §1-1), 그 파일들로 같은 스캔을 돌리면 결과가 다르다 —
> 개발본 D 에는 `PREV_ASSMNT_RANK`·`AFTER_ASSMNT_RANK` 가 **둘 다 있다.**
> **"157현장 버그가 조치됐다"고 읽지 말 것.** 기본본을 받아 재대조해야 확정된다 → [HANDOFF_금번수정_리포트반영.md §6-2](./HANDOFF_금번수정_리포트반영.md)

`.crf` 바이너리에서 필드명을 추출해 대조한 결과:

| 리포트 필드 | A | B | C | D |
|---|---|---|---|---|
| `PREV_ASSMNT_RANK` (이전등급 ← 066_001) | · | **O** | **O** | · |
| `AFTER_ASSMNT_RANK` (감소후등급 ← 066_002) | · | · | **O** | · |

**D 에는 두 컬럼이 없다.** 그런데 Case 는 `048_001='T'` 를 최우선으로 잡으므로, 066 옵션을 켠 현장도 048_001 이 켜져 있으면 D 로 접힌다.

운영 데이터 (2026-08-10 기준):

| 조합 (066_1/066_2/048_1) | 배정 타입 | 현장 | 평가서 | 최근등록 | 잃는 컬럼 |
|---|---|---|---|---|---|
| `T` `F` `T` | D | 151 | 455 | 2026-08-05 | 이전등급 |
| `T` `T` `T` | D | 6 | 419 | 2026-08-07 | 이전등급 + 감소후등급 |
| `F` `T` `T` | D | 4 | 141 | 2026-08-05 | 감소후등급 |
| `F` `F` `T` | D | 6 | 288 | 2026-08-03 | (정상) |
| `T` `T` `F` | C | 4 | 128 | 2026-06-29 | (정상) |
| `F` `T` `F` | C | 3 | 40 | 2026-07-20 | (정상) |
| `T` `F` `F` | B | 3 | 55 | 2026-06-11 | (정상) |
| `F` `F` `F` | A | 6,128 | — | — | (정상) |

- **이전등급을 옵션으로 켜놓고도 리포트에 안 나오는 현장 157곳 / 평가서 874건** (최근 2026-08-07, 현재 진행형)
- 그중 **감소후등급까지 같이 잃는 현장 10곳 / 560건**

> 다만 "D 를 쓰는 2개 회사는 원래 그 컬럼을 원치 않았다"는 업무 결정이었을 가능성은 배제 못 한다.
> 만약 그렇다면 **그 회사들이 066 옵션을 켜둔 것 자체가 잘못**이므로, 어느 쪽이든 정리 대상이다. 담당자 확인 필요.

## 3. 진단 — 무엇이 잘못된 설계인가

파일이 늘어나는 게 문제가 아니라, **분기가 잘못된 계층에 있다.**

- `SFAS_OPT_040_001` · `048` · `049` 는 **4개 `.crf` 전부의 MAIN 데이터셋 필드**로 들어가 있다 → 리포트 **내부 조건**으로 처리 중.
- `066_001` · `066_002` · `048_001` 만 **파일 선택**으로 승격돼 있다.

같은 성격(컬럼 표시 여부)인데 처리 계층이 다르다. 후자가 조합 폭발과 위 버그의 원인이다.
**리포트 내부 조건 분기는 이 시스템에서 이미 검증된 패턴**이다 — 새로 도입할 기법이 아니다.

## 4. 권고

### 4-1. [즉시] 버그로 먼저 처리
구조 개선과 분리해서, 157 현장이 켜둔 옵션대로 출력되게 만든다. 임시 조치라면 Case 우선순위 재정의보다 **D 계열에 두 컬럼을 조건부로 추가**하는 쪽이 맞다(우선순위를 바꾸면 048_001 을 잃는다).

### 4-2. [근본] `DVS_CD` 의 역할을 다시 정의한다

> **`DVS_CD` 는 "지면 구성이 근본적으로 다른 서식 계열"에만 쓴다.
> 옵션에 따른 컬럼 표시/숨김은 반드시 리포트 내부 조건으로 처리한다.**

이 기준을 지금 4종에 적용하면 **셋 다 "컬럼 유무"라서 나눌 이유가 없다** → 원리적으로 **1개 파일**로 수렴 가능.

- 방법: `066_001` · `066_002` · `048_001` 을 리포트 파라미터/MAIN 필드로 내려보내고, 해당 컬럼의 표시조건으로 건다. `040_001`·`048`·`049` 가 이미 그렇게 되어 있으니 같은 방식.
- 효과: 옵션 추가 시 **파일이 아니라 조건 하나**만 늘어난다 → 선형.
- 비용: 컬럼 폭 가변 처리(숨김 시 잔여 폭 재배분)가 리포트 디자인에서 제일 손이 많이 간다. 이게 실질 작업량의 대부분.

### 4-3. 단계적으로 간다면

1단계 — **B·C 를 A 에 흡수** (셋 다 같은 list 계열, 차이는 등급 컬럼 2개뿐). 4종 → 2종.
2단계 — **D 를 A 에 흡수** (라인추가 작성주체 컬럼 1개 + D 고유의 재해형태 pivot 여부 확인 필요). 2종 → 1종.

> D 는 A 와 토큰을 많이 공유한다(`DR_CD_1..7`·`DR_NM_IMG1..7`·`TITLE1_x` 등 재해형태 pivot 구조). B·C 는 `ASSMNT_*`·`ATDT_SEQ` 중심의 다른 구성.
> **즉 실제 계열은 A/D(pivot) vs B/C(list) 로 갈린다.** 1단계(B·C→A)가 오히려 계열을 건너는 작업이므로, 순서를 뒤집어 **D→A 부터** 하는 편이 쉬울 수 있다. 실물 열어보고 판단할 것.

> ⚠️ **2026-09-02 주석 — 위 계열 판정의 전제가 틀렸다.**
> `DR_CD_1..7`·`DR_NM_IMG1..7`·`TITLE1_x` 는 재해형태 pivot 이 아니라 **서명란 7슬롯**이다(`TSFAS_PROJ_REPORT_DTL.TITLE1`·`TITLE2`·`DR_CD`, `DR_CNT`=서명란수 — [README §5-1](./README.md)). 재해형태는 `DISASTER_FORM`·`DR_FORM`·`DR_SN` 을 쓴다.
> 현재 폴더 사본 기준 실제 갈림은 **항목상세 list(A·D) vs 종합의견+서명란슬롯(B·C)** 로 보인다 — 위 판정과 반대다.
> **어느 쪽이 맞는지는 기본본을 받아 재대조해야 확정된다** → [HANDOFF_금번수정_리포트반영.md §5-3·§6-3](./HANDOFF_금번수정_리포트반영.md)

### 4-3-1. [추가 2026-09-02] 슬롯 + DB 메타 — 이 시스템에 이미 있는 세 번째 방식

내부 조건(4-2)은 옵션 증가에 **선형**이다. 그런데 **상수**로 만드는 방식이 이 리포트 안에 이미 있다 — **서명란**이다.

서명란은 슬롯 7개를 고정으로 두고 라벨·코드·개수를 DB 메타에서 받는다
(`TSFAS_PROJ_REPORT.REPORT_NM`·`DR_CNT` / `_DTL.TITLE1`·`TITLE2`·`DR_CD` → `.crf` 의 `TITLE1_1..7`·`TITLE2_1..7`·`DR_CD_1..7`). 그래서 현장마다 서명란이 달라도 **`.crf` 는 하나다.** 근거는 [README §5-1](./README.md).

같은 구조를 **항목상세 그리드**에 적용하면 옵션이 추가돼도 `.crf` 는 무변경이고 SQL 한 곳만 바뀐다.

| | 지금 | 슬롯 + 메타 |
|---|---|---|
| 옵션 추가 비용 | `.crf` N개 수정(또는 파일 증식) | **SQL 한 곳**, `.crf` 무변경 |
| 증가 특성 | 지수(파일 선택) / 선형(내부 조건) | **상수** |
| 초기 비용 | — | 항목상세 밴드 1회 재작성 |

- **선행 확인**: 서명란 슬롯이 **가변 폭·미사용 슬롯 접힘을 어떻게 처리하는지** 디자이너에서 확인. 같은 기법을 상세 그리드로 옮길 수 있는지가 관건이다.
- **제약**: 셀 병합·정렬·서식이 컬럼마다 다르면 슬롯화가 어렵다.

### 4-4. 검토했으나 권하지 않는 대안

| 대안 | 판단 |
|---|---|
| **서브리포트 부품화** (옵션별 조각 `.crf` + 마스터 조립) | 증가는 선형이 되지만 **파일 수가 오히려 늘고**, `.crf` 마다 DB 접속정보가 박혀 있어 환경 관리 부담이 배가된다. 지금은 "컬럼 3개 표시여부"라 과한 해법 |
| **HTML 템플릿 → PDF 이관** | 근본 해결(텍스트라 diff·리뷰·테스트 가능)이지만 서명·도장 이미지·페이지 제어를 전부 재구현해야 한다. 이 건의 해법으로는 규모가 안 맞음. 별도 로드맵 과제 |
| **Case 우선순위만 정교화** | `When` 을 늘려 조합을 더 촘촘히 매핑 — 파일이 또 늘거나, 또 다른 조합이 조용히 먹힌다. **지금 상태를 만든 방식 그 자체** |

## 5. 재발 방지

- **리뷰 체크포인트**: `RPT_TYPE_CODE` 의 `Case` 에 `When` 을 추가하려는 순간이 경고 신호다. "이 옵션이 지면 구성을 바꾸나, 컬럼만 켜고 끄나?" 를 묻고, 후자면 리포트 내부 조건으로 보낸다.
- **정기 대조**: 옵션 조합 × `.crf` 필드 매트릭스를 뽑아 "옵션은 켜져 있는데 리포트에 필드가 없는" 조합을 찾는다. 이번 157 현장이 그렇게 나왔다.
  `.crf` 는 바이너리지만 UTF-16LE 문자열을 뽑으면 필드명은 읽을 수 있다 (`scratchpad/crf2_*.txt` 생성 방식 참조).

## 6. 제약 (어느 안을 택하든)

- `.crf` 는 **바이너리** → `git diff` 불가. 변경이력은 [README.md](./README.md) 6장에 수기로.
- `.crf` 에 **DB 접속정보가 내장**되어 있다 → 파일을 늘리는 안일수록 환경 관리 비용이 커진다.
- `docs/` 는 `.gitignore` 대상이라 이 문서는 **로컬 전용**이다. 협의 자료로 쓰려면 별도 공유 필요.
