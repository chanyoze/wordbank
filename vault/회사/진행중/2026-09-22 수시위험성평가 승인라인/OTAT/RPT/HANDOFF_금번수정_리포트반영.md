# HANDOFF — 금번 수정 4건 리포트 반영 (접수 RRPT_ID 31 · A~D)

## 0. 결론 먼저

1. **금번 4건은 신규 타입 0개다.** E·F·G·H 를 만들지 않는다 — 넷 다 "컬럼/값만 바뀌고 지면 구성은 그대로"라 기존 결정규칙의 후자다(§2).
2. **서명란은 2안(기존 서명란 유지)으로 확정.** 서명란 7슬롯이 이미 DB 메타로 그려지므로(§3-2) **원리적으로는 슬롯 이름 공급원 교체**로 끝난다 — 🔴 **단, 그건 B·C 계열에서만 확인됐다.** 정작 옵션 060_003 을 켠 현장이 서는 A·D 에는 그 슬롯 필드가 안 보인다(§6-1).
3. **분기축은 옵션이 아니라 `CFM_DEM_SN` 유무다.** 옵션 060_003 을 켠 현장에도 레거시 궤도 회차가 공존한다(§3-1). 여기를 틀리면 서명란이 빈 채로 인쇄된다.
4. **착수 전 블로커 3건**이 있다(§6). 특히 §6-1 은 공수를 SQL 교체 ↔ 서식 개편으로 가른다.

## 1. 금번 수정 4건 — 성격 판정

| # | 수정 건 | 성격 | 지면 구성이 바뀌나 | 처리 계층 | 신규 타입 |

| 1 | 승인 모듈 반영 — 리포트 서명란 | 슬롯의 **이름·서명 공급원 교체** | ❌ 슬롯 수·위치 동일<br>⚠️ A·D 는 슬롯 자체가 확인 안 됨(§6-1) | 리포트 내부 조건 | **0** |
| 2 | 쿼리 변경 | 데이터셋 SQL | ❌ | 리포트 내부 SQL | **0** |

판정 기준은 이 폴더가 이미 세워둔 질문이다 — [구조개선 검토 §5](./리포트_타입분기_구조개선_검토.md):

> **"이 옵션이 지면 구성을 바꾸나, 컬럼만 켜고 끄나?"**
> 컬럼만 켜고 끈다 → 리포트 내부 표시조건. 파일도 타입도 늘리지 않는다.

## 2. 왜 타입을 늘리면 안 되는가 — 이번엔 산술로

`RPT_TYPE_CODE` 는 옵션 3개의 `Case` 로 결정된다 — [SfasRegAtRiskasmtRcptSql.xml:63-72](../../../src/main/resources/sqlmap/mappers/sfas/SfasRegAtRiskasmtRcptSql.xml#L63-L72). 2026-09-02 확인 결과 **이 `Case` 는 아직 옵션 3개 그대로다**(CCTV·승인모듈 미반영).

금번 건을 파일 선택으로 승격하면:

| 시점 | 분기 옵션 | 조합 | 접수 파일 | 제출·회의록까지 |
|---|---|---|---|---|
| 현재 | 066_001 · 066_002 · 048_001 | 8 | 4 | 12+ |
| +CCTV(120) | 4개 | 16 | 최대 8 | 24+ |
| +승인모듈(060_003) | 5개 | 32 | 최대 16 | 48+ |

그리고 **`Case` 는 먼저 걸리는 `When` 이 이긴다.** 새 `When` 은 기존 조합을 삼킨다 — 실제로 그 방식 때문에 **157 현장이 이전등급을, 10 현장이 감소후등급을 리포트에서 못 받는 상태**가 만들어졌다([구조개선 검토 §2](./리포트_타입분기_구조개선_검토.md)).

> 옵션을 하나 더 파일 선택으로 올릴 때마다 **파일이 2배, 조합 사각지대도 2배**가 된다. 금번 4건은 전부 직교(지면 구성 무관)이므로 승격할 이유가 없다.

## 3. 2안 명세 — 서명란 유지

### 3-1. 🔴 분기축은 옵션이 아니라 `CFM_DEM_SN`

이미지의 1안·2안 설명은 "옵션 60-3 사용 시"로 되어 있으나, **옵션은 현장 단위고 승인 궤도는 회차 단위다.**

[TO-BE/승인_현재동작.md §2](../TO-BE/승인_현재동작.md) 기준:

> **궤도 판정 축은 `CFM_DEM_SN` 유무 하나다.** 옵션은 현장 단위인데 궤도는 회차 단위라, 한 현장·한 기준월 안에 레거시 궤도 · 미승인 · 승인 모듈 회차가 공존할 수 있다.

즉 옵션 060_003 을 켠 현장에도 레거시 궤도 회차(S3a·S3b·S4)가 남는다. **옵션으로 분기하면 그 회차들의 서명란이 빈 채로 인쇄된다.**

**리포트 분기식**

| 회차 | 조건 | 서명란 채우는 곳 |
|---|---|---|
| 승인 궤도 | `TSF_ASSMNT_RECEIVE.CFM_DEM_SN Is Not Null` | 승인라인 단계(§3-3) |
| 레거시 | `CFM_DEM_SN Is Null` | 기존 서명란 정의(현행 유지) |

**이 분기는 앱이 이미 같은 식으로 하고 있다.** 레거시 승인자명 3종(`APPRV_CONSTR_/SAF_/HDCF_USER_NAME`)이 `CFM_DEM_SN Is Null` 일 때만 표시된다(승인_현재동작 §2). 2안은 **같은 조건의 반대편만 채우는 것**이라 기존 사용자 회귀 위험이 낮다.

**앱 코드 변경 없이 리포트가 자체 조달할 수 있다** — 승인요청 식별자가 호스트 테이블에 역기록되어 있다:
`TSF_ASSMNT_RECEIVE.CFM_COMPANY_ID` · `CFM_PROJ_CODE` · `CFM_DEM_SN` · `CFM_STS_CODE`
([SfasAtRiskasmtSanctionHandlerSql.xml `updateCfmReceive`](../../../src/main/resources/sqlmap/mappers/sfas/SfasAtRiskasmtSanctionHandlerSql.xml))

> 선례: `사고보고서.crf` 가 이미 `SANCTN_COMPANY_ID`·`SANCTN_PROJ_CODE`·`DEM_SN` 으로 `SUB_SANCTN` 데이터셋을 만든다. 이 폴더에 사본이 있다.

### 3-2. 서명란 슬롯 계약 — **이미 데이터 주도다**

`.crf` 의 서명란은 고정 헤더가 아니라 **DB 메타를 읽는 7슬롯**이다. 이게 2안을 작게 만드는 핵심이다.

| 계층 | 테이블 | 컬럼 |
|---|---|---|
| 시스템 기본 | `TSST_PROJ_RPT` / `TSST_PROJ_RPT_SIGN` | `SIGN_USE_TF` · `MIN_SIGN_CNT` · `MAX_SIGN_CNT` / `SIGN_SUB1`(역할) · `SIGN_SUB2`(직책) · `RO_CODE` · `SORT_NO` |
| **현장별(실사용)** | `TSFAS_PROJ_REPORT` / `_DTL` | `REPORT_NM` · `SIGN_TF` · `MIN_DR_CNT` · `MAX_DR_CNT` · `DR_CNT` / **`TITLE1`(역할) · `TITLE2`(직책) · `DR_CD`(직책코드) · `SORT_NO`** |
| 리포트 필드 | `.crf` MAIN | `REPORT_NM` · `DR_CNT` · `TITLE1_1..7` · `TITLE2_1..7` · `DR_CD_1..7` · `DR_NM_1..7` · `DR_NM_IMG1..7` |

`.crf` 필드명이 현장별 메타 컬럼과 1:1로 대응한다(`TITLE1`→`TITLE1_x`, `DR_CD`→`DR_CD_x`). 실측(회사 30212, `REPORT_GB=1`): `REPORT_NM='수시위험성평가표'`, `MIN_DR_CNT=1` · `MAX_DR_CNT=7` · `DR_CNT=6`, DTL 예 `TITLE1='작성자'` / `TITLE2='협력업체소장'` / `DR_CD='F'`.

> 화면 `시스템관리 > 리포트관리 > 현장리포트서명란등록`([SstRegSystemProjectReportSigning.xml](../../../src/main/webapp/wqxml/sst/SstRegSystemProjectReportSigning.xml) · 현장별은 `ccms/CcmsRegCpnProjCoustmReport.xml`)의 "최소/최대/입력 서명란수" 라벨이 곧 `MIN_DR_CNT`/`MAX_DR_CNT`/`DR_CNT` 다.

**⇒ 슬롯을 가진 서식이라면 2안은 `.crf` 의 밴드를 건드리지 않는다. `TITLE1_x`/`TITLE2_x`/`DR_NM_IMGx` 를 채우는 SQL만 바꾸면 된다.**

🔴 **그러나 이 슬롯 필드는 폴더 사본 중 B·C 에서만 보인다.** A·D 에는 `TITLE1_x`·`DR_CD_x`·`REPORT_NM` 이 없고 대신 `Q_SIGN_FILE_NM`(+A 는 `DW_IMG_SIGN_DIR`)이 `ATDT_*`(참석자) 옆에 있다 — **근로자 참석지의 개인 서명** 기제로 보이지 그 자체가 결재 서명란은 아니다. §6-1 참조.

### 3-3. 승인라인 → 서명란 슬롯 매핑

승인요청 시점 스냅샷이 존재한다.

| 무엇 | 테이블 | 컬럼 |
|---|---|---|
| 단계 실행 | `TBASE_SANCTN_DEM_STEP` | `STEP_NO` · `STEP_SECT_CODE` · `STEP_NAME` · `STEP_GRP_NO` · `SANCTNER_USER_NO`(지정) · `ACT_USER_NO`(실처리) · `ACT_CODE` · `SANCTN_DT` · `SANCTN_OP` |
| 라인 스냅샷 | `TBASE_SANCTN_DEM_LINE_STEP` | `STEP_NO` · `STEP_NAME` · **`SANCTNER_SECT_CODE`** · **`SANCTNER_RO_CODE`** · `APPT_SANCTNER_USER_NO` |

**`RO_CODE` 가 양쪽에 같은 코드계로 존재한다** — 서명란 슬롯(`TSFAS_PROJ_REPORT_DTL.DR_CD` / `TSST_PROJ_RPT_SIGN.RO_CODE`)과 승인 단계(`SANCTNER_RO_CODE`)가 같은 A~G 코드를 쓴다. 실측(현장 승인건 `DEM_SN` 12647): 단계 `2-1`→`C`, `2-2`→`B`, `3`→`A` 이고, 서명란 정의의 `C`=공사팀장 · `B`=보건관리자 · `A`=소장과 1:1로 붙는다.

**승인자 구분(`SANCTNER_SECT_CODE`)별 슬롯 하단 표기** — 이미지의 "승인자구분" 열과 대응한다:

| 코드 | 의미 | 슬롯 직책칸(`TITLE2_x`)에 넣을 것 | 전체 분포(참고) |
|---|---|---|---|
| `RP` | 요청자 | `작성자`(요청자 고정) | 1,899 |
| `PROJ` | 현장직책 | `RO_CODE` → 직책명 | 3,557 (RO 보유 2,335) |
| `APPT` | 사용자 지정 | `지정자` 또는 지정 사용자명 | 803 |
| `HQ` | 본사직책 | `RO_CODE` → 직책명 | 235 |

### 3-4. 남은 결정 (설계 협의에서 확정할 것)

- [ ] **서명 이미지(`DR_NM_IMGx`)에 누구를 찍나** — `ACT_USER_NO`(실제 처리자)가 서명 주체로 맞아 보이나, 미처리 단계는 빈칸이 된다. `SANCTNER_USER_NO`(지정자)를 미리 찍으면 "서명 안 했는데 이름이 있는" 출력이 된다. **처리자 기준 권장 · 결정 필요.**
- [ ] **7슬롯 초과** — `MAX_DR_CNT=7` 인데 승인라인은 병렬 합의(`STEP_GRP_NO` 동일, 예 `2-1`·`2-2`)가 슬롯을 각각 먹는다. 총 단계가 7을 넘으면 **조용히 잘린다.** 초과 시 정책(잘라내기 / 병렬 1칸 병합 / 경고) 결정 필요.
- [ ] **단계명 표기** — 스냅샷 `STEP_NAME` 실측값은 `1`·`2-1`·`2-2`·`3` 같은 번호다. 이미지의 `1단계`·`2단계`는 등록 화면에서 붙인 이름이다. 그대로 쓸지 가공할지 결정 필요.
- [ ] **요청자 칸** — 이미지 2안은 첫 칸이 `요청자`/`작성자`다. `TBASE_SANCTN_DEM.RP_USER_NO` 를 쓴다.

## 4. 나머지 3건

### 4-1. 쿼리 변경

`.crf` 는 앱 매퍼를 거치지 않고 **자체 SQL 로 DB를 직접 읽는다**(README §2). 따라서 데이터셋 SQL 변경은 리포트 안에서 닫힌다 — 앱 코드 0줄.
단, 화면이 안 보내는데 리포트가 자체 조회하는 옵션이 이미 있다(`SFAS_OPT_084`·`SFAS_OPT_092`). **같은 방식으로 조달하면 파라미터 추가도 불필요하다.**

### 4-2. CCTV관제여부(옵션120)

기존 [HANDOFF_CCTV관제여부_리포트반영.md](./HANDOFF_CCTV관제여부_리포트반영.md) 가 정본이다. 요지만:

- **타입 신설 금지 · 앱 코드 0줄** — 리포트가 `TCC_PROJ_CODE.SFAS_OPT_120` 을 자체 SQL 로 조달(그 문서 §6-1)
- 표기는 승인 팝업과 통일 → `Decode(CCTV_MON_TF, 'T', 'O', 'X')`
- 위치는 `DR_FORM_NAME` 다음 · `IMPRV_MTHD` 앞 (화면 그리드 순서와 동일)
- 그 문서 §6-1(자체 SQL)과 §6-3(파라미터 전달) 중 **하나만**

> ⚠️ "CCTV 때문에 타입 분기가 필요하다"는 방향이 논의된다면 그 문서 §5·§9 가 그걸 명시적으로 기각한 근거를 담고 있다.

### 4-3. 리포트명 동적 변경

**이미 필드가 존재한다.** `REPORT_NM` 이 `.crf` MAIN 필드로 들어와 있고(폴더의 TypeB·TypeC 사본에서 확인), 값의 출처는 현장별 `TSFAS_PROJ_REPORT.REPORT_NM` 이다. 즉 신규 개발이 아니라 **적용 대상 서식·타이틀 위치를 넓히는 작업**이다.

- 근로자 참석지 타이틀 = `#{리포트명} 근로자 참석지` 형태로 조립
- 4종 중 이 필드를 아직 안 쓰는 서식에 같은 방식으로 추가

## 5. "다음에 또 늘어날 텐데" — 조합폭발 타개

금번 건은 타입을 안 늘려도 되지만, 질문은 그다음이다. 세 단계로 본다.

### 5-1. [즉효 · 이번 건] 옵션은 리포트 내부 조건으로

이 시스템에서 **이미 검증된 패턴**이다 — `SFAS_OPT_040`·`040_001`·`048`·`049`·`049_001` 은 4개 `.crf` 전부의 MAIN 필드로 들어가 내부 조건으로 처리되고 있다(폴더 사본 실측). 새로 도입할 기법이 아니다.
반면 `066_001`·`066_002`·`048_001` 만 파일 선택으로 승격돼 있고, 그게 조합폭발과 §2 버그의 원인이다.

**비용은 컬럼 폭 재배분**(숨김 시 잔여 폭 처리)이고, 이게 실질 작업량의 대부분이다.

### 5-2. [근본] 서명란의 7슬롯 방식을 항목상세에도 쓴다

**서명란은 이미 이 문제를 풀어놨다.** 서명란은 슬롯 7개를 고정으로 두고, 라벨(`TITLE1`/`TITLE2`)·코드(`DR_CD`)·개수(`DR_CNT`)를 **DB 메타에서 받는다**(§3-2). 그래서 서명란 구성이 현장마다 달라도 `.crf` 는 하나다.

같은 구조를 **항목상세 그리드**에 적용하면:

| 지금 | 제네릭 슬롯 적용 후 |
|---|---|
| 컬럼마다 `.crf` 에 필드·헤더·조건식이 박힘 | `COL1..COLn` + `COL_TITLE1..n` + `COL_CNT` |
| 옵션 추가 = `.crf` N개 수정 (또는 파일 증식) | 옵션 추가 = **SQL 한 곳** (`.crf` 무변경) |
| 컬럼 폭 재배분을 매번 수동 | 슬롯 폭 규칙 1회 확정 |

- **초기 비용**: 항목상세 밴드 1회 재작성(서식별). 셀 병합·정렬이 컬럼마다 다르면 제약이 생긴다.
- **효과**: 옵션 증가에 대해 **완전 상수** — 이번 사용자 질문("다음에 또")의 유일한 근본 답.
- **선행 확인**: 서명란 7슬롯의 폭·라벨 처리를 디자이너에서 열어 **어떻게 가변 폭을 다루는지** 확인. 같은 기법을 상세 그리드에 옮길 수 있는지가 관건.

### 5-3. [정리] `DVS_CD` 의 역할 재정의 + 4종 → 2종

> **`DVS_CD` 는 "지면 구성이 근본적으로 다른 서식 계열"에만 쓴다. 옵션에 따른 컬럼 표시/숨김은 반드시 리포트 내부 조건으로 처리한다.**

폴더의 현재 사본 기준으로 보면 계열은 둘로 갈린다:

| 계열 | 파일(현재 사본) | 특징 필드 |
|---|---|---|
| **항목상세 list형** | A · D | `RISK_FACT`·`IMPRV_MTHD`·`ASSMNT_*`·`WORK_STAFF` + `ATDT_*`(참석자) + `Q_SIGN_FILE_NM` |
| **종합의견 + 서명란 슬롯형** | B · C | `APPRV_CMT`·`SYNTH_CONSTR_OP`·`SYNTH_SAF_OP` + `REPORT_NM`·`DR_CNT`·`TITLE1_x`·`TITLE2_x`·`DR_CD_x`·`DR_NM_IMGx` |

이 기준이면 4종 → **2종**으로 수렴 가능하다.

🔴 **단, 어느 파일이 어느 계열인지는 지금 확정할 수 없다.**
- 폴더 사본이 개발회사 전용본으로 교체되면서 8월 판정과 정반대가 됐다(§6-3)
- 8월 문서는 `DR_CD_1..7` 을 "재해형태 7종 pivot" 으로 읽었으나, DB 대조 결과 **서명란 슬롯**(`TSFAS_PROJ_REPORT_DTL.DR_CD`)이다. 재해형태는 이 코드베이스에서 `DISASTER_FORM`·`DR_FORM`·`DR_SN` 을 쓴다
- **실물 확인 후 확정**한다

## 6. 🔴 착수 전 블로커

### 6-1. 2안이 필요한 서식(A·D)에 서명란 슬롯이 안 보인다

**CCTV 건과 똑같은 모양이다** — "요청자가 쓰는 서식에 넣을 자리가 없다".

옵션 060_003 을 켠 현장을 `RPT_TYPE_CODE` Case 로 돌려본 결과(개발 DB, 2026-09-02):

| RPT_TYPE | 현장 | 회사 |
|---|---|---|
| **A** | 1 (`HT0001`) | 30212 `[개발(원)] 클라우드랩` |
| **D** | 4 (`A0001`·`GC001`·`R2353`·`UT001`) | 〃 |
| B·C | **0** | — |

그런데 서명란 7슬롯 필드(`TITLE1_x`·`TITLE2_x`·`DR_CD_x`·`REPORT_NM`)는 **B·C 사본에만** 있고 A·D 에는 없다(§3-2).

| | 서명란 슬롯 | 다른 서명 기제 |
|---|:--:|---|
| A | ❌ | `Q_SIGN_FILE_NM` · `DW_IMG_SIGN_DIR` (참석자 서명) |
| B · C | ✅ | — |
| D | ❌ | `Q_SIGN_FILE_NM` (참석자 서명) |

- 필드 **"있음"은 강한 증거**지만 **"없음"은 약하다**(압축 구간). 다만 A·D 가 *다른 서명 기제*를 갖고 있다는 건 단순 누락이 아니라 **설계가 다르다**는 신호다
- A·D 에 결재 서명란이 정적 서식(고정 텍스트)으로 그려져 있다면, 2안은 **SQL 교체가 아니라 서식 개편**이 된다 → 공수가 완전히 달라진다

**확인할 것**

- [ ] A·D 를 디자이너로 열어 **결재 서명란이 있는지, 있다면 DB 메타를 읽는지 정적인지**
- [ ] 위 조회는 **개발 DB 기준**이다. 운영에서 060_003 을 켠(켤) 현장의 실제 타입을 확인할 것
- [ ] A·D 에 슬롯이 없다면: ⓐ B·C 의 슬롯 기제를 A·D 에 이식할지, ⓑ A·D 전용으로 별도 설계할지 결정

> ⚠️ 이미지의 1안/2안 목업은 **항목상세 list형 지면**(유해위험요인·위험성감소대책·작업일정·검토의견 그리드)이다. 현재 사본 기준 그건 **A·D 계열**이다 — 위 조회 결과와 일치한다.

### 6-2. 승인라인 스냅샷이 대부분 비어 있다

위험성평가 승인건 기준 실측(2026-09-02):

| 항목 | 건수 |
|---|---|
| 승인건(`CFM_DEM_SN` 보유) | **22** |
| 그중 라인 스냅샷(`TBASE_SANCTN_DEM_LINE_STEP`) 존재 | **3** |
| 그중 직책(`SANCTNER_RO_CODE`) 보유 | **1** |

스냅샷을 만드는 SQL 자체는 있다(`CommonSanctionSql.insertSanctionDemandLineStep`, `TBASE_SANCTN_LINE_STEP` → `DEM_LINE_STEP` 복사). **전환·소급 경로에서 라인 스냅샷이 생성되지 않는지 확인이 필요하다.**

- 스냅샷이 없으면 2안은 **직책칸을 못 채운다** → 서명란이 비거나 fallback 이 필요하다
- 확인 결과에 따라: ⓐ 전환 경로에 스냅샷 생성 추가(앱 작업 발생) 또는 ⓑ 리포트가 현재 라인 정의(`TSST_SANCTN_LINE_STEP`)를 참조 — 단 ⓑ는 **승인라인 변경 후 재출력 시 옛 문서에 오늘 직책이 찍히는** 정합성 문제가 있다

### 6-3. 이 폴더의 `.crf` 사본이 배포 기본본이 아니다

폴더 파일이 전부 `_LGHTEST` 접미로 교체돼 있다(2026-08-12·08-25). DB 확인 결과:

- `TCC_RRPT_FILE_CPN` 에 **2026-08-14** 등록된 **회사 30211 `[개발(하)] 클라우드랩` · 30212 `[개발(원)] 클라우드랩` 전용 오버라이드**
- 해석 순서: `CPN`(회사별)이 있으면 `BAS`(기본)를 **덮는다** ([CommonPrcsSql.xml `selectReportList`](../../../src/main/resources/sqlmap/mappers/common/CommonPrcsSql.xml))
- `DVS_CD`↔파일명 매핑 자체는 정상(A→`Register_LGHTEST`, B→`TypeB_LGHTEST`, …)

**그런데 같은 `DVS_CD` 인데 8월 판정과 계열이 어긋난다:**

| DVS_CD | 문서(2026-08-10, 기본본 기준) | 폴더의 현재 사본(`_LGHTEST`) |
|---|---|---|
| A | 항목상세 0종 | **항목상세 10종** |
| B·C | 항목상세 10종 | **없음**(`TITLE1_x`·`DR_CD_x` 구성) |
| D | 항목상세 0종, 등급컬럼 없음 | **항목상세 10종 + 이전등급 + 감소후등급** |

- 필드 **"있음"은 강한 증거**(문자열 실존), **"없음"은 약하다** — 압축 구간이 있어 못 읽는 부분이 있다. 8월 문서도 같은 한계를 스스로 적어뒀다("디자이너로 열어 최종 확인할 것")
- **개발회사 전용본이 기본본과 다른 설계일 가능성**이 크다. 어느 쪽을 기준으로 작업할지 먼저 정해야 한다
- 부수: 구조개선 검토 §2 의 **157현장 이전등급 누락**은 기본본 기준 진단이다. 개발본 D 에는 두 컬럼이 다 있으므로 **조치됐다고 단정하지 말 것**

**⇒ 착수 전에 배포 기본본 4종을 받아 사본을 정렬한다.**

## 9. 참고 — 이번 건이 말해주는 것

앱은 `setColumnVisible` 한 곳이면 끝나는 변경이 리포트에서는 **파일 수 × 옵션 수**로 불어난다. 서명란은 이 문제를 **슬롯 + DB 메타**로 이미 풀어놨고, 항목상세만 아직 안 풀려 있다(§5-2).

**다음에 옵션이 추가될 때의 판단 기준:**

> 지면 구성이 근본적으로 다른가 → 그때만 `DVS_CD`
> 컬럼만 켜고 끄는가 → 리포트 내부 조건
> 자주 바뀌는가 → 슬롯 + DB 메타(서명란 방식)
