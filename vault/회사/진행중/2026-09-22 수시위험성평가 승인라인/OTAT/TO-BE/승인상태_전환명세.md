# 승인 상태 전환 명세 (옵션 미사용 / 060 / 060_003)

> **성격**: 아직 구현하지 않은 **결정 명세**. 현재 동작(SoT)은 [현행/SCNT_구현방식_공유.md](../현행/SCNT_구현방식_공유.md).
> **작성**: 2026-08-23 · 공유받은 결정사항 반영
> **최종 갱신**: 2026-08-27 — §5 이행 현황 실측(§5-1), 승인 팝업·승인라인변경 구현분 반영(§9)
> **선행 문서 관계**: SoT §2.5 의 `C·D 분기`(2026-08-21 추가)는 **이 문서 §5 로 대체된다.**

---

## 0. 이 문서가 필요한 이유

승인 옵션은 세 가지 상태가 있고, 현장이 이 사이를 오간다.

| 옵션 상태 | 의미 |
|---|---|
| **미사용** (`060=F`, `060_003=F`) | 승인 없이 접수/미접수만 |
| **레거시** (`060=T`) | 공사팀장 → 안전팀장 → 현장소장 3단 결재 |
| **승인모듈** (`060_003=T`) | 표준승인(SCNT) — 승인라인 지정 후 요청/승인 |

옵션을 바꾸는 순간 **기존 회차를 어떻게 할 것인가**가 매번 문제가 됐고, 판단이 그때그때 달라져 코드와 문서가 어긋났다. 이 문서로 기준을 고정한다.

> 공유받은 결정 3건이 **기존 로직 어디에 꽂히고 무엇을 바꾸는지**는 §8 에 지점별로 정리했다.

## 1. 용어 — 두 어휘 체계를 섞지 않는다

같은 `STS_NAME` 컬럼에 **성격이 다른 두 어휘**가 들어온다. 문서·대화에서 이걸 섞으면 반드시 오해가 생긴다.

### 1-A. 레거시 어휘 (승인과 무관, 협력사 화면 기준)

| 값 | 의미 | 근거 |
|---|---|---|
| `작성중` | 협력사가 아직 제출 안 함 | `REGIS.CHECK_TF = 'F'` |
| `제출` | 협력사가 제출함, 원청 접수 전 | `REGIS.CHECK_TF = 'T'` |
| `접수` | 원청이 접수함 | `RECEIVE.CHECK_TF = 'T'` |
| `미접수` | 원청이 아직 접수 안 함 | `RECEIVE.CHECK_TF = 'F'` |

### 1-B. 승인 상태 어휘

| 값 | 코드 | 의미 |
|---|---|---|
| `요청대기` | `REG` / 라인없음 | 승인요청 전 |
| `승인대기` | `DEM` | 승인요청함 |
| `승인중` | `PROG` | 중간 단계까지 진행 |
| `승인반려` | `REJ` | 반려됨 |
| `승인완료` | `CMPL` | 최종 승인 |

### 1-C. 레거시 결재 어휘 (옵션60 전용)

`공사팀장승인대기`(`STTS_CD` 30) · `안전팀장승인대기`(40) · `현장소장승인대기`(50) · `평가서승인완료`(60)

> ⚠️ **`작성중` 은 1-A 에만 존재한다.** 승인 상태에는 `작성중` 이 없다 — 승인요청 전은 전부 `요청대기` 다(2026-08-21 통일).
> 공유 문서의 *"제출취소 후 작성중 상태로 돌아가서"* 는 **1-A 의 `작성중`** 이다(협력사 화면). 코드와 일치한다.

## 2. 옵션 상태별 동작 상세

### 2-1. 회차 유형

상태명은 **회차가 어느 궤도에 있는지**로 정해진다. 유형은 넷뿐이다.

| 유형 | 판별 | 뜻 |
|---|---|---|
| **A** | `CFM_DEM_SN` 있음 | 승인라인이 만들어진 회차 |
| **B** | `STTS_CD` 30~60, 라인 없음 | 레거시 결재가 진행된 회차 |
| **C** | `STTS_CD` 10/20, 라인 없음, **제출자 없음** | 원청이 직접 만든 회차 |
| **D** | `STTS_CD` 10/20, 라인 없음, **제출자 있음** | 협력사가 제출한 회차 |

> C/D 판별은 §4 참조. 제출자 정보는 지금 없고 핫픽스로 만든다.
>
> **용어** — 제출자는 `SUB_COMPANY_ID`·`SUB_USER_NO` 에 담는다(사내 표준 컬럼명, §4-2).
> 승인 모듈의 요청자(`TBASE_SANCTN_DEM.RP_USER_NO`) 와는 다른 값이다 — 전환 시 전자를 후자로 복사한다.

### 2-2. 상태명 매트릭스

| 유형 | 미사용 (F/F) | 레거시 (060=T) | 승인모듈 (060_003=T) |
|---|---|---|---|
| **A** 라인 있음 | 승인 상태명 | 승인 상태명 | 승인 상태명 |
| **B** 레거시 30~60 | 접수 / 미접수 | 레거시 결재 어휘 | 레거시 결재 어휘 🔒 |
| **C** 원청 작성 | 접수 / 미접수 | 접수 / 미접수 | 접수 / 미접수 🔒 → 전환 시 **요청대기** |
| **D** 협력 제출 | 접수 / 미접수 | 접수 / 미접수 | 접수 / 미접수 🔒 → 전환 시 **승인대기** |

**A 는 옵션과 무관하다.** 승인라인이 한 번 생기면 옵션을 어떻게 바꾸든 승인 상태명을 유지한다 — 진행 중인 결재가 끊기면 안 된다.

**옵션을 켜는 것만으로는 C·D 가 바뀌지 않는다.** 소급 회차는 누군가 명시적으로 전환할 때까지 접수 흐름 그대로다(§7-1).
전환 경로는 둘 — 원청이 접수화면 버튼을 누르거나, 협력사가 제출 버튼(=승인요청)으로 승인 궤도에 올린다.

### 2-3. 편집 권한

| 옵션 상태 | 회차 상태 | 수정 가능자 |
|---|---|---|
| 미사용 | 전체 | 제한 없음(기존) |
| 레거시 (060) | `STTS` 30 | 제한 없음 |
| 레거시 (060) | `STTS` 40~60 | 자기 차례 결재자만 |
| 승인모듈 | `요청대기`·`승인반려` | 제한 없음 |
| 승인모듈 | **`승인대기`** | **모든 내용 수정 가능** — 레거시 `공사팀장승인대기` 와 동일 취급 |
| 승인모듈 | **`승인중`** | **현재 단계 ~ 이후 단계 승인자 전원** — 레거시 060 프로세스와 동일 규약 |
| 승인모듈 | `승인완료` | 잠금 |

> `승인중` 의 "현재~이후" 범위는 §7-3 확정 — 미처리 단계의 승인자 + 그 단계의 대리인.

## 3. 전환 시 처리 — 소급유지 방식

### 3-1. 원칙

**소급유지의 목적은 "진행 중이던 결재가 끊기는 것"을 막는 것 하나다.** 진행 중이지 않은 회차는 소급유지 대상이 아니다.

### 3-2. 전환별 처리

| 전환 | 처리 |
|---|---|
| **미사용 ↔ 060** | **소급 없음** — 옵션 토글 즉시 반영. 레거시엔 표시/잠금 소급이 애초에 없었고, 옵션을 끄면 `STTS_CD` 무시하고 접수로 돌아간다(데이터는 보존) |
| **미사용 → 060_003** | B 만 소급유지. **C·D 는 승인단계를 생성해 승인 궤도로 편입**(§3-3) |
| **060 → 060_003** | B 만 소급유지(레거시 결재 어휘·승인버튼 유지). C·D 는 위와 동일 |
| **060_003 → 미사용/060** | A 는 승인 상태명 유지(끊기면 안 됨). 나머지는 해당 옵션 규칙을 따름 |

### 3-3. 기존 데이터 편입 규칙 (미사용/060 → 060_003)

공유받은 결정이다.

**① 제출 전 회차 (협력사 화면 `작성중`)**
협력사가 제출취소해서 `작성중` 으로 돌아간 뒤 협력사 화면에서 승인이력을 생성한다. **현재 동작하는 기능이라 추가 작업 없음.**

**② 접수 상태 회차 → 접수화면에서 승인단계 생성**

| 조건 | 요청자 | 결과 상태 |
|---|---|---|
| **제출자 데이터 있음** (유형 D) | **제출자** | `승인대기` |
| **제출자 데이터 없음** (유형 C) | **세션 사용자** | `요청대기` |

논리: 협력사가 실제로 제출한 회차는 "요청까지 끝난 것"으로 보아 `승인대기` 로 올리고, 원청이 스스로 만든 회차는 아직 요청 행위가 없으므로 `요청대기` 에 둔다.

> ⚠️ **이 규칙은 2026-08-21 에 구현한 "협력 제출본 소급유지"를 대체한다.** §6 참조.

## 4. 상태 구분 방식 — 제출자 데이터

### 4-1. 현재 제출자를 알 수 없다

두 생성 경로가 테이블에 **같은 모양**을 남긴다.

| | 협력 제출 (`trscSub`) | 원청 직접작성 (`insertAsmt`) |
|---|---|---|
| `TSF_ASSMNT_RECEIVE` | Merge | Insert |
| `TSF_ASSMNT_REGIS` | 협력이 미리 작성 | **같은 트랜잭션에서 함께 Insert** |
| `CHECK_TF` | 제출 시 `'T'` | `#{RCPT_TF}` — 접수하면 `'T'` |

- `REGIS` 유무로 판별 불가 — 실측 365k 중 364k 가 `REGIS` 있음(원청 작성분 24,975 포함)
- `REGIS.CHECK_TF` 로도 판별 불가 — 364k 가 `'T'`
- 제출자 전용 컬럼 **없음**. 협력 제출 시 `RECEIVE.MODUSERNO` 만 갱신되고, 이후 원청이 수정하면 **덮어써진다**

### 4-2. 제출자 컬럼 신설 (핫픽스)

`TSF_ASSMNT_REGIS`·`TSF_ASSMNT_RECEIVE` 에 **제출자**를 남긴다. 사내 표준 컬럼명을 그대로 쓴다.

```
SUB_COMPANY_ID   -- 제출자_회사ID
SUB_USER_NO      -- 제출자_사용자번호
```

**신조어가 아니라 이미 쓰이는 표준이다.** 같은 도메인에도 선례가 있다.

| 컬럼 | 코멘트 | 쓰는 테이블 |
|---|---|---|
| `SUB_COMPANY_ID` | 제출자_회사ID | `TSF_RISK_ASSMNT_APPRV_CMNT` · `TSF_RISK_DAILY_APPRV_CMNT` · `TSF_WA_DCHK` · `TEMPHS_CHK_CFM_COOP` · `TWTLB_SAF_EDU` |
| `SUB_USER_NO` | 제출자_사용자번호 | `TSF_WA_DCHK` · `TEMPHS_CHK_CFM_COOP` · `TWTLB_SAF_EDU` |

**`RP_*`(요청자) 를 쓰지 않는 이유** — 값이 기록되는 순간의 행위는 **제출**이다.
승인 미사용·060 시점에는 "요청" 개념 자체가 없어서, 존재하지 않는 개념으로 데이터를 명명하는 꼴이 된다.

| | |
|---|---|
| 행위와 일치 | 협력사 화면 이름이 `상시·수시위험성평가제출` 이다 |
| `요청` 은 이미 점유됨 | `요청대기` · `요청취소` · `DEM_SN`(요청순번) · `RP_USER_NO`(`TBASE_SANCTN_DEM`). RECEIVE 에 또 `RP_*` 를 두면 **어느 테이블 값인지** 매번 헷갈린다 |
| 의미가 다름 | RECEIVE 의 값 = "이 회차를 제출한 사람" 이라는 **사실** / DEM 의 `RP_USER_NO` = "이 승인요청의 요청자" 라는 **역할**. 전환 시 전자를 후자로 복사할 뿐이다 |

> `SUB_TF`(제출여부) 와 같은 계열이라 테이블 안에서도 일관된다.

#### 대상 테이블 — `RECEIVE` 뿐 아니라 `REGIS` 에도 둔다 (2026-08-27 실측으로 확정)

**원청 접수 화면이 `REGIS`(제출본)까지 만든다** — `SfasRegAtRiskasmtRcptSql.xml:1518` `Insert Into TSF_ASSMNT_REGIS`.
그래서 두 테이블 **모두** 기존 컬럼으로는 제출자를 유도할 수 없다. 운영 실측:

| 관측 | 운영 건수 | 뜻 |
|---|---|---|
| `REGIS.CRTUSERNO` 가 원청 소속 | **24,904** (6.6%) | 만든 사람 ≠ 낸 사람. `R_COMPANY_ID` 로 대체 불가 |
| `RECEIVE.CRTUSERNO` 가 `Null` | **2,761** | 판별불가 |
| `RECEIVE.CRTUSERNO` 소속 불명 | **1,012** | 판별불가 (합쳐 1.0%) |
| 두 테이블의 `CRTUSERNO` 불일치 | **14,364** | 한쪽 값을 다른 쪽으로 미룰 수 없다 |

> 원청 소속 생성자 상위 15명은 각각 수백 건을, 여러 현장·수십 개 협력사에 걸쳐 2017년부터 어제까지 만들었다.
> 배치·이관 흔적이 아니라 **상시적인 대리작성 운영 패턴**이다.

| 테이블 | `SUB_*` 의 뜻 | `Null` 일 때 |
|---|---|---|
| `TSF_ASSMNT_REGIS` | 이 **제출본을 낸** 주체. 대리작성이면 원청 값 | — |
| `TSF_ASSMNT_RECEIVE` | 이 **회차를 제출한** 주체 | 제출 행위 자체가 없음 = 원청 직접 작성 (유형 C / D 판별) |

DDL: [`docs/db/migration/20260922_TSF_ASSMNT_제출자컬럼.sql`](../../db/migration/20260922_TSF_ASSMNT_제출자컬럼.sql)

#### 기록 시점 — 작성이 아니라 **제출**이다

제출자는 **`trscSub`(제출 트랜잭션)을 실행한 사람**이다. 회차를 만든 사람(`insertAsmt`)이 아니다.
원청이 협력사 대신 작성해 두고 협력사가 제출하는 흐름이 실재하므로 둘은 다를 수 있다.
사내 선례(`SfasRegCompanyRoundCheckSql` · `SfasRegCompanyDailySafetyCheckSql`)와 같은 식을 쓴다.

```sql
SUB_COMPANY_ID = Decode(#{SUB_TF}, 'T', #{SESSION_COMPANY_ID}, Null),  -- 제출자_회사ID
SUB_USER_NO = Decode(#{SUB_TF}, 'T', #{SESSION_USER_NO}, Null)  -- 제출자_사용자번호
```

> `#{SESSION_COMPANY_ID}` 가 협력사를 실제로 가려낸다 — 선례 `TEMPHS_CHK_CFM_COOP` 에서
> `SUB_COMPANY_ID <> COMPANY_ID` 인 행이 4,582건이다(운영 실측). 테넌트ID 고정값이 아니다.

**저장 지점 8곳 (✅ 2026-08-27 반영 완료)** — 하나라도 빠지면 판별불가가 계속 생긴다.

| 구분 | 위치 | 대상 | 넣는 값 |
|---|---|---|---|
| 웹 · 접수 작성 | `SfasRegAtRiskasmtRcptSql.xml` `insertAsmt` | `RECEIVE` Insert | **`Null`** (원청 작성 — 제출 행위 없음) |
| 웹 · 접수 작성 | `SfasRegAtRiskasmtRcptSql.xml` `insertAsmt` | `REGIS` Insert | **`Null`** (원청 대리작성) |
| 웹 · 협력 작성 | `SfasRegAtRiskasmtSubSql.xml` `insertAsmt` | `REGIS` Insert | **`Null`** (아직 미제출) |
| 웹 · **제출** | `SfasRegAtRiskasmtSubSql.xml` `trscSub` | `REGIS` Update | `Decode` |
| 웹 · **제출** | `SfasRegAtRiskasmtSubSql.xml` `trscSub` | `RECEIVE` Merge (Matched) | `Decode` |

### 4-3. 소급분 백필

핫픽스 이전 데이터는 제출자가 **영구히 없다.** 유일하게 남는 신호는 `CRTUSERNO` 소속이다.

```sql
(Select Max('T') From TCC_EMPLOYE x Where 1 = 1 And x.USER_NO = a.CRTUSERNO And x.COMPANY_ID = a.R_COMPANY_ID) COOP_CRT_TF
```

> Oracle 은 `Select` 절에서 `Exists` 를 못 쓴다. 스칼라 서브쿼리여야 한다.

**교차검증** — 원청 경로는 RECEIVE·REGIS 를 한 트랜잭션에서 만들어 `CRTDATE` 가 같고, 협력 경로는 작성과 제출 시점이 벌어진다.

| `CRTDATE` 관계 | 협력 | 원청 | 판별불가 |
|---|---|---|---|
| RECEIVE 가 나중 (제출 패턴) | **313,589** | 468 | 3,293 |
| 동시생성 5초 이내 (한 트랜잭션) | 22,700 | **24,452** | 469 |

원청의 98%, 협력의 93% 가 각각 한쪽에 몰린다. 두 독립 신호가 같은 방향을 가리킨다.

**판별불가 3,768건(1%)** — 생성자 `Null` 2,761 / 사용자 정보 없음 639 / 회사 불일치 368.

> ⚠️ **오분류를 받아들여야 한다.** 판별불가는 "제출자 없음" 으로 떨어져 `요청대기` + 요청자=세션사용자가 되는데, 실제로는 협력이 제출한 건이 다수다. 백필로 줄일 수는 있어도 0 으로는 못 만든다. §7-5 결정 필요.

| 🔴 **A. 하드 `CHECK_TF`** | `And a.CHECK_TF = 'T'` (게이트 없음) | **데이터 사라짐** | 가져오기 팝업 대부분 · 운영현황(3) · 평가결과모니터링(2) · 상시평가점검 2종(3) · 안전작업허가 4종 |
| 🔴 **B. 하드 `STTS_CD`** | `In ('20','60')` / `!= '10'` (게이트 없음) | **데이터 사라짐** | `SfasPopRegAssmntRecive`(389) · `SfasRegCompanyRoutineCheckItemPopGetRiskAssessment`(147) · **`SfasRegMeetingConfirm`(643)** · **`SfasRegMeetingDraft`(1455)** |
| 🟡 **C. 상태명 표시** | `When a.CHECK_TF='T' Or a.STTS_CD='20' Then '접수'` | **미접수로 표시** (데이터는 보임) | 재해사례 3종 · `SfasInqCompanyAnytimeRiskAssessment` · `SupvInqCompanyAnytimeRiskAssessment` · 모니터링 2종 |
| ⚪ **D. `060` 게이트 있음** | `(SFAS_OPT_060='F' Or STTS_CD In('20','60'))` | **무해** — 060='F' 면 통과 | A 와 같은 줄에 붙어 있는 짝. 게이트 있는 쪽만 무해 |
| ⚪ **E. `060` 전용 Case** | `When SFAS_OPT_060='T' And STTS_CD=20` | **무해** — 안 탐 | TBM 비정기 2종 |

**가져오기 팝업은 `CHECK_TF='T'`(하드) + `STTS_CD` 게이트 쌍으로 되어 있다.** 게이트가 지켜주는 건 `STTS_CD` 쪽뿐이고
`CHECK_TF` 는 무방비라 A 등급이다. 즉 **가져오기 계열은 060 이 꺼져 있어도 목록이 빈다.**

**회의록 2종이 새로 드러났다** — `STTS_CD != '10'` 은 게이트가 없어 060_003 현장은 회의록에서 평가서를 못 가져온다.

> ⚠️ **판정 방법 주의 (2026-08-27 시행착오 기록).** alias 를 파일 전역으로 매칭하면 오판한다 —
> `a`·`x` 같은 한 글자 alias 를 여러 테이블이 돌려쓴다. 실제로 대시보드 3종(동문·금성백조·한국농어촌공사)은
> `TSF_ASSMNT_REGIS`(협력 제출본), 모니터링 일부는 `TSF_SERCURITYCHECK_DETAIL` 소속이라 **영향 없음**이었다.
> Oracle 은 `Select` 절이 `From` 보다 위라 역방향 탐색으로도 못 찾는다. **해당 라인에서 가장 가까운 `테이블 alias` 바인딩**을 채택해야 맞다.
>
> **대시보드는 영향받지 않는다** — `TSF_ASSMNT_REGIS.CHECK_TF`(협력사 제출여부)를 보는데,
> 승인요청 시 `mergeRegisToReceive` 가 `trscSub` 을 `SUB_TF='T'` 로 태워 이 값을 켠다. 060_003 에서도 정상 동작한다.

##### ⚠️ `060` 과 `060_003` 이 동시에 켜질 수 있다

개발 서버(PMIS4) 실측 — 060_003 을 켠 현장 3개 중 **1개가 `060='T'` 와 동시에 켜져 있다.**

| 현장 | 회사/코드 | 060 | 060_003 | 회차수 |
|---|---|---|---|---|
| 그냥테스트현장 | 30212 / A0001 | F | T | 29 |
| 검측요청서 현장 | 30212 / GC001 | F | T | 34 |
| **단위 테스트 기업 현장** | 30212 / UT001 | **T** | **T** | 1 |

**이 조합에서는 D 등급이 D 가 아니다.** `060='T'` 라 게이트가 열리지 않고 `STTS_CD In('20','60')` 을 그대로 요구하는데,
060_003 에서 `STTS_CD` 는 `'10'` 에 묶여 있으므로 **가져오기 팝업 계열이 통째로 빈 목록이 된다.**

**✅ 정책은 이미 확정돼 있다 — 미결이 아니다 (2026-08-27 확인).**

[SCNT_표준승인_도입계획.md](../설계아카이브/발표자료/SCNT_표준승인_도입계획.md) 의 **결정 D11** 이 상호배타를 못 박았다.

> `060=T XOR 060_003=T` (둘 다 F = 미사용). **SCNT 현장은 `060=F` 로 저장.**
> admin UI 에서 하나를 T 로 하면 다른 하나를 자동 F + readonly (양방향). **원천 차단.**

따라서 D 등급(060 게이트 있음)은 설계대로면 **영원히 무해**하다. 위에서 본 `UT001` 은 admin 차단이 아직 구현되지 않아 손으로 만들어진 예외였고, **2026-08-27 조치 완료**다.

> 📌 [옵션전수 §12.0](./SfasRcpt_옵션전수_화면제어.md) 의 2026-08-05 실측에서도 `T/T` 조합은 0건이었다.
> 이번에 1건이 잡힌 것은 그 이후 수동 설정된 것으로, 실측이 틀렸던 게 아니다.

**남은 것은 정책이 아니라 가드다** — admin UI 의 자동 F + readonly 처리가 실제로 들어갔는지 확인이 필요하다.
그 전까지는 손으로 T/T 를 만들 수 있고, 그 조합에서는 가져오기 팝업 계열이 빈 목록이 된다.

#### 6-1-d. 조치

조회 43곳을 CFM 기준으로 고치는 것은 범위와 누락 위험이 크다. **쓰기 한 곳에서 값을 맞춘다.**

승인요청 시점에 `CHECK_TF='T'` · `STTS_CD='20'` · `CHECK_USER_NO` 를 함께 기록한다. 삽입 지점이 이미 있다.

```java
// SfasAtRiskasmtSanctionHandler.mergeRegisToReceive
if("T".equals(mRegis.get("RCPT_EXISTS_TF"))) return;   // ← 여기서 접수 컬럼 3종 갱신 후 return
```

승인 궤도에 오른 것을 "원청이 받았다" 로 보는 것은 이미 선언한 *"승인 팝업이 접수를 대체한다"* 와 일관된다.
`CHECK_USER_NO` 에는 요청을 실행한 사용자를 넣는다.

접수취소와도 충돌하지 않는다 — 접수완료 회차엔 전환 버튼과 접수취소 버튼이 함께 뜨고, 원청이 둘 중 하나를 고른다(§9-10 ②).

> **백필 불필요** — 운영에 `SFAS_OPT_060_003` 컬럼 자체가 없어 켠 현장이 0개다. 경계가 전부 미래에 있다.

> ⚠️ **`STTS_CD='20'` 은 확인이 필요하다.** `'20'`(접수)로 올리면 레거시 판정(`STTS 30~60 → 레거시 궤도`)에는 안 걸리지만,
> `STTS_CD` 를 단계로 읽는 곳이 `'20'` 을 어떻게 다루는지 43개 중 해당 매퍼만 확인해야 한다.
>
> **확인 방법 (2026-08-26 합의)** — 43개 전수가 아니라 `'20'` 을 **분기 조건으로 쓰는** 매퍼만 본다.
> `STTS_CD` 를 `Select` 로 실어 나르기만 하는 곳은 값이 늘어도 무해하므로 대상이 아니다.
> 판정 기준은 *"`'20'` 이 특정 분기에 들어가서 다른 결과를 내는가"* 이고, 🔴 표시한 커스텀 대시보드·모니터링·운영현황·감리 계열이 우선이다.
>
> **`RCPT_TF` 도 같은 축이다.** 060_003 에서 무관하다고 봤으나 `STTS_CD` 와 함께 갱신하는 편이 맞는지 판단이 서지 않았다.
> `RCPT_TF = STTS_CD In('40','50','60') Or CHECK_TF='T'` 이므로 **`STTS_CD='20'` 만으로는 `RCPT_TF` 가 켜지지 않는다** — `CHECK_TF='T'` 가 켜는 쪽이다.
> 즉 위 조치(§6-1-d)로 `CHECK_TF='T'` 를 함께 쓰면 `RCPT_TF` 는 따라온다. **별도 갱신은 불필요**하되, 이 연쇄를 의도한 것인지 확인이 남았다.

#### 6-1-e. A·B 처리 — 값은 `'20'` 뿐이다

**A·B 는 §6-1-d 조치 하나로 함께 해소된다.** A 는 `CHECK_TF='T'` 를, B 는 `STTS_CD` 가 `'10'` 이 아니기를 요구하는데
승인요청 시점에 둘 다 기록하면 29개 매퍼를 손대지 않고 끝난다. 조회를 고치는 안은 범위·누락 위험이 크다(§6-1-d).

**`STTS_CD` 값은 `'20'` 이어야 한다. 다른 값은 전부 부작용이 있다.**

| 후보 | 문제 |
|---|---|
| `'30'` (공사팀장승인대기) | §2-3 의 *"`DEM` = 레거시 30 과 동일 취급"* 과 의미는 맞지만, **레거시 궤도 판정에 걸린다** |
| `'60'` (평가서승인완료) | 승인완료 시 올리고 싶어지지만 역시 레거시 궤도 판정에 걸린다 |
| **`'20'` (접수)** | 레거시 판정을 안 타면서 A·B·C·D 를 모두 만족하는 **유일한 값** |

레거시 궤도 판정은 `SfasRegAtRiskasmtRcptSql` 956·963·970 행이다.

```sql
When a.STTS_CD In ('30', '40', '50', '60') Or (a.CFM_DEM_SN Is Null And Nvl(d.SFAS_OPT_060_003, 'F') = 'F') Then
    SFCC_GET_USER_NM(a.COMPANY_ID, a.APPRV_C_USER_NO)   -- 레거시 승인자명 노출
```

`'30'`·`'60'` 으로 올리면 승인 모듈 회차가 **레거시로 오인돼 옛 승인자명이 되살아난다.**
따라서 **승인완료 시에도 `'20'` 을 유지한다.** 완료 여부는 `CFM_STS_CODE` 로 읽는다.

#### 6-1-f. 갱신 시점 명세 — ✅ 확정 (2026-08-27)

**승인 모듈에서도 `CHECK_TF`·`STTS_CD` 를 계속 갱신한다.** 레거시 컬럼을 죽은 값으로 두지 않고 살려서 맞춘다.
쓰는 시점은 **승인요청 한 번뿐**이고, 이후 상태 변화에는 손대지 않는다.

| SCNT 시점 | 상태 | `CHECK_TF` | `STTS_CD` | `CHECK_USER_NO` | 근거 |
|---|---|---|---|---|---|
| 승인라인 저장 | `REG` | `'F'` | `'10'` | — | 아직 궤도 밖(§7-1) |
| **승인요청** | `DEM` | **`'T'`** | **`'20'`** | **승인요청자** | *"승인 팝업이 접수를 대체한다"* — 레거시 접수 시점에 대응 |
| 중간 승인 | `PROG` | 유지 | 유지 | 유지 | 멱등 |
| 반려 | `REJ` | 유지 | 유지 | 유지 | 되돌리지 않음 |
| 승인완료 | `CMPL` | 유지 | 유지 | 유지 | **`'60'` 금지** — 레거시 궤도 판정에 걸린다(§6-1-e) |
| 요청취소 | → `REG` | 유지 | 유지 | 유지 | 되돌리지 않음 |

###### 접수자는 세션이 아니라 **승인요청자**다 (2026-08-27 정정)

`CHECK_USER_NO` 에 세션 사용자를 넣으면 **처리 시점에 따라 다른 사람이 박힌다.**
`PROG`·`CMPL` 에서도 도는 구조라(아래 참조) `DEM` 을 놓친 회차는 승인 처리자가 접수자가 된다.

> 실측 — `GC001` / `REG_SN 9089` 는 접수자 `66791` 인데 요청자(`TBASE_SANCTN_DEM.RP_USER_NO`)는 `66792` 다.
> 옵션 전환 전에 만들어져 `DEM` 이벤트를 못 받았고, `PROG` 처리 때 채워지면서 승인 처리자가 들어갔다.

**요청순번(`DEM_SN`)으로 요청자를 찾아 넣는다.** 언제 돌아도 같은 값이라 시점 의존성이 사라지고,
*"이 회차를 원청 궤도에 올린 사람"* 이라는 뜻과도 맞는다. 요청을 못 찾을 때만 세션으로 떨어진다.

**`PROG`·`CMPL` 에서도 도는 이유** — `DEM` 한정으로 좁히면 옵션 전환 전에 생성된 회차가 **영영 안 채워진다.**
위 9089 가 그런 회차고, 그러면 §6-1-b 구멍 3건이 그대로 남는다. `Where` 가드로 이미 멱등이라 비용은 0행 `Update` 한 번이다.

###### `MODUSERNO`·`MODDATE` 는 갱신하지 않는다 (2026-08-27 정정)

레거시 `trscRcpt` 는 둘을 갱신하지만 그건 **원청이 접수 버튼을 누른** 명시적 행위였다.
승인 모듈에서는 승인요청의 **부수 동기화**이고, 요청자는 대개 협력사다 —
최종수정자를 협력사 요청자로 덮으면 원청 목록의 *"최종수정자"* 가 오히려 레거시와 달라진다.

> §8-1 이 *"`MODUSERNO` 는 최종수정자라서 원청이 한 번만 수정해도 제출자가 지워진다"* 를 문제 삼았다.
> 같은 덮어쓰기를 우리가 또 하면 자가당착이다. 승인 이력의 시각은 SCNT 테이블이 갖는다.

**되돌리지 않는 이유** — 승인 모듈은 접수취소 개념을 없앴다(`CHK_CANC_PSBL_TF='F'`). 되돌리려면 취소·반려 훅을 새로 열어야 하는데,
레거시에서도 접수 후 반려 상태에서 가져오기가 가능했으므로 *"한 번 승인 궤도에 올랐다"* 를 유지하는 편이 동작과 일관된다.

##### ⚠️ 부수 효과 — 노출 시점이 앞당겨진다 (✅ 수용, 2026-08-27)

이 조치는 결함 해소만 하는 것이 아니라 **회차가 다른 메뉴에 보이기 시작하는 시점 자체를 바꾼다.**

| | 노출 시작 |
|---|---|
| 레거시 | 협력사 제출 → **원청이 접수 버튼**을 눌러야 |
| 승인 모듈 (이 조치 후) | 협력사 제출 → **승인요청만 하면** |

즉 **원청의 확인 행위 없이** 가져오기 · 회의록 · 순회점검 · 안전작업허가 · 운영현황 · 평가결과모니터링에 노출된다.
승인이 나기 전이고 반려될 수도 있는 회차가 이미 잡힌다. 요청취소·반려 후에도 값을 되돌리지 않으므로 계속 남는다.

**검토한 대안 — 노출을 승인완료(`CMPL`)로 미루기**

`syncReceiveState` 를 `CMPL` 에서만 돌리면 *"승인 난 것만 쓴다"* 가 되지만,
**승인 진행 중인 회차가 운영현황·평가결과모니터링에 집계되지 않는다.** 레거시는 접수만 하면 잡혔으므로 후퇴다.

**→ 미루지 않기로 했다.** 승인 모듈에 접수 개념이 없는 이상 승인요청이 *"원청이 받았다"* 에 가장 가까운 시점이고,
이미 선언한 *"승인 팝업이 접수를 대체한다"* 와도 일관된다.

> 📌 **모르고 지나가면 문의가 된다.** *"승인도 안 났는데 왜 가져오기에 뜨나"* 는 결함이 아니라 **의도된 동작**이다.

##### 구현 지점 — `mergeRegisToReceive` 안이 아니라 별도 메서드

§6-1-d 가 제시한 삽입 위치(`RCPT_EXISTS_TF` 분기 안)는 **틀렸다.** 그 분기는 "복사 완료됨" 일 때만 타므로
최초 요청분과 원청 직접작성분(REGIS 없음 → `mRegis == null` 로 조기 return)을 놓친다. 접수 컬럼 갱신은 복사 여부와 무관하다.

```java
@Override
public void onActionApplied(Map<String, Object> amActionData) {
    String sStsCode = Objects.toString(amActionData.get("STEP_STS_CODE"), "");
    if(sStsCode.isEmpty()) return;

    mergeRegisToReceive(amActionData, sStsCode);
    syncReceiveState(amActionData, sStsCode);   // ← 신설
    writeCfmCache(amActionData, sStsCode);
}
```

`syncReceiveState` 는 `REQUESTED_STS`(`DEM`·`PROG`·`CMPL`)일 때만 동작하고, **`CHECK_TF <> 'T'` 인 행만** 갱신한다.
이미 켜진 행은 건드리지 않으므로 멱등이고 불필요한 쓰기도 없다.

```sql
Update TSF_ASSMNT_RECEIVE
Set
    CHECK_TF = 'T',  -- 접수여부
    STTS_CD = '20',  -- 상태코드 <20:접수>
    CHECK_USER_NO = #{SESSION_USER_NO}  -- 접수자
Where 1 = 1
And COMPANY_ID = #{COMPANY_ID}
And PROJ_CODE = #{PROJ_CODE}
And REGIS_SEQ = #{REG_SN}
And Nvl(CHECK_TF, 'F') <> 'T'
```

> `RCPT_TF` 는 `CHECK_TF='T'` 로 자동으로 켜진다(§6-1-d 주). 별도 갱신 불필요.

##### ⚠️ 이 조치로 안 풀리는 곳 — 모니터링 2종

`STTS_CD='20'` 이 **읽는 쪽마다 다른 뜻**으로 쓰인다.

| 읽는 곳 | `'20'` 의 뜻 |
|---|---|
| 가져오기 · 회의록 · 순회점검 | **접수됨 = 쓸 수 있다** |
| 모니터링 `CMPL_CNT` | **완료됨** |

```sql
-- MontInqCompanyRiskAssessmentMonitoringCompanySql 1041, ~PopDetail 989
(Case
    When c.SFAS_OPT_060 = 'T' And a.STTS_CD = '60' Then 1
    When c.SFAS_OPT_060 = 'F' And a.STTS_CD = '20' Then 1   -- ← 060_003 현장이 여기 걸린다
    Else 0
 End) CMPL_CNT
```

레거시에서는 충돌하지 않았다 — `060='T'` 면 완료가 `'60'` 이라 구분되고, `060='F'`(승인 미사용)는 접수가 곧 완료였다.
**060_003 은 "060='F' 인데 승인이 있는" 새 조합이라 이 전제가 깨진다.** 승인요청만 해도 완료로 집계된다.

**모니터링 2종에만 `060_003` 분기를 추가한다.** 29개 중 2개이고, 완료 판정은 `CFM_STS_CODE = 'CMPL'` 로 한다.

```sql
When c.SFAS_OPT_060_003 = 'T' Then Decode(a.CFM_STS_CODE, 'CMPL', 1, 0)
```

> 나머지 27개는 손대지 않는다. `'20'` 을 "쓸 수 있다" 로 읽는 쪽은 승인요청 시점이 맞다.

## 7. 결정 사항 (인터뷰 2026-08-24)

### 7-1. 승인단계 생성 시점 — ✅ 확정

**자동 전환하지 않는다.** 옵션을 켜는 것만으로 기존 회차의 상태가 바뀌는 일은 없다.
누군가 명시적으로 전환해야만 승인 궤도로 올라간다 — 경로는 둘이다.

| 전환 경로 | 누가 |
|---|---|
| 접수화면의 전환 버튼 | 원청 |
| 제출 버튼(= 승인요청) | 협력사 |

> 협력사는 **제출취소를 할 필요가 없다.** 제출 상태에서도 제출 버튼이 승인 팝업을 연다(§7-1-a). 취소는 선택지일 뿐 필수 경로가 아니다.

기본은 소급유지(접수 상태 그대로)이고, 원청이 전환을 실행할 때만 승인라인이 생긴다.
이렇게 읽어야 *"접수분은 소급유지"* 와 *"접수화면에서 승인단계생성"* 이 모순 없이 양립한다.

> 켜는 시점의 회차 셋 중 **둘은 이미 경로가 있다** — §7-1-a 참조.

#### 7-1-a. 회차 상태별 승인 궤도 진입 경로

| 회차 상태 | 원청 목록에 | 협력사 경로 | 원청 경로 |
|---|---|---|---|
| 작성중 (미제출) | 안 보임 (`RECEIVE` 없음) | 승인라인 지정 → 요청 ✅ | — (목록에 없음) |
| 제출 (접수 전) | 미접수 | 그대로 지정 → 요청 ✅ | 전환 버튼 ❌ **신규** |
| 접수 완료 | 접수 | 그대로 지정 → 요청 ✅ | 전환 버튼 ❌ **신규** |

**전환 버튼의 대상은 접수 여부가 아니라 `RECEIVE` 존재 여부다.** 원청 목록에 뜨는 회차는 전부 대상이다 —
승인 모듈에는 접수 개념이 없으므로(`RCPT_BTN_VISIBLE_TF` 가 060_003 이면 항상 `'F'`) 접수를 거칠 이유가 없다.
규칙은 한 줄로 줄어든다 — **제출자가 있으면 요청자에 제출자, 없으면 세션 사용자.**

**소급유지는 원청 화면에서만 적용된다.** 미제출 회차는 `RECEIVE` 가 없어 원청 목록에 뜨지도 않으므로,
원청 화면에 보이는 것은 전부 제출 · 접수분 = 소급유지 대상이다.

**협력사 화면은 승인 어휘를 쓴다** — 060_003 현장이면 `CFM` 유무와 무관하게 승인 상태명이다.

```sql
When a.SFAS_OPT_060_003 = 'T' Then
    (Case When Nvl(a.CFM_STS_CODE, 'REG') = 'REG' Then '요청대기'   -- 승인라인이 없어도
          Else SF_GetCommonCodeName('SANCTN_STS_CODE', a.CFM_STS_CODE) End)
Else
    Decode(a.RECEIVE_TF, 'T', '접수', Decode(a.CHECK_TF, 'T', '제출', '작성중'))
```

그래서 협력사는 제출했든 회수했든 화면에서 `요청대기` 를 보고, 그 자리에서 승인 팝업으로 들어간다.

**제출 상태가 잠기지도 않는다** — `SUB_TF`(협력사 화면의 모든 잠금이 도는 축)는 060_003 현장에서 `CHECK_TF` 를 무시하고 `CFM_STS_CODE` 만 본다.

```sql
(Case
    When a.SFAS_OPT_060_003 = 'T' Then
        Decode(a.CFM_STS_CODE, 'DEM', 'T', 'PROG', 'T', 'CMPL', 'T', 'F')
    Else
        a.CHECK_TF
 End) SUB_TF
```

켜는 시점에 제출돼 있던 회차는 `CFM_STS_CODE` 가 `Null` → `SUB_TF = 'F'` → 편집·승인라인 지정·요청이 그대로 가능하다.
**제출취소 후 재제출은 필요 없다.**

### 7-2. 승인라인 결재자 — ✅ 확정

**표준단계 자동적용** (`cips.sanction.loadStdStep`). 현장에 설정된 표준 승인단계를 그대로 넣는다.
`승인대기` 로 만들어도 결재자가 채워져 있어 바로 진행된다.

> **표준단계 미설정 현장은 존재하지 않는다 (2026-08-27 확인).** 시스템이 최소 하나를 디폴트로 제공하므로 빈 결재자 예외는 성립하지 않는다.

**자동적용 후 손댈 수단이 생겼다 (2026-08-25 구현, §9-2).** 표준단계가 현장 사정과 다를 때 원청이 승인라인을 통째로 교체할 수 있다.
소급 전환으로 만들어진 라인도 마찬가지다 — 자동적용이 틀렸을 때 되돌릴 길이 없다는 제약이 사라졌다.

### 7-3. `승인중` 편집 권한 — ✅ 확정

| 승인 상태 | 수정 가능자 |
|---|---|
| `DEM` 승인대기 | **전원** (레거시 `STTS` 30 과 동일) |
| `PROG` 승인중 | **미처리 단계의 승인자 + 그 단계의 대리인** |
| `CMPL` 승인완료 | 잠금 |

**대리인 포함** — 대리인은 그 단계의 승인 권한을 위임받은 사람이므로 수정 권한도 같이 간다.

**새로 짜지 않는다.** [CommonSanctionSql](../../src/main/resources/sqlmap/mappers/common/CommonSanctionSql.xml) 이 이미 `TBASE_SANCTN_DEM_STEP_AGT`(단계별 대리인)를 포함해 처리 가능자를 판정한다(`SANCTN_PSBL_TF`).
그 판정에서 **"현재 그룹" 조건만 풀면 "현재~이후"** 가 된다.

### 7-4. 제출자 저장 단위 — ✅ 확정

**회사ID + 사용자번호 쌍.** 표준 승인모듈이 `SANCTNER_COMPANY_ID` + `SANCTNER_USER_NO` 쌍으로 다루고 `SFCC_GET_USER_NM` 도 쌍을 키로 쓴다. 요청자로 넣을 때 그대로 쓸 수 있다.

### 7-5. 소급 경계 — ✅ 확정

**제출자 컬럼(`SUB_*`)의 값 유무로 가른다.** 옵션 적용일시(`SFAS_OPT_060_003_DTTM`) 컬럼은 **추가하지 않는다.**

핫픽스 이전 데이터는 전부 제출자가 없어 자연히 소급유지로 떨어진다. 별도 시점 관리가 필요 없다.

> 대가: 핫픽스~9/22 사이에 제출된 건은 제출자가 있어 승인 궤도로 분류된다. 이 구간의 모호함을 수용한다.

**궤도 플래그 컬럼은 두지 않는다.** 자동 변환을 없앤 이상 `CFM_DEM_SN` 유무가 곧 궤도다.
폐기(§5) 후 남는 `STS_NAME` 분기는 전부 `CFM_*` 기반이고, `SFAS_OPT_060_003` 참조는
**레거시 30~60 을 승인 어휘로 보여줄지** 한 곳에만 남는다. 옵션을 껐다 켜도 회차 표시가 흔들리지 않는다.

> 🔎 **`CFM_DEM_SN` = 궤도 판정은 추가 확인 대기 (2026-08-26).** 방향은 유효하나 확정 전 확인이 남아 있다.
> §5-1 의 미이행 2건(`fnIsScntRow`·`UPD_PSBL_TF`)이 아직 `SFAS_OPT_060_003` 만으로 궤도를 판정하고 있어,
> **"`CFM_DEM_SN` 유무가 곧 궤도"는 문서상 확정이지 코드상 사실이 아니다.** 두 지점을 정리해야 이 절이 성립한다.

### 7-6. 백필 오분류 — ✅ 확정

**무시한다.** §4-3 의 판별불가 3,768건(1%)은 보정하지 않는다.

`CRTUSERNO` 가 없거나 사용자 정보가 안 잡히는 건은 정상 흐름으로 만들어진 데이터가 아니다 —
개발자가 수동으로 넣은 데이터일 가능성이 크다. 보정 비용 대비 실익이 없다.

### 7-7. 소급분 전환 방식 — ✅ 확정

**A(원청 버튼) + B(협력사 경로) 병행.** B 는 이미 동작하므로 A 만 신규 구현한다.

#### 7-7-a. 전환은 '제출(=승인요청)' 버튼으로 일어난다 — 취소가 아니다

060_003 현장에서는 협력사 화면의 두 버튼이 모두 승인 팝업으로 리매핑돼 있다.

| 버튼 | 060_003 현장에서의 동작 |
|---|---|
| 제출 | **승인 팝업 → 승인라인 지정 → 승인요청** ← 전환 지점 |
| 취소 | 승인 팝업 → 요청취소. 소급 회차는 취소할 요청이 없어 할 일이 없다 |

```js
scwin.wbtnSend_onclick = function(e) {
    // [승인 모듈 분기] 제출 = 승인요청. 승인라인 지정·요청은 팝업이 담당한다.
    if(wdlAsmt.getCellData(wdlAsmt.getRowPosition(), "SFAS_OPT_060_003") == "T") {
        scwin.openSanctnPopup();
        return;
    }
```

`SUB_TF` 가 `CHECK_TF` 를 무시하고 `CFM_STS_CODE` 만 보므로(§7-1-a) **원청이 접수를 끝낸 뒤에도** 제출 버튼이 살아 있다.
위 분기가 맨 앞에서 팝업을 열고 반환하므로 레거시의 `RCPT_TF` 차단(*"건설사에서 접수하여 제출을 취소할 수 없습니다"*)도 타지 않는다.

> **제출취소·삭제 후 재작성은 어느 유형에서도 필요 없다.**

#### 7-7-b. 원청 직접작성분도 협력사 화면에 보인다

`insertAsmt` 가 `TSF_ASSMNT_REGIS` 를 함께 만들고(§8-1), 협력사 화면은 그 REGIS 를 조회한다.
따라서 **두 유형 모두 협력사가 승인요청할 수 있다** — 원청 작성분에 경로가 없는 게 아니다.

#### 7-7-c. 그럼 원청 버튼(A)이 왜 필요한가

| | |
|---|---|
| ❌ 아님 | "원청 작성분은 협력사 경로가 없어서" |
| ✅ 맞음 | **"원청이 접수까지 끝내 협력사가 손 뗀 건을, 아무도 안 올리는 상태로 두지 않기 위해"** |

즉 A 는 **경로 신설이 아니라 안전망**이다. 요청자 기록도 갈린다.

| 누가 올리나 | 요청자 |
|---|---|
| 협력사가 제출 버튼 (B) | 협력사 세션 사용자 |
| 원청이 전환 버튼 (A) | §3-3 규칙 — 제출자 있으면 제출자, 없으면 세션 사용자 |

### 7-8. 검토의견 검증 시점 — ✅ 확정

**최종 승인 직전에 한 번, 전체를 검증한다.**

단계별로 나눠 검증할 수 없다 — 승인라인은 현장이 자유롭게 구성하므로 **승인 단계와 검토의견 컬럼이 매핑되지 않는다.**
"이 단계 사람이 쓸 의견" 을 특정할 방법이 없으므로 단계별 본인 의견 검증은 성립하지 않는다.

| 시점 | 검증 |
|---|---|
| 승인요청(`REG` → `DEM`) | 하지 않음 |
| 중간 단계 승인 | 하지 않음 |
| **최종 승인(→ `CMPL`)** | **옵션 `060_001`·`060_002`·`092` 기준 전체 검증** |

> **수용하는 대가**: 최종 승인자가 앞 단계 승인자의 미작성 때문에 막힐 수 있다.
> 대안(각 단계 본인 의견만 검증)은 위 매핑 문제로 구현 불가라, 이 방식이 유일하게 성립한다.

구현 지점은 `SfasAtRiskasmtSanctionHandler` 다. 현재 `validateBeforeDemand` 가 TODO 스텁인데,
**요청 시점이 아니라 최종 승인 시점 훅으로 옮겨야 한다.**

#### 7-8-1. 왜 옮겼나 — 게이트가 문 한 짝에만 걸려 있었다 <sub>(2026-09-02 발견 · 같은 날 이행)</sub>

옮기기 전에는 **두 팝업이 서로 다르게 동작했다.**

| | 원청 팝업 | 협력 팝업 |
|---|---|---|
| 종합의견 게이트 `fnValidateSynthOp` | 있음 (요청 시점) | 없음 |
| 항목별 게이트 `fnValidatePerItemCmt` | 있음 (요청 시점) | 없음 |
| 최종 승인 시점 검증 | 없음 | 없음 |

**결과** — 같은 평가서라도 **협력사가 요청하면 검토의견 없이 승인완료까지 갔다.** 원청이 요청할 때만 막혔다.

협력 팝업에 요청 시점 게이트를 다는 것은 답이 아니다. **검토의견을 쓸 수 있는 쪽은 원청뿐**이고(협력 화면은 검토의견 그리드가
`oReadOnlyColumns:["ALL"]`), 협력사가 요청하는 순간이 원청이 그 회차를 **처음 보는** 시점이다(요청 = 제출 = `mergeRegisToReceive`).
없는 것을 검사하라는 셈이라 영구 차단이 된다. §7-8 의 최종 승인 시점이 두 짝을 동시에 닫는 유일한 지점이다.

> ⚠️ **가정도 틀렸었다** — *"092=T 라 이 경로는 미발현"* 이라던 기록과 달리,
> `060_003='T'` 5개 현장 중 **A0001·UT001·GC001·R2353 이 `092='F'` + `060_001='B'`** 다.

#### 7-8-2. ✅ 구현 (2026-09-02)

**코어가 완료로 판정한 다음에 게이트를 태우고, 막으면 예외로 승인 자체를 되돌린다.**
"이번 승인이 마지막인가" 를 훅이 되짚지 않는다 — 병렬 그룹·전결 때문에 완료 시점이 달라지는데 그 판정은 `actSanction` 소관이다.

| 파일 | 변경 |
|---|---|
| `CommonSanctionTargetHandler` | `validateBeforeComplete` 외 **훅 5종 신설**(아래 §7-8-3) |
| `CommonSanctionBridgeServiceImpl` | 훅 5종 호출부 배선 + `fireAfterAction(.., abFromAction)` |
| `SfasAtRiskasmtSanctionHandler` | `validateBeforeComplete` 구현 + `gateError` 헬퍼 / `validateBeforeDemand` 빈 스텁 **제거** |
| `SfasAtRiskasmtSanctionHandlerSql` | `selectRvwOpChk` 신설 |
| `SfasPopRegRiskAssessmentRcptConfirm` | 요청 시점 게이트 3함수·데이터셋 2·서브미션 1·옵션 2컬럼 **제거** |

**호출 순서** — 게이트는 `onActionApplied` **다음**이다.

```
actSanction  →  STEP_STS_CODE  →  onActionApplied(merge·syncReceiveState)  →  ★validateBeforeComplete  →  onCompleted
```

앞에 두면 협력 제출분의 접수본이 아직 없어 검사 대상이 0건이 되고, **그 0건이 통과로 읽힌다.**
같은 트랜잭션(`rollback-for="Exception"`)이라 게이트가 막으면 복사·상태갱신·승인이 함께 되돌아간다.

**판정 규칙** — 옵션은 화면 값이 아니라 `TCC_PROJ_CODE` 에서 직접 읽는다.

| 092 | 060_002 | 060_001 | 검사 | 막힐 때 문구 |
|:--:|:--:|:--:|---|---|
| `T` | `T` | — | `SYNTH_CONSTR_OP`·`SYNTH_SAF_OP` 둘 다 | 공사팀장·안전팀장 검토의견을 모두 입력해야 승인을 완료할 수 있습니다. |
| `T` | `F` | — | **없음** | — |
| `F` | — | `A` | **없음** | — |
| `F` | — | `B` | 전 항목 | 등록되지 않은 검토의견이 있습니다. |
| `F` | — | `C` | `PRIORITY='O'` 항목만 | 〃 |

> `092='T'` + `060_002='F'`(HT0001)는 **원래도 게이트가 없었다.** 옮기면서 새로 막지 않았다.

##### ⚠️ 문구가 화면에 뜨는 경로 — `[NOTICE] ` 접두사가 없으면 조용해진다

`common.js` `com.resultMsg` 는 업무오류(`errorCode='E9999'`)일 때 **`rsMsg.message` 를 안 쓴다.**
`messageDetail` 안에서 `ORA-20009` 또는 **`[NOTICE] `** 를 찾아 그 뒤쪽만 잘라 `com.alert(..., "warn")` 한다.
둘 다 없으면 **아무 창도 안 뜬다** — 예외는 나고 롤백도 되는데 사용자는 아무것도 못 본다.

#### 7-8-3. 공통 훅 5종 신설 (2026-09-02)

승인 모듈은 재사용 표준이므로, **브리지의 코어 호출 지점을 전수로 훑어 훅이 없는 자리를 메웠다.** 전부 `default {}` 라 동작 변화는 0이다.

| 훅 | 브리지 호출 위치 | 쓸 자리 |
|---|---|---|
| `onDemandUpdated` | `updateDemand` 끝 | 단계 구성을 자기 테이블에 캐시하는 모듈의 갱신 |
| `validateBeforeAction` | `actSanction` **전** | 반려 의견 필수, 특정 호스트 상태에서 승인 금지 |
| `validateBeforeCancel` | `cancelSanction` **전** | *"원청이 접수한 회차는 요청취소 불가"* 같은 호스트 제약 |
| `onRejected` | `REJ` 확정 후 | `onCompleted` 의 짝. 승인 흐름의 종착점 둘 중 반려에만 훅이 없었다 |
| `onFlagsLoaded` | `loadStatus` 플래그 산출 후 | 코어 버튼 플래그를 도메인이 **더 좁힐** 자리 |

**결정 두 가지**

- **빈 훅만 두지 않는다.** 호출부 없는 훅은 거짓말이라 5개 모두 브리지에 배선했다(훅 14개 ↔ 호출부 14개 대조 완료).
- `fireAfterAction` 의 두 번째 인자를 `abGateOnComplete` → **`abFromAction`** 으로 바꿨다. 완료 게이트와 `onRejected` 가 같은 조건(승인/반려 액션에서 온 호출)을 쓰기 때문이다.
  **취소로 상태가 `CMPL`·`REJ` 가 된 것은 종착이 아니라 되돌림**이므로 둘 다 타지 않는다.

> `onFlagsLoaded` 는 **넓히는 용도가 아니다.** 코어가 `'F'` 준 것을 `'T'` 로 되돌리면 권한 판정을 우회한다.
> 그리고 버튼을 감추는 것과 액션을 막는 것은 다르다 — 실제 차단은 `validateBeforeAction/Cancel` 이 해야 한다(단축키·직접 호출).

---

**사내 규약이 이미 이걸 처리한다** — `throw new <모듈>Exception("문구", true)`.
두 번째 인자 `abNoticeToUser` 가 `"[NOTICE] "` 를 접두하고, Controller 의 기존 `catch (Exception)` 이
`setMsg(STATUS_ERROR, .., e)` 로 예외를 3번째 인자에 실으면 `messageDetail` 이 채워져 화면에 뜬다.
`CommonException`·`PointException`·`SfasException` 등 **19곳**이 이미 이 방식이고, **도메인 예외를 따로 잡는 Controller 는 하나도 없다.**

> ⚠️ 첫 구현에서 전용 예외 클래스(`CommonSanctionGateException`)와 전용 catch 를 새로 만들었다가 **되돌렸다.**
> 규약을 세어보지 않고 만든 중복이었다.

**발생 위치를 남긴다** — 핸들러의 `gateError(문구)` 헬퍼가 메시지를 이렇게 만든다.

```
[SFAS Exception] [SfasAtRiskasmtSanctionHandler.validateBeforeComplete] [NOTICE] 등록되지 않은 검토의견이 있습니다.
 └ 모듈 태그(고정)   └ 발생 위치(스택에서 읽음)                          └ 노출 토큰  └ 사용자가 보는 부분
```

- 위치는 **스택에서 읽는다**(`new Throwable().getStackTrace()[1]`). 문자열로 적으면 메서드명을 바꿀 때 안 따라와 로그가 거짓말을 한다.
- 위치는 반드시 `[NOTICE] ` **앞**이다. 뒤에 두면 사용자 화면에 클래스명이 그대로 노출된다.
- `[NOTICE] ` 는 **지울 수 없다.** 장식이 아니라 `com.resultMsg` 의 표시 트리거다.

기존 `ORA-20009` 문구(*"승인권한이 없습니다"* 등)가 화면에 뜨는 것도 같은 함수의 다른 분기다.

**남는 자국** — 팝업 컨트롤러 `SfasPopRegRiskAssessmentRcptConfirmController.selectCdRvwOpChkList` 는 이제 호출부가 없다.
같은 쿼리를 외곽 `SfasRegAtRiskasmtRcpt`(레거시 060 경로)가 자기 엔드포인트로 쓰고 있으므로 서비스·매퍼·SQL 은 그대로 두고,
**팝업 쪽 엔드포인트만 죽은 채로 남겼다**(삭제는 영향 범위가 달라 별건).

### 7-10. 노출 시점을 미루지 않는다 — ✅ 확정 (2026-08-27)

접수 컬럼을 **승인요청 시점에** 기록하므로(§6-1-f), 회차가 다른 메뉴에 보이는 시점이 **레거시보다 앞당겨진다.**

| | 노출 시작 |
|---|---|
| 레거시 | 원청이 **접수 버튼**을 눌러야 |
| 승인 모듈 | 협력사가 **승인요청만 하면** |

**수용한 대가** — 승인 전이고 반려될 수도 있는 회차가 가져오기 · 회의록 · 순회점검 · 안전작업허가 ·
운영현황 · 평가결과모니터링에 **원청의 확인 행위 없이** 노출된다. 요청취소·반려해도 되돌리지 않으므로 계속 남는다.

**대안을 검토했다** — `CMPL` 에서만 기록하면 *"승인 난 것만 쓴다"* 가 되지만,
승인 진행 중인 회차가 운영현황·모니터링에 **집계되지 않아** 레거시보다 후퇴한다. 그래서 미루지 않는다.

> 📌 *"승인도 안 났는데 왜 가져오기에 뜨나"* 는 **결함이 아니라 의도된 동작**이다. 문의가 오면 이 절을 근거로 답한다.

## 8. 결정 → 기존 프로세스 반영 매핑

공유받은 결정 3건이 **기존 어느 로직에 꽂히고, 무엇이 바뀌는지**를 지점별로 적는다.

### 8-1. 제출자 관리

> 웹, 모바일 핫픽스로 해서 최대한 빠른 시점으로 수정하여 배포 진행

**꽂히는 지점** — 회차를 만드는 두 경로 전부. 웹·모바일 대칭이라 6곳이다.

**AS-IS**

제출자를 담는 컬럼이 없다. 협력사가 제출하면 `trscSub` 의 `Merge` 가 `MODUSERNO = #{SESSION_USER_NO}` 만 갱신한다.
`MODUSERNO` 는 **최종수정자**라서 원청이 접수 후 한 번만 수정해도 제출자가 지워진다.

```sql
When Matched Then
Update Set
    MODUSERNO = #{SESSION_USER_NO},   -- 제출자가 여기 남지만 곧 덮어써진다
    MODDATE = SYSDATE,
```

그래서 접수된 회차를 놓고 **"이건 협력이 제출한 건가, 원청이 만든 건가"** 를 물으면 답할 방법이 없다.
`REGIS` 유무·`REGIS.CHECK_TF` 모두 판별력이 없다(§4-1 실측).

**TO-BE**

`TSF_ASSMNT_REGIS`·`TSF_ASSMNT_RECEIVE` 에 제출자 컬럼(`SUB_COMPANY_ID`·`SUB_USER_NO`)을 신설하고, 8곳에서 채운다.

| 경로 | 넣는 값 | 의미 |
|---|---|---|
| 협력 제출 (웹·모바일 `Merge` ×4) | 세션 사용자 (`SUB_*`) | 제출자 있음 → 유형 **D** |
| 원청 직접작성 (웹·모바일 `Insert` ×2) | **넣지 않음(`Null`)** | 제출자 없음 → 유형 **C** |

**이게 바꾸는 것** — §3-3 의 편입 규칙(`제출자 있음 → 승인대기` / `없음 → 요청대기`)이 비로소 성립한다.
이 컬럼 없이는 §3-3 을 구현할 수 없으므로 **모든 후속 작업의 선행**이다. 그래서 핫픽스다.

> 핫픽스 이전 데이터는 제출자가 영구히 없다 → `CRTUSERNO` 백필(§4-3)로 메우고, 못 메우는 1% 는 유형 C 로 떨어진다.

### 8-2. 문서 수정 권한

> 승인대기: 모든 내용 수정가능 (기존 공사팀장승인대기와 동일)
> 승인중: 기존 60번 프로세스를 따라 현재~이후 승인가능한 사람들 모두에게 문서 수정권한 제공

**꽂히는 지점** — `SfasRegAtRiskasmtRcptSql.selectAsmtList` 의 `UPD_PSBL_TF`(수정가능여부) Case.
화면 잠금(`fnCheckEditLock`)과 `readOnly` 는 이 값을 읽으므로 여기만 고치면 따라온다.

**AS-IS** — 승인 모듈은 요청 이후를 **통째로 잠근다.**

```sql
When a.STTS_CD = '30' Then 'T'                                       -- 레거시: 공사팀장 승인 전 → 전원 허용
When (060 Or 060_003) And a.STTS_CD In ('40','50','60') Then         -- 레거시: 자기 차례 결재자만
    (Case When a.APPRV_C_USER_NO  = #{SESSION_USER_NO} And Nvl(a.APPRV_C_TF, 'F')  = 'F' Then 'T'
          When a.APPRV_BD_USER_NO = #{SESSION_USER_NO} And Nvl(a.APPRV_BD_TF, 'F') = 'F' Then 'T'
          When a.APPRV_A_USER_NO  = #{SESSION_USER_NO} And Nvl(a.APPRV_A_TF, 'F')  = 'F' Then 'T'
          Else 'F' End)
When a.CFM_DEM_SN Is Not Null And a.CFM_STS_CODE In ('DEM','PROG','CMPL') Then 'F'   -- ← 여기가 바뀐다
When a.CFM_DEM_SN Is Not Null Then 'T'                               -- REG(요청대기)·REJ(반려) → 허용
```

즉 **승인요청을 하는 순간 아무도 못 고친다.** 고치려면 요청취소로 `REG` 까지 되돌려야 한다.
레거시(060)는 `STTS` 30 에서 전원 허용, 40~60 에서 자기 차례 결재자 허용이었는데 — **승인 모듈이 더 빡빡했다.**

**TO-BE** — 레거시와 같은 관대함으로 맞춘다. 세 상태를 갈라야 한다.

| 승인 상태 | AS-IS | TO-BE | 대응하는 레거시 상태 |
|---|---|---|---|
| `DEM` 승인대기 | 잠금 | **전원 허용** | `STTS` 30 공사팀장승인대기 |
| `PROG` 승인중 | 잠금 | **현재~이후 단계 승인자** | `STTS` 40~60 자기 차례 결재자 |
| `CMPL` 승인완료 | 잠금 | 잠금 (유지) | `STTS` 60 |

**이게 바꾸는 것**

- `In ('DEM','PROG','CMPL')` 한 덩어리를 **세 분기로 분해**한다.
- `PROG` 분기는 레거시처럼 컬럼 3개를 보는 게 아니라 **승인단계 테이블을 조회**해야 한다 — 단계 수가 고정이 아니기 때문. 레거시의 `APPRV_C/BD/A_USER_NO` 3열 비교와 구조가 다르다.
- 판정이 SQL 안에서 무거워지므로 [TODO_EDIT_TF_JS이관.md](./TODO_EDIT_TF_JS이관.md)(EDIT_TF 를 JS 로 옮기는 백로그)와 **충돌 검토가 필요**하다.

> `PROG` 의 "현재~이후" 범위는 §7-3 확정 — 미처리 단계의 승인자 + 그 단계의 대리인.

### 8-3. 승인모듈 미사용 → 사용 시 기존 데이터 처리

> 제출취소 후 작성중 상태로 돌아가서 협력사에서 승인이력 생성 (현재 되고 있는 기능)
> 접수상태일 때 접수화면에서 승인단계생성 하도록 처리

기존 회차를 **제출 전 / 접수 후** 로 나눠 다르게 처리한다.

#### ① 제출 전 회차 — 기존 기능 그대로 (작업 없음)

협력사가 제출취소하면 `REGIS.CHECK_TF = 'F'` 가 되어 협력사 화면에서 `작성중`(레거시 어휘, §1-A)으로 돌아간다.
거기서 협력사가 승인라인을 만들고 승인요청하면 정상적으로 승인 궤도에 올라탄다.

**협력사 화면(`SfasRegAtRiskasmtSub`)의 SCNT 배선이 이미 되어 있어 추가 작업이 없다.**

#### ② 접수 상태 회차 — 접수화면에서 승인단계 생성 (신규)

**AS-IS**

옵션을 켜면 무라인 회차는 **표시만 바뀌고 승인라인은 안 생긴다.** 사용자가 승인 팝업을 열어 직접 만들어야 한다.

```sql
When d.SFAS_OPT_060_003 = 'T' Then '요청대기'   -- 라인 없이 상태명만
```

이미 접수까지 끝난 회차인데 승인 관점에서는 **아무것도 시작되지 않은 상태**로 남는다.
협력사가 실제로 제출했던 건도 원청이 새로 요청해야 해서, 승인이력에 "누가 올린 건지"가 사라진다.

**TO-BE**

접수화면에서 승인단계를 생성하고, **제출자 유무로 요청자와 시작 상태를 가른다.**

| 조건 | 요청자 | 시작 상태 | 근거 |
|---|---|---|---|
| 제출자 있음 (유형 **D**) | **제출자** | `승인대기`(`DEM`) | 협력이 이미 제출 = 요청 행위가 있었다 |
| 제출자 없음 (유형 **C**) | **세션 사용자** | `요청대기`(`REG`) | 원청이 만든 건 = 아직 요청 행위가 없다 |

**이게 바꾸는 것**

- 상태명 산출이 **표시 로직에서 데이터로** 옮겨간다. `STS_NAME` 의 `060_003` 분기가 필요 없어지고, 생성된 `CFM_STS_CODE` 를 그대로 읽으면 된다(유형 A 로 흡수).
- **2026-08-21 에 넣은 `RCPT_DRCT_TF` 분기·`fnIsScntRow` 변경이 폐기된다**(§5). 그 구현은 "라인을 안 만들고 표시만 바꾸는" 전제였다.
- 승인이력에 제출자가 요청자로 남아 **감사 추적이 실제 행위와 일치**한다.

> `승인대기` 로 만들 때 결재자는 §7-2 의 표준단계 자동적용으로 채워진다. 표준단계 미설정 현장은 존재하지 않으므로 빈 결재자로 멈추는 경우는 없다.

### 9-5. 빈 저장이 동적 submission 을 무너뜨린다 (2026-08-27 조치)

**증상** — 승인 팝업에서 **저장할 것이 없는 상태**로 저장 버튼을 누르면 콘솔에 에러가 났다.

```

개발자 정의 함수 호출 에러 / message: Cannot read properties of null (reading 'action')
```

**원인** — 호출 사슬의 끝인 [`com.executeSubmission_dynamic`](../../src/main/webapp/js/websquare/common.js) 에 **null 가드가 없다.**

```js
var submissionObj = $p.getSubmission(options.id);
if (submissionObj === null) { com.createSubmission(options); submissionObj = $p.getSubmission(options.id); }
else { $p.deleteSubmission(options.id); com.createSubmission(options); submissionObj = $p.getSubmission(options.id); }
com.executeSubmission(submissionObj, requestData, obj);   // ← null 이면 여기서 .action
```

submission 생성이 실패하면 그대로 넘겨 `.action` 을 읽는다. **LOV 종료 콜스택 문제(§9-2 주)와 같은 함수·같은 실패**다.

**진짜 결함은 그 위**였다. 팝업의 `save.onClickBefore` 가 변경분 유무와 무관하게 `fnSave()` 를 호출했다.

```js
} else {
    oGwin.scwin.fnSave();   // 변경 없음 — 신규 승인요청 생성 등은 그대로 진행
}
```

승인라인을 새로 만드는 경우를 살리려던 분기인데, **정말 아무것도 없는 상태**까지 저장을 태웠다.

**조치 — 양쪽에 넣었다.**

| 위치 | 내용 |
|---|---|
| `CommonWFrameSanctnGrid` | `fnCanSave()` 신설 — 미저장 변경분이 있거나, 아직 만들어지지 않은 승인라인(`DEM_SN` 없음)에 단계가 있을 때만 참 |
| 〃 | `fnSave()` 진입 가드 — `단계 0건 && 삭제분 0건` 이면 중단 |
| 승인 팝업 2종 | `fnCanSave()` 가 거짓이면 안내 후 반환 — 저장을 태우지 않는다 |

> 가드에서 **삭제분(`aoDelStep`)을 함께 보는 이유** — 승인라인변경으로 기존 단계를 전부 걷어내면 그리드는 0건이지만
> 삭제분이 대기 중이라 저장이 필요하다. 행 수만 보면 그 경로가 막힌다.
>
> ✅ **2026-08-27 확인 완료** — 빈 저장 차단 · 승인자 미지정 경고 · 정상 저장 · **승인라인 전체 교체 후 저장** 네 경로 모두 정상.

```js
for(const oPopup of $p.getAllPopupList()) { ... return; }             // 메시지창 활성

```

`getActiveWindowInfo()` 는 모달 팝업을 활성 창으로 돌려주므로 **팝업에서도 단축키가 정상 도달**한다.
단축키로 에러가 안 났던 것은 위 게이트에 걸려 **저장이 시작조차 안 됐기 때문**이지, 경로가 달라서가 아니다.

### 9-8. 소급 회차를 접수 흐름으로 되돌림 (작업 #9, 2026-08-27)

|---|---|
| `fnIsScntRow` 마지막 줄 | `return bUseOpt060003 === true` → **`CFM_DEM_SN` 유무만** 본다 |
| `selectAsmtList` `STS_NAME` | `When d.SFAS_OPT_060_003 = 'T' Then '요청대기'` 분기 **제거** → `접수`/`미접수` 로 떨어짐 |
| `UPD_PSBL_TF` 의 `060_003 → 'T'` | **유지**(폐기하지 않음) — 아래 참조 |

`fnIsScntRow` 한 줄이 6군데로 퍼진다. 상태명 링크·클릭 핸들러·승인 컬럼 표시 집계·잠금 안내·레거시 판별이 전부 접수 흐름으로 돌아간다.
**부수 효과로 현장소장의견이 외곽 그리드에서 다시 편집 가능해진다** — 소급 회차는 레거시 흐름이므로 일관되며, 의도한 동작으로 수용했다.

> ⚠️ **`UPD_PSBL_TF` 는 폐기하지 않는다 (2026-08-27 결정).** §9-4 는 둘 다 폐기하라고 적었지만,
> 폐기하면 미접수 회차가 원청에게 잠긴다. **미접수·접수 모두 `승인대기` 와 같은 편집 권한으로 본다** — 협력이 제출한 이상 요청이 있었던 것으로 보기 때문이다.
> §2-3 의 *"`승인대기` = 모든 내용 수정 가능"* 과 같은 선이다.

#### 협력사 화면 (`SfasRegAtRiskasmtSub`)

원청만 고치면 반쪽이다. `SUB_TF` 가 `CHECK_TF` 를 무시하고 `CFM_STS_CODE` 만 봐서,
**원청이 접수 완료한 회차도 협력사가 다시 편집·재제출할 수 있었다.** 상태명도 `요청대기` 로 떠서 원청 화면과 어긋났다.

**규칙 — 아무 프로세스도 진행하지 않은 회차만 옵션에 맞춘다.**

| 회차 | 상태명 | `SUB_TF` | 승인 팝업 |
|---|---|---|---|
| 승인라인 있음 | 승인 상태명 | `CFM_STS_CODE` 파생 | ✅ |
| **미제출** (아무 프로세스 없음) | **`요청대기`** | `'F'` (열림) | ✅ 제출 = 승인요청 |
| 제출 · 접수된 소급 회차 | **`제출`/`접수`** | `CHECK_TF` (잠김) | ❌ 원청 전환 버튼으로만 |

| 지점 | 변경 |
|---|---|
| `SfasRegAtRiskasmtSubSql` `SUB_TF` | `060_003='T'` **And `CFM_DEM_SN Is Not Null`** 일 때만 승인상태 파생 |
| 〃 `STS_NAME` | `060_003='T'` **And (`CFM_DEM_SN` 있음 **또는** 미제출)** 일 때만 승인 어휘 |
| `SfasRegAtRiskasmtSub` | `scwin.fnIsScntRow` 신설(원청판의 협력사 버전). 상태명 링크·클릭·제출·취소 4곳이 옵션 대신 이 함수를 본다 |

> **남은 것** — 제출/취소 버튼 라벨은 현장 단위 1회 세팅이라 회차별로 갈리지 않는다.
> 소급 회차는 레거시 제출취소로 도는데 라벨은 `요청취소` 로 뜬다. 행 선택마다 갱신하려면 별도 훅이 필요하다. **미결**

#### 요청 단계 대리인 — ✅ 확정 (2026-08-27)

전환 시 요청자를 제출자로 넣으면 `DEM` 단계 승인자가 협력사가 되어 **원청이 요청 버튼을 못 누른다**
(`CommonSanctionSql` 76행이 요청 단계 승인자를 요청자로 배정한다).

**대리인에는 승인전환 버튼을 누른 세션 사용자를 넣는다.** 요청 명의는 협력사(제출자), 실행 권한은 원청 담당자다.
실제로 누른 사람은 요청 단계의 `ACT_USER_NO` 에 남으므로 *"협력 명의로 요청되었고 원청 아무개가 실행했다"* 가 그대로 기록된다.

### 9-9. 설계 감사 (2026-08-28)

소급 회차 처리를 넣은 뒤 규칙끼리 부딪히는 지점을 전수로 훑었다. **결함 4건 + 편집권한 완화(작업 #6)** 를 반영했다.

#### ① 협력사 화면이 옵션을 먼저 봤다 — 규칙 위반

§3-2 는 *"승인 모듈 → 미사용/060 전환 시 승인건이 있는 회차는 승인 상태명 유지"* 로 정했는데,
협력사 판별식이 `060_003` 을 먼저 봐서 **옵션을 끄면 협력사 화면만 레거시로 돌아갔다.** 원청 화면은 `CFM_DEM_SN` 만 보므로 두 화면이 어긋난다.

| 지점 | 변경 |
|---|---|
| `SfasRegAtRiskasmtSubSql` `SUB_TF` | `060_003` 조건 제거 — `CFM_DEM_SN Is Not Null` 만 본다 |
| 〃 `STS_NAME` | `CFM_DEM_SN Is Not Null` **Or** (`060_003='T'` And 미제출) |
| `SfasRegAtRiskasmtSub` `fnIsScntRow` | 승인건 검사를 옵션 검사보다 **앞으로** |

#### ② 승인 궤도인데 원청 목록에서 빠졌다

원청 목록 필터는 접수본이 아니라 **제출본**의 제출여부를 본다. 접수본이 이미 있으면 `mergeRegisToReceive` 가 복사를 건너뛰므로
협력이 제출취소했던 회차를 승인 궤도에 올리면 **제출본이 회수 상태로 남아 원청이 못 본다.**

```sql
And (Nvl(b.CHECK_TF, 'T') = 'T' Or a.CFM_DEM_SN Is Not Null)
```

> 승인건이 없는 회차는 예전 그대로다 — 협력이 회수하면 원청 목록에서 빠진다(수용).

#### ③ 소급 회차의 제출본 제출여부가 `'F'` 로 남았다

승인 모듈에서 **승인요청은 곧 제출**이므로 제출본 `CHECK_TF` 도 `'T'` 여야 한다.
신규 흐름은 `mergeRegisToReceive` → `trscSub` 이 올려주지만, 접수본이 있는 소급 회차는 복사를 건너뛰어 `'F'` 로 남는다.
②의 필터로 증상은 막았지만 신규분과 데이터 모양이 갈리므로 `updateRegisSubmitted` 를 신설해 근본을 맞췄다.

> 요청취소·반려에도 되돌리지 않는다 — 접수 컬럼과 같은 원칙(§6-1-f).

#### ④ 전환 직후 `REG` 구간에 협력사가 열린다 — 미구현 구간

`SUB_TF` 는 `REG` 를 열린 상태로 본다(승인 모듈 본래 동작). 전환 버튼이 승인라인 저장까지만 하면 그 상태가 되므로
**접수 완료 회차를 전환한 직후 협력사 화면이 다시 열린다.**

전환 시작 상태를 `승인대기` 로 만드는 작업(§9-8 남은 일)이 닫는다. **요청 실패 시 승인라인을 롤백**해야 어정쩡한 상태가 안 남는다.

#### ⑤ 편집권한 완화 (작업 #6)

`UPD_PSBL_TF` 의 `In('DEM','PROG','CMPL') → 'F'` 한 덩어리를 셋으로 분해하고, **승인 분기를 레거시 분기보다 앞에** 뒀다
(`STTS_CD` 30 + 승인라인 조합이 실재하므로).

> **결과는 [승인_현재동작.md §4 편집](./승인_현재동작.md) 이 정본이다.**
> `PROG` 를 *"미처리 단계의 승인자 + 대리인"* 으로 잡은 것은 레거시 40~60 의 *"자기 차례 결재자"* 를 다단계로 옮긴 것이고,
> `DEM` 을 연 것은 레거시 `STTS` 30(결재 착수 전)과 같은 성격이기 때문이다(§7-3).

`PROG` 판정은 새로 짜지 않았다 — 코어(`CommonSanctionSql.SANCTN_PSBL_TF`)가 세션 사용자의 단계로 이미 좁혀 판정하는데,
거기서 **현재 그룹 조건만 풀면 "현재~이후"** 가 된다. 미처리 단계(`ACT_CODE Is Null`)는 정의상 현재 진행 그룹 이상이므로
그룹번호 비교 자체가 필요 없어져 조건이 단순해졌다.

```sql
And s.STEP_SECT_CODE <> 'DEM'   -- 요청 단계는 결재가 아니다
And s.ACT_CODE Is Null          -- 미처리
And (s.SANCTNER_USER_NO = #{SESSION_USER_NO} Or Exists (... TBASE_SANCTN_DEM_STEP_AGT ...))
```

> **실측 검증 (GC001)** — `PROG` 9097 은 `'T'`(해당 사용자가 미처리 단계 승인자), 9089 는 `'F'`(남은 단계 승인자가 아님).
> `CMPL` 은 미처리 0건이라 자연히 `'F'` 다.

### 9-10. 회차 단위 판정 완성 · 신규 등록 승인건 (2026-08-28)

§9-9 이후 *"옵션이 아니라 회차로 판정한다"* 를 남은 지점까지 밀고, 그 결과 생긴 구멍을 메웠다.

#### ① 접수 · 접수취소 버튼이 옵션만 보고 있었다

오늘 상태명 · 편집권한 · 승인자명 · 전환버튼을 전부 회차 단위로 옮겼는데 **이 둘만 옵션에 남아 있었다.**
`060_003` 이면 무조건 `'F'` 라 승인라인이 없는 소급 회차에서 버튼이 사라졌고,
그러면 *"전환하지 않으면 접수 흐름 그대로 굴러간다"*(§7-1)를 **지킬 수단이 없다.**

| 지점 | 변경 |
|---|---|
| `RCPT_BTN_VISIBLE_TF` | `060_003='T' → 'F'` → **`CFM_DEM_SN Is Not Null → 'F'`** |
| `CHK_CANC_PSBL_TF` | 동일 |

> 옵션은 현장 단위인데 궤도는 회차 단위다. 한 현장·한 기준월 안에 레거시 궤도 · 미승인 · 승인 모듈 회차가 공존할 수 있다.

#### ② 접수완료도 전환 대상이다 <sub>(2026-08-31 재확정)</sub>

①로 접수취소가 살아났으므로 한때 `SCNT_CHG_BTN_TF` 에 `STTS_CD='20' And CHECK_TF='T' → 'F'` 를 넣어
**접수취소 → 승인전환** 두 단계를 강제했다. *"이미 절차를 밟은 회차를 옵션 하나로 단번에 옮기면 어폐가 있다"* 는 취지였다.

**되돌렸다.** 그 경로가 오히려 절차 기록을 지우기 때문이다.

| 단계 | 컬럼 | 결과 |
|---|---|---|
| 접수취소 (`trscRcpt`, `RCPT_TF='F'`) | `CHECK_USER_NO = Decode(#{RCPT_TF}, 'T', #{SESSION_USER_NO}, Null)` | **접수자 → `Null`** |
| | `CNL_CMT` | 있지도 않은 취소 사유가 남는다 |
| 이후 승인요청 (`updateReceiveState`) | `CHECK_USER_NO = Nvl(CHECK_USER_NO, 요청자)` | **요청자로 덮인다** |

**실측** — `30212 / HT0001 / 202608` 의 9082 · 9120 은 `CHECK_USER_NO = 66791`(이찬호p) 이 실제로 들어 있다. 접수취소를 강제하면 이 값이 지워진다.

원래 접수한 원청 담당자가 사라진다. *"절차를 존중한다"* 가 그 절차의 유일한 기록을 지우는 셈이라 취지에 반한다.

접수완료 회차에는 **전환 버튼과 접수취소 버튼이 함께** 뜬다 — 원청이 *"승인으로 올릴지 / 접수를 무를지"* 를 고른다.
`STTS_CD='30'` 에서 레거시 결재와 전환이 나란히 뜨는 것과 같은 구조다(§9-9).

> 남는 제약은 40·50·60(레거시 결재 실적 있음)뿐이다. 승인 궤도 판정은 이제 **`CFM_DEM_SN` 유무 하나**로 수렴한다.

#### ③ 원청 신규 등록 시 승인건 생성

승인 모듈 현장에서 원청이 새로 만든 회차는 `CHECK_TF='T'` · `STTS_CD='20'` · 승인건 없음으로 태어난다.
**소급 접수분과 데이터가 한 글자도 다르지 않다** — 옵션이 켜진 시각이 어디에도 없으므로(§7-5) 조회로는 못 가린다.
그대로 두면 방금 만든 회차도 접수취소를 거쳐야 해서 불합리하다.

**`insertAsmt` 직후 `createDemand` 를 호출해 승인건을 함께 만든다.** 승인건 유무가 *"옵션 켠 뒤에 만들어졌나"* 를 대신한다.

| | |
|---|---|
| 위치 | `SfasRegAtRiskasmtRcptServiceImpl.createDemandOnNewAsmt` — `save()` 의 `rowStatus='C'` 분기 |
| 표준 승인선 | `bridgeService.selectStdStep` — **화면 `fnLoadStdStep` 과 같은 경로** |
| 시작 상태 | `요청대기`(`REG`) — 등록만 했을 뿐 요청 행위는 아직 없다 |
| 요청자 | 코어가 세션 사용자로 채운다 |
| 표준단계 없음 | 그냥 반환 — 승인건만 만들면 요청할 수단이 없다. 접수 흐름으로 남겨 전환 버튼을 쓰게 한다 |

> 같은 트랜잭션이라 승인건 생성이 실패하면 회차 등록까지 함께 롤백된다.
> **기존 데이터는 안 바뀐다.** 적용 전에 만들어진 원청 작성분은 계속 소급분이다 — 접수취소 → 전환 경로를 탄다.

##### ③-1. "등록과 동시에 저장" 을 택한 이유 <sub>(2026-08-31 재검토·확정)</sub>

08-31 에 *"타 화면은 평가서 저장과 승인라인 저장을 분리하는데 여기만 붙어 있다"* 는 지적으로 한 번 **보류**했다가 되돌렸다.
대안(승인건만 만들고 단계는 사용자가 저장)을 설계해 보니 **공통 코드 두 곳을 고쳐야** 했다.

| | 등록과 동시에 저장 <sub>(채택)</sub> | 승인건만 생성 + 사용자가 단계 저장 |
|---|---|---|
| 변경 파일 | **0** (이미 구현됨) | 3 |
| 공통 코드 | 없음 | `CommonWFrameSanctnGrid` · `CommonSanctionBridgeServiceImpl` |
| 영향 범위 | OTAT | **승인 모듈 전 모듈** |

**대안이 공통 코드를 요구하는 이유** — 승인 wframe 이 `DEM_SN` 유무로 갈린다(`CommonWFrameSanctnGrid` initW).
`DEM_SN` 이 없으면 `fnLoadStdStep()` 으로 표준선을 채우고, 있으면 `fnReload()` 로 단계이력을 조회한다.
**`DEM_SN` 있음 + 단계 0건은 빈 그리드가 뜬다** — 표준선 폴백이 없다.
거기에 `updateDemand` 는 `stampRequesterOnDemStep` 을 돌리지 않아, 요청 단계 승인자가 비면 `actSanction` 이 `-20009` 로 승인요청을 막는다.

**사용자가 보는 차이는 "저장 버튼을 누르는가" 하나뿐이다.**
둘 다 상태명 `요청대기` · 상태명 링크로 팝업 진입 · 표준선 표시 · 승인자 변경 가능(`REG` 은 편집 자유)이고,
채택안은 단계가 하나 적다(저장을 안 눌러도 승인요청이 된다).

> 보류 당시 들었던 사유 3개 중 둘은 과대평가였다.
> **패턴 불일치** — 결과 상태가 같고 `REG` 은 편집·재저장이 자유라 사용자가 못 하는 일이 없다.
> **표준단계 없는 현장은 승인건 없이 접수 상태** — 접수완료에서도 전환 버튼이 뜨게 되면서(§9-10 ②) 막다른 길이 아니게 됐다. 오히려 안전한 폴백이다.
> 남는 건 **트랜잭션 롤백 위험** 하나인데, 조용한 실패가 아니라 사용자에게 에러가 보인다.

> ⚠️ **부수 효과** — `REG` 는 협력사 화면이 열린 상태다. 원청이 만든 회차를 **협력사가 이어받아 승인요청**할 수 있다.
> 협력사 신규 흐름과 같은 상태라 수용했다. 회수(제출취소)는 여전히 `RECEIVE.CHECK_TF='T'` 라 막힌다.

#### ④ 협력사 외곽 버튼 — 승인 궤도면 숨긴다

승인 진행을 전부 승인 팝업에 일임했으므로 외곽에 승인 어휘 버튼을 둘 이유가 없다.
`SUB_BTN_TF` · `CANC_BTN_TF` 두 플래그를 신설해 노출을 회차 단위로 옮기고, **라벨을 옵션으로 바꾸던 코드를 지웠다.**

| 회차 | 외곽 버튼 |
|---|---|
| 승인 궤도 · 소급 미제출 | **없음** — 상태명 링크로 팝업 |
| 소급 · 제출됨 | **`제출취소`** — 협력이 회수해 `요청대기` 로 돌아갈 수 있다 |
| 소급 · 접수됨 | `제출취소` (누르면 기존대로 `ORA-20009`) |

> 미결이던 **버튼 라벨 어긋남이 해소**됐다. 승인 어휘 라벨을 외곽에서 아예 쓰지 않는다.

#### ⑤ 삭제 조건 — 궤도별로 갈랐다

삭제는 복구 비용이 크므로 편집권한(`UPD_PSBL_TF`)보다 **좁게** 잡는다.

| 회차 | 협력 | 원청 |
|---|:--:|:--:|
| 미제출 | ✅ | ❌ |
| 제출 · 접수됨 | ❌ | ✅ |
| `요청대기` | ✅ | ✅ |
| `승인대기` | ❌ | ✅ |
| **`승인중`** | ❌ | **❌** |
| **`승인반려`** | **❌** | ✅ |
| `승인완료` | ❌ | ❌ |

**협력** — `반려` 만 새로 막았다. `DEM`·`PROG`·`CMPL` 은 `SUB_TF='T'` 라 기존 조건에서 이미 걸린다.
반려는 원청이 개입한 결과이고 승인 축이 원청에 있으므로 협력사가 지울 수 없다.

**원청** — `승인중`·`승인완료` 를 막았다. 편집권한 완화(§9-9 ⑤)로 `승인중` 의 미처리 단계 승인자에게 편집이 열렸는데,
**다른 사람이 이미 승인한 건을 뒷 단계 사람이 지우면 안 된다.**

그리고 판정을 궤도별로 갈랐다 — 승인 궤도는 승인상태를, 그 외는 접수여부를 본다.
승인 궤도 회차에 접수여부를 물으면 *"접수되지 않아 삭제할 수 없습니다"* 가 뜨는데 **그 회차에는 접수 버튼이 없어** 안내대로 할 수가 없다.

#### ⑥ 전환 시작 상태 — 재확정

| | 시작 상태 | 요청자 |
|---|---|---|
| **승인전환 버튼** (소급 회차) | `승인대기`(`DEM`) ← **결정. 백필 선행이라 현재 구현은 `REG`** | **제출자** |
| **원청 신규 등록** | `요청대기`(`REG`) | 세션 (원청) |

전환은 *"요청까지 채워 넣는"* 행위라 `승인대기`, 신규 등록은 아직 요청 전이라 `요청대기` 다.

> ⚠️ `DEM` 시작은 **아직 구현되지 않았다.** `onDemandCreated` 가 `REG` 로 역기록한다(제출자 백필이 선행).
> 현재 값은 [승인_현재동작.md §3 S5](./승인_현재동작.md) 를 본다.

**요청자=제출자 구현 (2026-08-31)** — 코어는 `RP_USER_NO` 가 비면 **세션 사용자**를 요청자로 쓴다
(`CommonSanctionServiceImpl.insertSanctionDemand`). 그대로 두면 원청이 전환한 회차의 요청자가 원청 담당자가 되고,
접수자 역산(`updateReceiveState`)까지 원청이 된다.

| | |
|---|---|
**교체는 저장 시점이 아니라 조회 시점에 한다.** 서버가 저장할 때 몰래 바꾸면 사용자가 보고 저장한 내용과 결과가 달라진다.
표준선을 내려줄 때 이미 제출자로 채워 보내면 화면에 그대로 뜨고, **원하지 않으면 사용자가 다른 사람으로 고칠 수 있다.**

> **순서와 현재 규칙은 [승인_현재동작.md §5 요청자](./승인_현재동작.md) 가 정본이다.**
> 여기서는 훅 두 개(`onStdStepLoaded` · `beforeDemand`)를 왜 신설했는지만 남긴다.

**2′ 이 필요한 이유** — `changeLine` 과 `selectStdStep` 은 같은 `selectSanctionLineStep` 을 부른다.
한쪽만 보정하면 **승인라인을 바꾸는 순간 승인자 기본값이 세션(원청)으로 되돌아가** 화면이 오락가락한다.

> 승인라인변경은 **LOV 종료 콜스택**에서 도는 선언형 submission 이라 모듈별 PK 를 개별 파라미터로 못 싣는다(동적 submission 불가).
> 화면이 호스트 PK 를 `USE_TGT_INFO` 한 칸에 담아 보내고, 브리지 `withTgtKeys` 가 펼쳐 훅에 넘긴다 — `createDemand` 가 쓰는 규약 그대로다.

> 라인을 바꿔도 **이미 처리된 요청 단계 실적은 유지된다** — `fnApplyChangedLine` 이 `ACT_CODE` 가 있을 때만 옛 승인자를 되돌려 놓는다.
> 아직 요청 전이면 새 라인의 값(=제출자)이 그대로 남는다.

| | |
|---|---|
| 훅 | `onStdStepLoaded(alStepRows, amKeys)` · `beforeDemand(amDemandData, alStepRows)` — 둘 다 **신설** |
| 판별 | **제출자 소속 ≠ 세션 소속** — 남의 제출건을 올리는 것이니 전환이다 |
| 미적용 | 제출자 미기록(백필 전·원청 직접 작성분) · 같은 회사 안의 위임(A 제출 → B 요청) |

**요청자를 DB 가 아니라 화면 값에서 읽는 이유** — 3에서 사용자가 승인자를 바꿨는데 서버가 DB 의 제출자를 쓰면,
`TBASE_SANCTN_DEM.RP_USER_NO`(제출자)와 요청 단계 `SANCTNER_USER_NO`(사용자가 고른 사람)가 갈라진다.
화면 값을 옮기기만 하면 **둘이 항상 같다.**

> **2 는 기본값 제안일 뿐이다.** 3에서 원청이 다른 사람으로 바꿨다면 그건 원청의 의도이므로 서버가 되돌리지 않는다.
> 서버가 저장 시점에 제출자로 덮어쓰는 방식은 **채택하지 않았다** — 사용자가 보고 저장한 내용과 결과가 달라지기 때문이다.

> ⚠️ **저장 이후 재편집은 요청자가 따라가지 않는다.** `updateDemand` 는 단계만 CRUD 하고 `updateSanctionDemand` 를 부르지 않아
> 요청 단계 승인자만 바뀌고 `RP_USER_NO` 는 최초 저장값으로 남는다. **수용한 제약**이다 —
> 요청 전(`REG`)에만 열려 있는 좁은 창이고, 접수자 역산은 승인요청(`DEM`) 이후에 돌기 때문에 실무 영향이 작다.

> **요청자가 세션과 달라도 승인요청은 막히지 않는다.** `actSanction` 은 요청 단계(`STEP_GRP_NO = 1`)를 사용자 검사 없이 통과시키고,
> 처리 시 `ACT_CODE = Decode(SANCTNER_USER_NO, #{SESSION_USER_NO}, 'SANCTN', 'AGT')` 로 기록한다.
> 즉 **요청자는 협력사, 실제 처리는 원청이 대리(`AGT`)** 로 정확히 남는다.

> `updateDemand` 는 훅을 부르지 않는다 — 이미 만들어진 요청의 요청자를 바꿀 이유가 없다.
> 회사 비교인 이유: 같은 협력사 안에서 A 가 제출하고 B 가 요청하는 건 정상 위임이고, **요청은 B 가 한 것**이다.

> **대리인 배정은 불필요하다 (2026-08-28 확인).** `actSanction` 이 요청 단계(`STEP_GRP_NO=1`)를 사용자 검사 없이 통과시키고,
> 처리 직후 *"요청단계 승인자가 아닐 경우 대리인에 등록"* 을 **코어가 이미 한다.**
> 이전 판의 *"원청을 요청 단계 대리인으로 함께 넣어야 한다"* 는 틀렸다 — `DEM_PSBL_TF` 는 승인건 상태만 보고 사용자를 보지 않는다.

### 9-12. 전환 시 `승인대기`(DEM) 시작 — 착수 전 설계 검토 (2026-09-02)

§3-3 ② 가 정한 *"제출자 있으면 `승인대기`"* 는 아직 미구현이다(§9-7). 막고 있던 전제(백필)가 풀려 착수 가능해졌고,
착수 전에 확인해야 할 것을 여기 남긴다. **아직 구현하지 않았다.**

#### ① 지금 무엇이 어긋나 있나

| | §3-3 결정 | 현재 구현 |
|---|---|---|
| 요청자 | 제출자 | **제출자** ✅ (`onStdStepLoaded` + `beforeDemand`) |
| 시작 상태 | `승인대기`(`DEM`) | **`요청대기`(`REG`)** ❌ |

`onDemandCreated` 가 C·D 구분 없이 `STS_REG` 를 박는다. 그래서
**"제출자 명의로 요청됐는데 아직 요청은 안 한 상태"** 라는 모순된 조합이 남는다.

실측 — `30212 / K001 / 9144` (2026-09-02): `SUB_USER_NO=66792`(협력사 이찬호c) · `CFM_DEM_SN=12681` · `CFM_STS_CODE='REG'`.
유형 D 조건을 다 갖췄는데 `REG` 다.

부작용은 §9-9 ④ 가 이미 지적했다 — `SUB_TF` 는 `REG` 를 열린 상태로 보므로
**접수 완료 회차를 전환한 직후 협력사 화면이 다시 열린다.**

#### ② 판정 기준 — `SUB_USER_NO Is Not Null` 하나면 된다

§3-3 원문이 *"제출자 데이터 있음(유형 D)"* 이고, 회사 비교는 필요 없다. `insertAsmt` 가 원청 작성분을 명시적으로 `Null` 로 넣기 때문이다.

```sql
Null, -- 제출자_회사ID (원청 작성이라 제출 행위 없음)
Null  -- 제출자_사용자번호
```

| 경로 | `SUB_*` | 판정 |
|---|---|---|
| 원청 신규 등록 (`insertAsmt` → `createDemandOnNewAsmt`) | **`Null`** | `REG` ✅ §9-10 ⑥ 결정과 일치 |
| 협력 제출분 (신규 · 백필 Pass 1) | 협력사 / 제출자 | `DEM` |
| 원청 대신작성분 (백필 Pass 2) | 원청 / 작성자 | `DEM` — 실제로 제출된 회차라 맞다 |

> 요청자 교체(`onStdStepLoaded`)가 쓰는 *"제출자 회사 ≠ 세션 회사"* 는 **다른 기준이다.** 여기서 재사용하지 않는다.
> 대신작성분은 회사가 같아 요청자는 세션이 되지만, 제출은 있었으므로 상태는 `DEM` 이 맞다.

#### ③ 어디서 요청을 태우나 — 브리지가 맞다

| 안 | 내용 | 판정 |
|---|---|---|
| A. 팝업 FE — 저장 후 `cips.sanction.request` 이어 호출 | 두 번의 통신 | ❌ **롤백 불가.** 저장은 됐는데 요청이 실패하면 `REG` 로 남는다 |
| B. 핸들러 `onDemandCreated` 안에서 코어 호출 | 한 트랜잭션 | ❌ **규약 위반.** 핸들러 주석: *"오케스트레이션/코어호출은 CommonSanctionBridgeService 가 수행(여기서 코어 직접호출 X)"* |
| **C. 브리지 `createDemand` 끝** | 핸들러엔 판정만 묻고 실행은 브리지 | ✅ **채택** |

§9-9 ④ 가 *"요청 실패 시 승인라인을 롤백해야 어정쩡한 상태가 안 남는다"* 고 정했으므로 한 트랜잭션이어야 한다. A 는 탈락.
B 는 트랜잭션은 맞지만 핸들러가 코어를 직접 부르게 되어 **오늘 만든 훅 5종과 반대 방향**이다.

**C 의 형태** — 판정 훅을 하나 더 두고, 실행은 브리지가 기존 `applyAction` 을 재사용한다.

```
createDemand
    insertSanctionDemand → insertSanctionDemandStep → onDemandCreated(REG 역기록)
    ↓
    if (handler.shouldRequestOnCreate(amReqData))
        applyAction(tgtCode, {ACT_CODE:"SANCTN", …})
            → actSanction → onActionApplied(merge·sync·CFM_*=DEM) → …
```

`applyAction` 을 그대로 쓰면 **접수 컬럼 동기화(`syncReceiveState`)와 제출본 복사까지 기존 경로로 따라온다.**
새로 쓸 코드가 없다.

#### ④ 코어가 이미 해주는 것 — 추가 구현이 필요 없는 부분

- **요청자가 세션과 달라도 통과한다.** `actSanction` PL/SQL 은 요청 단계(`STEP_GRP_NO = 1`)를 사용자 검사 없이 지나간다.
- **대리 기록도 자동이다.** `DEM` 단계 승인자 ≠ 세션이면 `TBASE_SANCTN_DEM_STEP_AGT` 에
  *"승인자가 아닌 사용자가 승인요청"* 으로 넣고, `ACT_CODE` 를 `AGT` 로 남긴다.
  → *"협력 명의로 요청되었고 원청 아무개가 실행했다"* 가 그대로 기록된다(§9-8 의 대리인 결정과 같은 동작).

#### ⑤ 짚어둘 위험

| | |
|---|---|
| **단계가 1개뿐인 승인선** | 요청이 곧 완료(`CMPL`)가 된다. 이때 검토의견 게이트(§7-8-2)가 걸리면 전환 자체가 롤백된다. 동작은 맞지만 사용자에겐 *"전환했는데 검토의견 안내가 뜨는"* 상황이라 문구 확인이 필요하다 |
| **자기호출(self-invocation)** | 브리지가 자기 `applyAction` 을 부르면 프록시를 안 거쳐 새 트랜잭션이 안 열린다 — **이 경우엔 그게 맞다**(같은 트랜잭션이어야 롤백이 된다). 다만 의도한 동작임을 주석에 남긴다 |
| **되돌릴 수 없다** | `DEM` 이 되면 협력사 화면이 잠긴다(`SUB_TF='T'`). 요청취소로 `REG` 로 되돌릴 수는 있다 |
| **운영 백필 선행** | 전체 백필 전에 운영에서 전환하면 소급분이 전부 유형 C 로 굳어 영영 `REG` 다(§9-7 ⚠️). 개발은 08~09 만 백필돼 있어 **그 범위 밖 회차는 여전히 `REG` 로 나온다** — 테스트 시 혼동 주의 |
