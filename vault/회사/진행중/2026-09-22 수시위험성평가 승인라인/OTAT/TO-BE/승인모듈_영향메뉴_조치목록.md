# 승인 모듈(060_003) 영향 메뉴 · 조치 목록

> **성격**: 사이드 이펙트 점검용 **작업 목록**. 왜 이렇게 되는지의 근거는 [승인상태_전환명세.md](./승인상태_전환명세.md) §6-1.
> **실측**: 2026-08-27 · 개발 서버(PMIS4) 기준
> **삭제 조건**: 아래 조치가 전부 반영되고 060_003 현장에서 회귀 확인이 끝나면 폐기한다.

---

## 0. 한 줄 요약

**대부분은 손대지 않는다.** 승인요청 시점에 `CHECK_TF='T'`·`STTS_CD='20'` 을 기록하는 **쓰기 조치 1건**으로 27개 매퍼가 함께 풀리고,
**따로 손봐야 하는 것은 3건뿐**이다(모니터링 2종 + 회의록 2종의 Null 처리).

> **진행 상황 (2026-08-27)** — 공통 조치 **구현 완료**(§7-1). 다음은 060_003 현장 회귀 확인.
> 모니터링(§4-1) · TBM(§4-3)은 **보류** — 모니터링 계열을 몰아서 볼 때 함께 처리한다.

---

> 📌 **전제 일부가 바뀌었다 (2026-08-31).** 조치(C-1·C-2)는 그대로 유효하지만, 아래 두 가지가 달라졌다.
> ① 승인 모듈 현장에도 **접수·접수취소 버튼이 돌아왔다** — 옵션이 아니라 회차 단위로 판정한다(명세 §9-10 ①).
>    따라서 *"접수 버튼(trscRcpt)뿐"* 이라는 §1 의 서술은 더 이상 정확하지 않다. 다만 승인요청 시 쓰기 조치는 여전히 필요하다.
> ② 제출본(`TSF_ASSMNT_REGIS.CHECK_TF`)도 승인요청 시 함께 맞춘다 — `updateRegisSubmitted` 신설(명세 §9-10).
>
> **미해소로 남은 것은 §4-4(옵션 관리 화면에 `060_003` 없음)** 하나다.

## 1. 왜 영향을 받나

승인 모듈은 접수 버튼을 없앴다(`RCPT_BTN_VISIBLE_TF` 가 060_003 이면 항상 `'F'`).
그런데 `TSF_ASSMNT_RECEIVE.CHECK_TF`(`'T'`)와 `STTS_CD`(`'20'`)를 쓰는 곳이 **접수 버튼(`trscRcpt`)뿐**이다.

→ 060_003 현장의 회차는 **영영 `CHECK_TF='F'` · `STTS_CD='10'`** 에 묶인다.
→ 이 값을 조건으로 쓰는 화면들이 그 회차를 **못 보거나, 미접수로 표시**한다.

**조치 원칙** — 조회 29곳을 고치지 않고 **쓰기 한 곳에서 값을 맞춘다.**
승인요청 시점에 세 컬럼을 기록하면 레거시와 같은 모양이 되어 대부분의 화면이 그대로 동작한다.

## 4. ⚠️ 따로 손봐야 하는 것 — 3건

### 4-1. 🔴 모니터링 2종 — `'20'` 을 **완료**로 읽는다

> ⏸️ **보류 (2026-08-27 결정).** 모니터링 계열은 별도로 몰아서 한 번에 작업한다. 상시/수시 쪽을 먼저 끝낸다.
>
> **보류 중 나타나는 증상** — 공통 조치(§2)가 들어간 상태에서 모니터링만 안 고치면
> **승인요청만 해도 완료로 집계**된다. 승인이 안 났는데 실적에 잡히므로, 모니터링 수치를 보고 판단하는 자리에서는
> 그 사이 기간의 060_003 현장 수치를 신뢰하면 안 된다. 켠 현장이 개발 3곳뿐이라 지금은 영향이 국소적이다.

**다른 곳과 정반대다.** 같은 `STTS_CD='20'` 을 가져오기 계열은 *"접수됨 = 쓸 수 있다"*, 모니터링은 *"완료됨"* 으로 읽는다.

| 메뉴 경로 | 화면 | 매퍼 · 행 |
|---|---|---|
| 위험성평가 › 모니터링 › **상시위험성평가모니터링** | [MontInqCompanyRiskAssessmentMonitoringCompany.xml](../../src/main/webapp/wqxml/mont/MontInqCompanyRiskAssessmentMonitoringCompany.xml) | `~Sql` **1041~1047** |
| 〃 (상세 팝업) | [MontInqCompanyRiskAssessmentMonitoringCompanyPopDetail.xml](../../src/main/webapp/wqxml/mont/MontInqCompanyRiskAssessmentMonitoringCompanyPopDetail.xml) | `~Sql` **989~995** |

```sql
(Case
    When c.SFAS_OPT_060 = 'T' And a.STTS_CD = '60' Then 1
    When c.SFAS_OPT_060 = 'F' And a.STTS_CD = '20' Then 1   -- ← 060_003 현장이 여기 걸린다
    Else 0
 End) CMPL_CNT
```

**왜 레거시에서는 문제가 없었나** — `060='T'` 면 완료가 `'60'` 이라 접수(`'20'`)와 구분됐고,
`060='F'`(승인 미사용)는 접수가 곧 완료였다. **060_003 은 "060='F' 인데 승인이 있는" 새 조합이라 전제가 깨진다.**
공통 조치를 하면 **승인요청만 해도 완료로 집계된다.**

**조치** — 060_003 분기를 앞에 추가하고 완료는 `CFM_STS_CODE` 로 판정한다.

```sql
(Case
    When c.SFAS_OPT_060_003 = 'T' Then Decode(a.CFM_STS_CODE, 'CMPL', 1, 0)   -- 추가
    When c.SFAS_OPT_060 = 'T' And a.STTS_CD = '60' Then 1
    When c.SFAS_OPT_060 = 'F' And a.STTS_CD = '20' Then 1
    Else 0
 End) CMPL_CNT
```

> 두 파일의 Case 가 동일하므로 **같은 패치를 두 곳에 적용**한다.

### 4-2. 🔴 회의록 2종 — `STTS_CD` Null 이 조건에서 탈락한다

| 메뉴 경로 | 화면 | 매퍼 · 행 |
|---|---|---|
| 회의록 확정 › 위험성평가 가져오기 | [SfasRegMeetingConfirm.xml](../../src/main/webapp/wqxml/sfas/SfasRegMeetingConfirm.xml) | `~Sql` **643·644** |
| 회의록 초안 › 위험성평가 가져오기 | [SfasRegMeetingDraft.xml](../../src/main/webapp/wqxml/sfas/SfasRegMeetingDraft.xml) | `~Sql` **1455·1463** |

```sql
And b.STTS_CD != '10'                                  -- ← 게이트 없음. Null 도 탈락
And (#{SFAS_OPT_060} = 'F' Or b.STTS_CD = '60')
```

**두 가지가 겹쳐 있다.**

1. **060_003 문제** — `STTS_CD` 가 `'10'` 에 묶여 있어 회의록에서 평가서를 못 가져온다 → **공통 조치로 해소**
2. **기존 결함 (060_003 무관)** — Oracle 에서 `Null != '10'` 은 참이 아니라 **Unknown** 이라 조건에서 탈락한다.
   개발 서버 실측 `STTS_CD` **Null 521건**(전체 2,076건 중 25%) — 이 회차들은 지금도 회의록에서 안 보인다.

**조치** — Null 을 살릴지 결정한다. 살린다면:

```sql
And Nvl(b.STTS_CD, '20') != '10'
```

> ⚠️ **이건 060_003 과 무관한 기존 결함**이다. 승인 모듈 작업 범위에 넣을지는 별도 판단.
> 손대지 않아도 승인 모듈은 정상 동작한다(신규 회차는 `'20'` 이 들어가므로).

설계대로면 이 분기가 살아날 일이 없다. 아래 §4-4 의 가드만 들어가면 닫힌다.

### 4-4. 🔴 옵션 관리 화면에 `060_003` 자체가 없다

**D11 이 요구한 admin 가드가 미구현이다.** 옵션 관리 화면 4종 어디에도 `SFAS_OPT_060_003` 이 없다.

| 화면 | wqxml | SQL |
|---|---|---|
| `CcmsRegSfasOptionByProj` (현장별) | 0건 | 0건 |
| `CcmsRegSfasOptionByProjManager` | 0건 | 0건 |
| `CcmsRegSfasOptionByCompany` (회사별) | 0건 | 0건 |
| `CcmsRegSfasOptionByCompanyManager` | 0건 | 0건 |

**결과**

1. 옵션을 **화면에서 켤 수 없다** — 지금까지 켠 3개 현장은 DB 를 직접 손댄 것이다
2. **상호배타 가드가 없다** — D11 이 요구한 *"하나를 T 로 하면 다른 하나를 자동 F + readonly (양방향)"* 가 없어
   손으로 `T/T` 를 만들 수 있다. 실제로 `UT001` 이 그 상태였다(2026-08-27 조치 완료)

> 🔴 **재발했다 (2026-09-02 PMIS4 실측).** `30212 / R2353` 이 `060='T'` + `060_003='T'` 다. 회차 25건(승인건 2건)이 이미 있다.
> 가드가 없으니 한 번 고쳐도 계속 되돌아온다 — **손으로 데이터를 고치는 대응은 이 항목의 해결이 아니다.**
> 아울러 `060_003='T'` 현장이 3곳에서 **5곳**(A0001·UT001·GC001·HT0001·R2353)으로 늘었다. §7-1 의 회귀 확인 현장 표도 낡았다.

**조치** — 관리 화면 4종에 `SFAS_OPT_060_003` 항목 추가 + `060` 과의 양방향 배타 처리.
컬럼 정의 · 그리드 컬럼 · 저장 SQL 세 곳을 `SFAS_OPT_060_002` 옆에 나란히 넣으면 된다.

> 배포 전까지는 DB 직접 수정으로 운용되므로 급하지 않지만, **운영 배포 전에는 반드시 필요**하다.

|---|---|
| `TSF_ASSMNT_RECEIVE` PK | `COMPANY_ID` + `PROJ_CODE` + **`R_COMPANY_ID`** + `REGIS_SEQ` |
| 기존 `updateCfmReceive` 의 Where | `COMPANY_ID` + `PROJ_CODE` + `REGIS_SEQ` — **`R_COMPANY_ID` 없음** |
| 그 키로 여러 행이 잡히나 | **0건** — 회사·현장·회차 조합으로 항상 단일 행 |
| 원청 작성분에도 RECEIVE 행이 있나 | **966건** (`COMPANY_ID = R_COMPANY_ID`) — 있음 |
| 협력 제출분 | 1,110건 |

`REGIS_SEQ` 단독으로는 5건이 중복되지만(회사·현장을 넘는 재사용), **Where 에 셋이 다 들어가므로 무해**하다.
따라서 `syncReceiveState` 는 기존 `updateCfmReceive` 와 **같은 키를 그대로 쓰면 된다.**

### 5-1. 다만 가드 조건은 두 컬럼을 다 봐야 한다

| 경로 | `CHECK_TF` / `STTS_CD` 분포 (개발 서버) |
|---|---|
| 원청작성 | `T`/`20` 389 · `T`/`30` 244 · `T`/Null 161 · `T`/`60` 86 · `F`/Null 21 · `F`/`10` 1 |
| 협력제출 | `T`/`20` 290 · `T`/Null 227 · `T`/`30` 168 · `F`/`10` 149 · `F`/Null 133 · `C`/Null 2 · **`T`/`10` 1** |

**`CHECK_TF='T'` 인데 `STTS_CD='10'` 인 행이 실제로 있다.**
가드를 `CHECK_TF <> 'T'` 하나로만 걸면 이런 행이 스킵돼 `STTS_CD` 가 `'10'` 에 남는다.

```sql
And (Nvl(CHECK_TF, 'F') <> 'T' Or Nvl(STTS_CD, '-') <> '20')   -- 둘 다 본다
```

> `CHECK_TF='C'` 2건은 `SfasPopRegAssmntReciveSql` 이 `In('T','C')` 로 받는 값이다. 의미 미확인 — 060_003 과 무관.

## 6. 영향 없음 — 오해 방지용 기록

조사 초기에 영향권으로 잘못 분류했던 것들이다. **다시 조사하지 않도록 남긴다.**

| 대상 | 왜 무해한가 |
|---|---|
| **대시보드 3종** (동문 · 금성백조 · 한국농어촌공사) | `TSF_ASSMNT_**REGIS**.CHECK_TF`(협력사 제출여부)를 본다. 승인요청 시 `mergeRegisToReceive` 가 `trscSub` 을 `SUB_TF='T'` 로 태워 이 값을 켜므로 060_003 에서도 정상 |
| 모니터링의 `CHECK_TF In('R','A')` | `TSF_FST_RISKS_EVLCHRT_RCV`(최초위험성평가) 소속 |
| 모니터링 1085 · 1137 행 | `TSF_SERCURITYCHECK_DETAIL`(보안점검) 소속 |
| `SfasRegAtRiskasmtSubSql` 등 투영만 하는 8개 매퍼 | `Select` 로 값을 실어 나르기만 해 결과가 안 바뀜 |

### 판정 시 주의 — alias 를 파일 전역으로 매칭하면 오판한다

`a`·`x` 같은 한 글자 alias 를 여러 테이블이 돌려쓴다. Oracle 은 `Select` 절이 `From` 보다 위라 역방향 탐색으로도 못 찾는다.
**해당 라인에서 가장 가까운 `테이블 alias` 바인딩**을 채택해야 맞다. 전역 매칭으로는 79개 참조가 35개 매퍼로 나왔지만,
최근접 규칙으로 다시 세니 **29개 매퍼 145건**이었고 대시보드 3종이 전부 빠졌다.

**값으로도 가를 수 있다** — `CHECK_TF` 가 `'R'`·`'A'` 면 최초위험성평가, `'T'`·`'F'`·`'C'` 면 상시/수시다.
