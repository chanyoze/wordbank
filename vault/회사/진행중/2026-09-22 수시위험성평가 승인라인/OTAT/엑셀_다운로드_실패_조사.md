# 상시·수시위험성평가 접수 — 엑셀 다운로드 실패

> **성격**: 운영 장애 **원인 규명 완료**. 조치 대기.
> **조사·확정**: 2026-08-27 · 운영 DB 실측
> **삭제 조건**: 재발 방지 조치가 배포되고 기존 데이터 정리가 끝나면 결론만 남기고 폐기한다.

---

## 0. 결론

셀 값에 **수직탭 `CHR(11)`(VT, `0x0B`)** 이 들어 있으면 그 회차의 엑셀 다운로드가 **통째로 실패**한다.

엑셀 요청 본문이 XML 인데 VT 는 **XML 1.0 이 표현을 금지한 문자**라 파싱이 깨지고,
엔진이 그 실패를 `D999 unexpected error` 로 뭉뚱그려 응답한다. 화면에는 아무 안내가 없어 **버튼 먹통**으로 보인다.

**영향 범위 (운영 실측)**

| 테이블 | 감소대책 | 유해위험요인 | 현장 | 회차 |
|---|---:|---:|---:|---:|
| `TSF_ASSMNT_RECEIVE_DETAIL` (원청 접수본) | 178 | 49 | 21 | **106** |
| `TSF_ASSMNT_REGIS_DETAIL` (협력 제출본) | 178 | 50 | 21 | 107 |

**106개 회차가 엑셀을 못 뽑는 상태다.**

## 1. 실패 경로

```
셀 값에 VT
  → 요청 본문 <![CDATA[ ... ]]> 안에 그대로 실림
  → 서버 Xerces 파싱 → [Fatal Error] An invalid XML character (Unicode: 0xb)
  → XMLUtil.getDocument 가 null 반환
  → GridGenerator.doExcel:39 에서 null 참조 → NullPointerException
  → GridToExcel2 catch → D999 응답 (message 비어 있음 — NPE 는 메시지가 null)
```

**xlsx 생성 단계가 아니라 요청 파싱 단계에서 죽는다.** 한 단계 앞이다.
따라서 **어느 화면·어느 그리드든** 셀에 VT 가 있으면 엑셀이 실패한다. 이 화면만의 문제가 아니다.

### 서버 로그

```
[Fatal Error] :41:40: An invalid XML character (Unicode: 0xb) was found in the CDATA section.
org.xml.sax.SAXParseException; lineNumber: 41; columnNumber: 40
    at websquare.util.XMLUtil.getDocument(XMLUtil.java:287)
    at websquare.http.controller.grid.excel.write.GridGenerator.doExcel(GridGenerator.java:38)
java.lang.NullPointerException:null
    at websquare.http.controller.grid.excel.write.GridGenerator.doExcel(GridGenerator.java:39)
```

`[Fatal Error] :줄:칸` 이 **문제 문자의 정확한 위치**를 찍어준다. 다음에 같은 일이 생기면 이걸로 바로 특정한다.

### ⚠️ ELK 에 안 잡힌다

`GridToExcel2` 는 `printStackTrace` 를 쓴다. **표준 에러로 직접 나가 log4j2 파이프라인을 타지 않는다.**
`log4j2-{env}.xml` 에 `websquare` 패키지 로거도 없다(등록된 것은 `com.cip.defg.saas`·`egovframework`·`org.springframework`·`jdbc.*`, `Root` 는 INFO).

→ **컨테이너 로그**(`catalina.out` · `localhost.*.log` · `docker logs`)를 봐야 한다.

재발 대비로 로거를 넣을 수는 있으나 `printStackTrace` 는 로거를 우회하므로 완전하지 않다.

```xml
<Logger name="websquare" level="DEBUG" additivity="false">
    <AppenderRef ref="rollingFileDebug"/>
</Logger>
```

## 2. VT 는 어디서 오나

**워드·한글에서 `Shift+Enter`(문단 안 줄바꿈)로 쓴 글을 복사해 붙여넣을 때** 들어온다.
그 프로그램들이 문단 안 줄바꿈을 `CHR(11)` 로 저장하고, 클립보드가 원문 그대로 담고, 브라우저도 정규화하지 않는다.

**화면에서는 줄바꿈처럼 보여 눈으로 구분되지 않는다.** 작성자는 인지조차 못 한다.

| 입력 | 저장되는 문자 |
|---|---|
| 워드·한글 `Shift+Enter` | **`CHR(11)` VT** |
| 워드·한글 `Enter` | `CHR(13)+CHR(10)` |
| 엑셀 셀 안 `Alt+Enter` | `CHR(10)` |
| 브라우저 textarea `Enter` | `CHR(10)` |

XML 1.0 이 허용하는 제어문자는 **탭(9)·개행(10)·복귀(13) 셋뿐**이다.
VT 는 문자 참조(`&#11;`)로도 표현이 금지돼 **우회로가 없다.**

## 3. 🔴 테이블이 이원화돼 있다 — 이것 때문에 3시간을 돌았다

**상세 데이터는 두 테이블에 따로 있다.**

| 테이블 | 소유 | 읽는 화면 |
|---|---|---|
| `TSF_ASSMNT_REGIS_DETAIL` | 협력사 제출본 | 상시/수시위험성평가서**제출** |
| **`TSF_ASSMNT_RECEIVE_DETAIL`** | **원청 접수본** | 상시/수시위험성평가서**접수** ← `selectContList` |

**둘은 독립적으로 갱신된다.** 협력사가 제출본을 고쳐도 접수본은 옛 값을 유지한다.

### 실제로 벌어진 일 (`554455` 회차, `REGIS_DETAIL_SEQ 5367411`)

| 테이블 | 121번째 문자 | `MODDATE` |
|---|---|---|
| `REGIS_DETAIL` | `Dump` → `a` = **LF** | 08-26 14:31:30 |
| `RECEIVE_DETAIL` | `Dump` → `b` = **VT** | **08-27 08:33:18** |

협력사가 제출본을 고쳐 `REGIS_DETAIL` 은 LF 가 됐지만 **접수본에는 VT 가 그대로 남았다.**
화면의 `MI_LST`(`SFSST_GetModInfo(a.MODUSERNO, a.MODDATE)`)가 08-27 08:33:18 인 것도 접수본 기준이라 일치한다.

### 왜 못 찾았나

1. 테이블 목록을 `TSF_ASSMNT_REGIS%` 패턴으로 뽑아 **`RECEIVE_DETAIL` 이 애초에 안 걸렸다**
2. 그 뒤로 계속 `REGIS_DETAIL` 만 조회하며 "VT 0건" 이라 결론냈다
3. DB 와 화면이 어긋나자 **DB 접속이 다른 인스턴스라고 오판**했다

**조회 SQL 의 `From` 절을 처음에 봤어야 했다.** 화면이 무엇을 읽는지 확인하지 않고 이름이 비슷한 테이블을 뒤진 것이 원인이다.

> 📌 **다음에 화면 데이터와 DB 가 어긋나면, 캐시·인스턴스를 의심하기 전에 조회 SQL 의 `From` 절부터 확인한다.**

## 4. 조치

### 4-1. 즉시 — 해당 회차 (운영 DML)

**접수본을 고쳐야 한다.** 제출본만 고치면 접수 화면은 그대로 실패한다.

```sql
Update TSF_ASSMNT_RECEIVE_DETAIL
Set
    IMPRV_MTHD = Replace(IMPRV_MTHD, Chr(11), Chr(10)),  -- 위험성감소대책
    RISK_FACT = Replace(RISK_FACT, Chr(11), Chr(10))  -- 유해위험요인
Where 1 = 1
And COMPANY_ID = 367698
And PROJ_CODE = 'R0006'
And REGIS_SEQ = 554455
And (Instr(IMPRV_MTHD, Chr(11)) > 0 Or Instr(RISK_FACT, Chr(11)) > 0)
```

`5367411`(121번째) · `5367423`(69번째) **2행**이 잡힌다.
치환 후 **반드시 재조회**한 뒤 엑셀을 누른다 — 그리드가 옛 값을 들고 있으면 그대로 실패한다.

> ✅ **2026-08-27 조치·확인 완료.** 치환 후 재조회하여 엑셀 정상 다운로드 확인.

### 4-2. 기존 데이터 일괄 — 두 테이블 모두

같은 `Update` 를 회차 조건 없이 돌린다. **`RECEIVE_DETAIL` 과 `REGIS_DETAIL` 양쪽**이다.
한쪽만 고치면 그 화면만 살아난다.

### 4-3. 재발 방지 — 붙여넣기로 계속 들어온다

| 안 | 내용 | 장단 |
|---|---|---|
| **A. 내보내기 직전 정화** | `excel.onClickBefore` 훅에서 제어문자 제거 | **경로·DB 상태와 무관하게 닫힌다.** 전 화면이 한 번에 풀림. 단 cips 공통 훅이라 영향 범위가 넓다 |
| B. 저장 시점 정화 | 저장 SQL·서비스에서 제거 | 근본이지만 저장 경로가 여럿(웹·모바일·가져오기)이라 범위가 크다 |

**A 를 먼저 권한다.** B 는 A 이후 여유 있을 때.

> ⚠️ **운영 반영은 2026-09-22 배포 이후다.** 그 전까지는 4-1·4-2 의 DML 로만 대응한다.

## 5. 조사 중 기각된 가설 — 다시 파지 않기 위해

VT 가 원인이라는 첫 진단은 옳았으나, **확인 범위가 좁아 스스로 기각했다가 되돌아왔다.**

| # | 가설 | 기각 근거 | 실제 |
|---|---|---|---|
| 1 | 수직탭 `CHR(11)` | "치환 후에도 재현" | 🔴 **오판** — 잘못된 테이블을 봤다 |
| 2 | 대괄호 `[ ]` | 오늘만 15개 회차 이상, 160건짜리도 정상 | ✅ 정당한 기각 |
| 3 | 개행 `CHR(10)` | 8월 이후 123,631건 중 **27,450건(22%)** | ✅ 정당한 기각 |
| 4 | DB 접속이 다른 인스턴스 | `MI_LST` 와 `MODDATE` 불일치 | 🔴 **오판** — 같은 DB, 다른 테이블 |

### 함께 배제된 것 (해당 회차 기준)

`CHR(13)` CR · 기타 제어문자 · XML 금지 문자(`FFFE`·`FFFF`·서로게이트) · `&` `<` `]]>` `"` `\` · 셀 길이(최대 201자) · 요청 본문 구조(컬럼 37개 일치, 인덱스·병합 정상)

### 집계 오류도 있었다

초기에 "VT 84건" 이라고 셌는데, 조건에 `Not Like '%'||Chr(10)||'%'` 를 넣어
**개행이 함께 있는 셀을 통째로 제외**했다. 실제는 두 테이블 합쳐 **455행 · 106회차**다.

> 📌 **제외 조건을 넣은 집계는 기저율을 함께 보고해야 한다.** 분자만 보면 규모를 놓친다.

## 6. 참고 — 호출 경로

```
엑셀 버튼
  → cips.event.commonTrigger.excel.onClick        (cips.js:9134)
  → com.downLoadExcel(grid, opts)                 (common.js:1629)
  → grdObj.advancedExcelDownload(options, infoArr)
  → POST xmlToExcel2.wq
  → GridToExcel2 → GridGenerator → XMLUtil.getDocument   (엔진 jar)
```

화면의 엑셀 훅(`excel.onClickAfter`)은 **비어 있다.** `bExcelPrcs` 기본값이 `true` 라 cips 공통 처리가 그대로 돈다.

`D999` 는 엔진 jar 의 `DeniedCode` 에 정의된 **catch-all** 이다(`D101`~`D706` 이 구체 코드, `D999` 는 `unexpected error`).

### 운영과 소스가 다르다

**개편본이 아직 배포되지 않았다(2026-09-22 예정).** 조사 중 요청 본문의 그리드 id 가 소스와 달라 혼선이 있었다.

| | 운영 | 작업 중 소스 |
|---|---|---|
| 내용 그리드 | `wgrdSub01` / `wdlSub01` | `wgrdCont` / `wdlCont` |
