# 표준 승인 — 구현 가능성 테스트 계획 🧪

> "적합성 분석(될까?)" → "**실측 검증(실제로 돌아가나?)**". 환경: **Spring 4.3.25 + eGovFramework + MyBatis, WAR 배포형, 테스트 인프라(JUnit) 없음**.
> 원칙: **싸게 먼저 깨진다** — 정적·컴파일로 블로커 대부분을 1~2시간에 잡고, 그 다음에야 DB/브라우저.

---

## T0 — 정적 블로커 검증 (실측 완료 ✅)

코드를 읽어 "스켈레톤 가정 vs 실제"를 대조. 결과:

| 검증 | 결과 | 근거 |
|---|---|---|
| **코어 재사용 가능?** | ✅ 존재 | `CommonSanctionService`(`module/common/service`)에 `actSanction`·`cancelSanction`·`insertSanctionDemand`·`insertSanctionDemandStep`·`selectSanctionDemandStep`·`selectDefaultSanctionLineStep` 등 전부 실재 |
| **빈 디스패치(if/switch 없음) 가능?** | ✅ 가능 | `context-common.xml` component-scan = `com.cip.defg.saas` 전체 → `@Component("DCMT")` 등록됨. Spring 4.3 은 `Map<String,Handler>` 빈이름 주입 지원 |
| **트랜잭션 원자성(core+handler) 확보?** | ✅ 조건부 | tx 포인트컷 = `execution(* com.cip.defg.saas..impl.*Impl.*(..))`, REQUIRED, **rollback-for=Exception** |
| **FE wframe 통신 패턴 실재?** | ✅ 검증된 관용구 | `wfrm.getWindow().scwin.fn()` 다수 화면 사용 + **로드 타이밍 가드 `if(scwin.bDataLoading)`** 패턴 존재 |
| **운영DB write 테스트 안전?** | ⛔ 금지 | `actSanction` 이 `CommonSanctionPushService` + `TransactionSynchronizationManager` 로 **커밋 후 실제 푸시 발송** → skpmis(운영)에서 write 테스트 시 사용자에게 푸시 발사 |

### T0이 드러낸 "조정 목록" (= 컴파일 시 빨강날 부분, 곧 구현 변경점)
1. **Bridge 위치**: `module/common/service/impl/CommonSanctionBridgeServiceImpl` 로 둬야 tx 포인트컷(`..impl.*Impl`)에 걸려 core+handler 원자화. (스켈레톤은 flat 패키지였음)
2. **`actSanction(Map) returns Map<String,Object> throws Exception`**: Bridge 는 `throws`/try 처리 + **반환 Map 에서 단계상태를 읽음**(스켈레톤의 `readStepStatus()` 스텁 제거).
3. **`selectSanctionDemandStep(String companyId, String projCode, String demSn)`** — Map 이 아니라 **3개 String 인자**. loadStatus 가 keys 에서 3개를 꺼내 전달하도록.
4. **승인라인 조회**도 positional(`selectSanctionLineStep(companyId, projCode, lineSn)`) — changeLine 어댑트.
5. **제네릭 컨트롤러는 서블릿 컨텍스트**에: component-scan(공통)이 `@Controller` 를 exclude → Bridge 컨트롤러는 dispatcher-servlet 스캔 대상에 등록.
6. **헬퍼 활용**: `createSanctionDemandSerialNumber()`(DEM_SN), `makeKey`/`makeCompositeKey` 이미 제공 → 직접 안 만듦.

## T1 — 컴파일 온 브랜치 (가장 싼 결정적 BE 테스트) ⏱️~1h  · **실행 완료 ✅ (2026-07-01)**
> 격리 미니 모듈(`예시구현/testbed/`)에서 **번들 JDK 8 + Maven 3.6.3** 로 실집행. 협력자는 stub 으로 대체.
> 결과: **컴파일 성공 · JUnit·Mockito 31 tests 그린 · JaCoCo 라인 100% / 분기 93.5% · 80% 게이트 PASS**.
> → BE 형틀 성립 확인. 매퍼 실메서드(`updateStsCode` 등) 실재 여부는 실제 브랜치 이관 시 재확인(추가 구현 스코프 판별용).
> 또한 이 실측으로 조정목록 #2(아래) 반영: `readStepStatus` 하드코딩(`"PROG"`) 제거 → `actSanction` 반환 Map / `selectSanctionDemand` 재조회에서 실제 `STS_CODE` 를 읽도록 수정 완료.

스켈레톤을 **실제 패키지 경로로 이동** + import 를 실제 `CommonSanctionService`/DCMT 매퍼로 교체 → `mvn -o test-compile`(또는 IDE 빌드).
- **한 번에** 모든 가정 시그니처·매퍼 메서드를 강제 검증(DB·배포·JUnit 불필요).
- 빨강 = "테스트 실패"가 아니라 **위 조정 목록의 잔여**. 초록 = BE 형틀 성립.
- **열린 질문 자동 해소**: 매퍼 메서드(`updateStsCode`·`updateDoc`·`selectCdDocInqAuth`)가 실재하지 않으면 → 그건 테스트 실패가 아니라 "추가 구현 스코프".

## T2 — 빈 와이어링 검증 ⏱️~30m
앱 기동 후 `@Autowired Map<String,CommonSanctionTargetHandler>` 에 `"DCMT"` 키가 차는지.
- dev 플래그로 가드한 **임시 진단 엔드포인트**에서 `handlers.keySet()` 로깅 한 줄.
- 빈 맵이면 스캔/빈이름 문제를 **조용한 실패 전에** 포착.

## T3 — BE write-path 스파이크 (격리 dev DB만) ⛔운영금지
같은 진단 엔드포인트에서 dev 의 알려진 `demSn` 으로 `bridge.applyAction("DCMT", ...)` →
- Oracle MCP(**dev 전용**)로 승인이력 row + 호스트 `STS_CODE` 변화 확인.
- 끝에 일부러 `throw new Exception` → **전체 롤백**되는지(원자성) 확인. 롤백되면 푸시도 안 나감.

## T4 — FE wframe 스파이크 ⏱️ 브라우저
버리는 호스트 화면에 grid/buttons wframe 2개 + 하드코딩 keys.
- T0에서 찾은 **`bDataLoading` 가드 관용구**로 `fnInit` 타이밍 맞춤.
- 승인요청/승인처리 클릭 → 라운드트립 + 그리드 리로드 확인.
- 정적으로 증명 불가한 **유일한 부분 = 비동기 로드 타이밍** 만 여기서 확정.

## T5 — 수직 슬라이스 (feature 브랜치)
DCMT 한 모듈을 옵션 토글 뒤에서 end-to-end. **최종 "구현 가능" 증명.**

## 권장 순서
**T1 · T2 먼저**(합쳐 1~2시간, 블로커 대부분 포착) → 통과 시 T3 → T4 → T5.
write 경로는 **dev DB 한정**, skpmis(운영)는 **읽기(스키마/조회)만**.
