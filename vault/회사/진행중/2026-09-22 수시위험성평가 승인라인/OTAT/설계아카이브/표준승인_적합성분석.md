# 표준 승인(CommonSanctionBridge) 적합성 분석 — DCMT/CESC 실측

> 목적: 제안한 표준(가제)으로 기존 모듈의 승인 처리가 실제로 되는지 **정적 분석으로 검증**.
> 방법: 3개 모듈 세트를 병렬 에이전트로 전수 조사 → 승인 코드 인벤토리 → 표준 매핑 → 갭 적발 → 판정.
> 대상: `DcmtPopRegDcmtConfirm`(승인 팝업) · `DcmtRegPrjtDcmt`(문서등록 본화면) · `CescPopRegCompanyEquipmentSafetyCheck`(교차검증).
> 관련: [예시구현 스켈레톤 v2](../구현참고/예시구현/README.md) · [발표자료](./SCNT_표준승인_발표.html)

---

## 1. 통합 판정 — **조건부 가능 (3/3 일치)**

구조적 충돌은 **없음**. 미충족 갭이 전부 **가산적(additive) 확장**이지 재설계가 아님. 조건: ① Handler를 "쓰기 4훅"에서 "쓰기+읽기+완료후속"으로 확장 ② 보안게이트·상태 이중소유 2건을 회귀검증 대상으로 못박음.

| 모듈 | 판정 | 한 줄 |
|---|---|---|
| DcmtPopRegDcmtConfirm | 조건부 가능 | BE는 이미 코어 100% 위임 + 의견팝업 공용 → 골격 입증. 위험은 FE 분기·읽기훅·라인변경 |
| DcmtRegPrjtDcmt | 조건부 가능 | 표시·진입은 유지, 승인 처리/상태롤백/라인삭제가 본화면에 박혀 이전 필요 |
| CESC Confirm | 조건부 공유 가능 | 같은 패널/Bridge 공유 가능, 단 취소경로 매핑 + 완료후속 훅 확장 필요 |

## 2. 이미 입증된 것 (가설 아님)

- **BE 승인 영속/조회 SQL이 호스트에 0줄** — 전부 `CommonSanctionService` 위임. 의견팝업도 이미 공용 `/common/CommonPopRegSanctionOpinion.xml`.
- **Trsc 5개 = 실제 코어 동작 2개** (`actSanction`/`cancelSanction`). DCMT `trscCfmDem/Act/Rej`는 바이트 동일. 5→2→엔드포인트 1개.
- **상태매핑** `updateStsCode`: 코어 단계상태 `REG/DEM/PROG/REJ/CMPL` → 호스트 `STS_CODE 10/20/30/40/50`(DCMT) / `RCPT_STS_CODE 20~60`(CESC).
- **CESC도 동일 구조** → 공통 표준 공유 성립. 상태코드 차이는 Handler 한 곳에 격리.

## 3. 갭 → v2 보강 매핑

| # | 갭 (실측) | 발견 모듈 | v2 반영 | 난이도 |
|---|---|---|---|---|
| 1 | 읽기 게이트/가공 훅 부재 (보안등급·결과가공) | DCMT팝업 | `Handler.canView()` + `onStatusLoaded()` 신설 | 중 |
| 2 | 취소 경로 상태매핑 누락 (`updateRcptSts`가 cancel에서도 호출) | CESC | `Bridge.cancel`도 `onActionApplied` 발화(`fireAfterAction`) | 하 |
| 3 | 완료 후속 전파 (`trscUpdateEquipAfterCmpl`) | CESC | `Handler.onCompleted()` 신설, CMPL 시 자동 호출 | 중 |
| 4 | 협력사 override (전체숨김/readonly, `COOP_UPD_PSBL_TF`) | DCMT팝업 | 패널 `guard{bHideActions,bForceReadonly}` 파라미터 | 중상 |
| 5 | 승인라인변경 (`wbtnCfmChg`) | DCMT팝업 | `cips.sanction.changeLine` + 패널 버튼 + `Bridge.changeLine` | 상 |
| 6 | 번들/벌크 생성 (`trscCrtAll`) | CESC | 단건 패널 밖 — 필요한 모듈 생기면 그때 별도(지금 미생성) | 중 |
| 7 | save = upsert + CFM 역기록 | DCMT팝업 | `createDemand`→`saveDemand`(stepRows), `onDemandCreated`가 `updateDoc` | 중 |
| 8 | 본화면에 승인 처리 직접 박힘 (`save()`가 `deleteSanctionDemand` 직접호출 + `STS_CODE` 자바 롤백) | DCMT본화면 | 이 경로를 Bridge/Handler로 이전 (스켈레톤 아닌 본화면 리팩토링) | 상 |

## 4. 🔴 반드시 처리할 회귀 위험 2가지

1. **보안 누출** — `loadStatus`가 코어를 직접 부르면 `DOC_INQ_PSBL_TF`(보안등급) 권한게이트를 우회 → 상위 등급 문서 누출. "실수 = 보안사고"인 유일 항목. → v2 `canView` 게이트 필수.
2. **상태 이중소유** — 본화면(`DcmtRegPrjt`)이 `STS_CODE`를 자바에서 직접 롤백(`amWdlDoc.put("STS_CODE","10")` + `updateCfmInfoReset`)하는데 표준도 상태를 소유하면 race. → 상태 소유를 한쪽(표준)으로 일원화.

## 5. v2 표준 인터페이스 (분석 반영 후)

```java
// 훅 인자 = Map<String,Object> (Context 클래스 없이 단순화)
interface CommonSanctionTargetHandler {           // 호스트가 상태캐시·게이트·가공 할 때만 구현
    String tgtCode();
    // ── 쓰기 ──
    default void validateBeforeDemand(Map data) {}
    void onDemandCreated(Map data);   // 요청 후: 상태=요청대기 + CFM_* 역기록(updateDoc)
    void onActionApplied(Map data);   // 승인/반려/취소 후: data["STEP_STS_CODE"]로 동기화 (★act·cancel 양쪽)
    default void onCompleted(Map data) {}              // [신규] CMPL 후속 (예: CESC 장비 전파)
    // ── 읽기 [신규] ──
    default boolean canView(Map keys) { return true; }            // 보안 게이트
    default void onStatusLoaded(List<Map> rows, Map keys) {}      // 결과 가공
}

interface CommonSanctionBridgeService {
    long saveDemand(tgtCode, req, stepRows);   // upsert + 역기록
    void applyAction(tgtCode, act);            // 승인/반려 → onActionApplied
    void cancel(tgtCode, act);                 // 취소 → onActionApplied (취소 경로도 발화)
    List loadStatus(tgtCode, keys);            // canView 게이트 + onStatusLoaded 가공
    List changeLine(tgtCode, req);             // 승인라인 변경
}
// 패널: <wframe> + guard{bHideActions,bForceReadonly}
// 벌크: 단건 패널 밖 — 필요한 모듈 생기면 그때 별도 (지금 미생성)
```

## 6. 결론

> **이 계획으로 처리 가능하다 — 단 Handler를 v2(읽기·완료후속 훅 + 패널 가드)로 확장하고, 보안게이트·상태 이중소유를 회귀검증 대상으로 명시하는 조건에서.**
> 실측이 초안(4훅)의 빈틈을 정확히 메웠고, 보강이 전부 가산적이라 **표준의 골격(코어 불가침 + Bridge + 모듈당 Handler)은 그대로 유효**하다.
